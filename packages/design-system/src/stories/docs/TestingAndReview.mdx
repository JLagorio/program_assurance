# Testing and review

The system should help a person understand the situation, choose an action, complete it, and recover if it fails. A familiar visual style alone does not establish that contract. Test the whole task with realistic content, keyboard input and the conditions people actually encounter.

## Before adding an API

Start with the user's task and the semantic HTML element. Reuse a native control when its behavior answers the task. A new prop needs a distinct consumer need and a documented default, valid combinations, ownership of state, and behavior when absent. Avoid booleans that encode several mutually exclusive modes. Prefer a union when only one mode can apply. Preserve native names for native behavior.

| Question                       | Required evidence                                                                                          |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Who owns the state?            | Controlled and uncontrolled behavior, defaults, reset, and async external updates.                         |
| What reaches the DOM?          | The target for `id`, `name`, `form`, `aria-*`, `data-*`, handlers, and the ref.                            |
| What can fail?                 | Pending, rejected save, retry, cancellation, and stale completion examples.                                |
| What can be composed?          | Compound slots and valid nesting; no interactive element inside another interactive element.               |
| What does a dependency expose? | Explicit adapter types for toast, table and chart APIs; all other implementation internals remain private. |

## State and content

Every collection needs loading, empty, filtered empty, error, ready, and refreshed states where applicable. A filtered empty state keeps filters visible and offers Clear filters. A save failure keeps the draft. Announce success only after the command succeeds; if persistence is local to this browser, say so. Permissions are business rules enforced by commands as well as reflected by controls.

Use sentence case, a specific verb for actions, and an error that says what the person can do next. Name the affected record when ambiguity is possible. Essential guidance belongs beside the control. Disabled actions need a visible reason; an enabled control must navigate or perform its stated action. Do not use a notification to conceal an unimplemented operation.

## Keyboard, focus and targets

Check Tab and Shift+Tab, Enter and Space, Escape, arrow keys, Home/End and typeahead where the widget requires them. Trees maintain one tab stop and expose level, expansion and selection. Closing a modal returns focus to its opener or an explicitly supplied replacement. Failed form submission focuses the first invalid control and exposes all errors. A sticky header or action bar must not fully obscure focused content.

The web minimum target requirement is **24 by 24 CSS pixels**, subject to the WCAG 2.2 spacing, equivalent, inline, user-agent and essential exceptions. Document any exception on the actual control. Native platform point guidance is not a CSS pixel requirement. Prefer larger targets for frequent touch actions. Measure both the target and the distance to neighboring targets; a small icon inside a sufficiently large button is fine.

Inspect 320 CSS pixel width, 200% text enlargement and 400% browser zoom. A dense data table may scroll in its own region; surrounding search, headings, dialogs and actions must reflow. Check focus after scrolling, opening menus, validating a long form, collapsing navigation, and removing the selected item. Reduced-motion preference should remove nonessential movement while keeping pending state understandable through text and semantics.

## Automated checks and their limits

`node scripts/ds-check.mjs` (`npm run ds:check`) resolves public exports through the TypeScript compiler, counts executable story references (a JSX element, a call, or a stories file's meta `component` when one of its stories renders from args), checks story coverage and that every family's stories have a page, and rejects a growing exception baseline. It fails when a compound's member is a function its module does not export (docgen documents a module's exports, so the member would get no props table) and when a family page renders no `<ArgTypes>` for its stories' component. It reports, without failing yet, the exported families with no page showing generated props, and how many catalog parts the application imports (`-- --usage` lists the rest). `node scripts/ds-public-api.mjs` prints the full public value/type inventory. A reference proves use, not correctness; interaction assertions establish behavior.

`test/api-conformance.test.mjs` (in `npm test`) reads every exported part through the TypeScript program and holds it to the component contract in the component library guide: every optional prop takes `undefined`; the caller's `className` and `ref` reach the element its other props land on; and `data-slot` comes after the caller's props, before them only on the base parts the guide names. A part that differs by design names its reason in the test's `EXCEPTIONS`. `test/story-manifest.test.mjs` holds a family's first manifest story to plain parts, with no ref, spy, element or helper of its stories file, and `test/family-status.test.mjs` holds every family page to one status line.

Every exported family, ActionBar, WorkPane and Inspector included, has stories and a page, so the render, accessibility and layout checks reach all of them.

Keep one family page with useful examples, generated props and relevant usage/accessibility guidance. The props tables come from the types: a part's own props and the Base UI props it inherits (a Dialog's `open` and `onOpenChange`), not the DOM's own attributes. There is no required heading set. Omit sections that add no information, and review the prose against the current examples and implementation. What an earlier spelling is written as now goes on [Upgrading](?path=/docs/guidance-upgrading--docs), under the family's name, and the changelog entry for the rename links it.

The package runs its stories through three scripts, from the repository root:

```sh
npm run test:a11y -w packages/design-system
npm run test:layout -w packages/design-system
npm run test:gates -w packages/design-system
# one file through both layout checks, from inside packages/design-system
npx vitest run --project storybook-narrow --project storybook-contained src/stories/components/Badge.stories.tsx
```

`test:a11y` runs every story in light, dark and forced-colours Chromium using Storybook’s built-in `test` tag. Each story gets a render check; its `play` function adds interaction assertions. Axe runs alongside them, and a story fails on a console error or on a Base UI or React warning. Dark mode also checks reduced motion. Two gates ride on these runs: in light, every tab stop is focused in turn and fails when a clipping or scrolling ancestor cuts half or more of its ring; in forced colours, a selected, pressed, current or checked item fails when it looks the same as its unselected sibling once system colours replace the tokens.

`test:gates` runs four more projects, without axe: `storybook-touch`, every story on a 390px touch phone with a coarse pointer and no hover, where a control under 24 by 24 CSS pixels by axe's `target-size` rule (counting the hit area `touch-target` draws) or a control that shows only on hover fails (the kit's one touch predicate is `any-pointer: coarse`: `any-pointer-coarse:` in a class, `useTouch` in script); `storybook-short`, the overlay families in a 320 by 256 window, where a control that takes focus less than half in view, or a title nothing scrolls back to, fails; `storybook-long`, the families that show titles, values and stamps, in the 320px frame with every text 40% longer and an 80-character unbroken token added, where sideways scroll, paint past the frame or text cut with no ellipsis fails; and `storybook-rtl`, the families whose layout or keys follow the writing direction (tables, trees, tabs, toolbars, paths, timelines, fields in place, toasts, the icon rail) laid out right to left by the Direction toolbar, where a text alignment that names a physical side, anything visible past the page's right edge (its start, out of reach) or a play that fails mirrored fails. A play that measures a line's start or end, scrolls sideways or presses a sideways arrow asks `src/stories/_lib/direction.ts` (`along`, `towardsEnd`, `arrows`), so it holds either way the page reads, and `ledger/no-non-token-class` reports a class that names a physical side (`text-left`, `pl-200`, `right-0`, `border-l`, `rounded-r-large`) outside a variant that names one, with its logical twin. `test/story-gates.ts` says what each gate measures; a story that predates a gate is listed with its count in `test/gates-allow.json`, which may only shrink.

`test:layout` renders every story twice more, without axe, once its web fonts have loaded: at a 390px phone (`storybook-narrow`) and in a 320px frame on the desktop canvas (`storybook-contained`, the toolbar's Frame: 320px container). A story fails when the page scrolls sideways, a word of four or more letters breaks across two lines, or anything paints past either edge of the frame outside a scroller. At phone width, visible content past the page's left edge fails too, because no one can scroll to it. A story whose overflow is its lesson (a Don't) is listed by id, with its reason, in `test/layout-allow.json`; a fixture that overflows because of a fixed width becomes fluid instead of being listed.

Two things change how a story is measured, both visible in the story. `layout: "fullscreen"` is page-level and gets no frame, so the contained check skips it; the phone check still measures it. A story's `globals` render it at the width they pin: a phone pin is measured at that width in both checks (inside the 320px frame in the contained one), a desktop pin takes it off the phone width, and `frame: "canvas"` takes it out of the frame. Pin a width only for a play function that measures a layout existing at that width. Overlays positioned against the viewport (sheets, dialogs, toasts) are not measured for paint past an edge, but an open one's words are checked at phone width; check an overlay's fit in a render at phone width.

Keep examples and their interaction tests in the same component’s `.stories.tsx` file. Add assertions to an existing example before introducing another render fixture. Use `fn()` from `storybook/test` for callbacks instead of rendering test counters or “check refs” buttons. Add a distinct story only for a distinct useful state or workflow. The Interactions panel shows the test steps; test-only controls do not belong in the component showcase.

Storybook applies `dev`, `test` and `manifest` automatically. No custom tag is needed to opt in, and no tag opts a story into a check. `!manifest` keeps a story that renders a `_lib` helper, and every Don't, out of the manifest MCP reads ([Writing stories](?path=/docs/guidance-writing-stories--docs)). Use `!test` only for a documented case that cannot run automatically; intentional accessibility anti-examples can scope an exception to the demonstrated axe rule, with an explanation beside the story. The other accessibility checks and the render test still run. Do not recreate a separate hidden story catalog.

See [Storybook interaction tests](https://storybook.js.org/docs/writing-tests/interaction-testing) and [tags](https://storybook.js.org/docs/writing-stories/tags). The package unit suite covers nonvisual logic and token generation. The packed consumer suite verifies installation, declarations, SSR and generated CSS.

Axe does not certify keyboard quality, reading order, useful labels, focus visibility, zoom or screen-reader announcements. Review representative workflows with a screen reader and Firefox/WebKit before release. Contrast results cover the declared pairs, including alpha compositing and interactive states; they do not prove every possible composition. Resting text-field borders keep the intentionally lighter 1.5:1 visibility floor, and meet 3:1 at increased contrast. The Checkbox and Radio boundary (`color.border.bold`) and the Switch's off track (`color.background.input.track`) meet 3:1 against every surface in every mode; focus and danger borders meet 3:1 against their declared adjacent surfaces. Text and non-text checks keep their separate thresholds.

## Reference workflows for review

| Workflow                     | Stories                       | Review focus                                                             |
| ---------------------------- | ----------------------------- | ------------------------------------------------------------------------ |
| Validate and repair a form   | Patterns/Forms stories        | All errors, first focus, preserved values, custom control wiring.        |
| Pick and submit a date       | Components/DatePicker stories | Closed picker FormData, external form, reset, disabled omission.         |
| Save inline with failure     | Patterns/Editable stories     | One pending operation, rollback ownership, external updates.             |
| Complete a nested modal task | Components/Dialog stories     | Escape, successful close, return to correct opener.                      |
| Navigate a hierarchy         | Components/Tree stories       | One tab stop, hierarchy, typeahead, selected item removal.               |
| Filter records and recover   | Patterns/DataTable stories    | Empty results, clear filters, visible labels, durable supported actions. |
| Read a chart                 | Patterns/Chart stories        | Table equivalent, deterministic formatting and color mode.               |

## Ownership and lifecycle

The repository maintainers own the package contract and review changes to tokens, accessibility behavior and adapters. A contribution names a responsible reviewer and intended consumer. A new part's page opens with `**Status: Experimental.**`, saying why and who owns it, and names its known limitations; it becomes `**Status: Stable.**` once a product screen uses it and the documented checks and consumer review pass. A deprecated part's status line names its replacement, and the changelog and [Upgrading](?path=/docs/guidance-upgrading--docs#status) give the migration. User testing and assistive-technology review remain release work even when all automated checks pass.
