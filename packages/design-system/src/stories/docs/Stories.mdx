# Writing stories

The Storybook is the package's test suite and its documentation at once: every story renders in both colour modes with its play function and an axe pass (`npm run test:a11y`) and again at a phone and in a narrow frame (`npm run test:layout`), every exported part must appear in one (`npm run ds:check`), and the family's MDX page draws its examples from the same file. The MCP tool `get-storybook-story-instructions` is the generic Storybook guidance (the package runs Storybook 10); this page is what this package adds to it.

## Shape of a stories file

```tsx
import type { Meta, StoryObj } from "@storybook/react-vite";
import { expect, fn, userEvent, within } from "storybook/test";

import { Badge, Button } from "../../components";
import { Inline, Stack } from "../../primitives";
import * as storyLayout from "../_lib/matrix";

// Story-only helpers, bound locally so the MCP snippet does not list them as package exports.
const { Matrix, Specimens } = storyLayout;

const meta = {
  title: "Components/Badge",
  component: Badge,
  parameters: { layout: "padded" },
  args: { children: "Featured", variant: "default" },
} satisfies Meta<typeof Badge>;
export default meta;
type Story = StoryObj<typeof meta>;

/** The usage to copy, first, with the controls. */
export const Playground: Story = {};

/** The six reference variants beside the icon positions. */
export const Variants: Story = {
  tags: ["!manifest"],
  render: () => <Matrix rows={…} cols={…} render={…} />,
};
```

- Imports come from `@storybook/react-vite` and `storybook/test`, never the `@storybook/test` or `@storybook/react` names.
- Parts are imported by relative path from `../../components`, `../../primitives`, `../../patterns`, `../../layout`. The package never imports its own root.
- `title` is `<Category>/<Family>`: Primitives, Components, Layout, Patterns, Tokens, Guidance. One family, one file, one `title`.
- The JSDoc comment above a story is its description on the docs page. Write it as the sentence the reader needs, not the story's name again.
- The first story in the manifest is the usage to copy: plain parts and primitives, no `_lib` helper, no element, component or function of the stories file, and no ref or storybook/test spy made at module level, alone or held in an object (`const refs = { nav: createRef() }`). A callback its play checks is an arg (`args: { onCopied: fn() }`, passed as `onCopied={args.onCopied}`), which the manifest prints in place as `fn()`. MCP `docs-show` returns the code of the first three stories Storybook's manifest holds, and an agent copies them. A family's comparison story may still lead its page, tagged out of the manifest (below), so the first story MCP returns is the first plain one. A story whose render is a component of the stories file shows in the manifest as that one call (`<LoadingDemo />`), with nothing to copy, so lead with a story that renders the parts themselves, such as the Playground, wherever the family has one. Where every story of a family is such a component, the first one's `render` is the component itself (`render: PickerStates`), and the manifest shows the component's body, so that body renders the parts directly too: a value accessor or a formatter is written inline (`value={(row, column) => …}`), not a function of the file. The second and third stories in the manifest are copied too: each may name a component of the stories file, as its one call or as a stand-in the reader replaces (a demo router link), but its own code names no ref, spy, function or element of the file. A callback its play checks is an `fn()` arg, a formatter or an accessor is written inline, and a check of refs and native attributes goes in a `NativeAttributes` story tagged `!manifest`. In all three, the manifest writes an arg in only where the code passes it straight to an element it returns, as `prop={args.key}` or `{...args}`, and then drops the `args` parameter: an arg read in a callback (`onSelect={() => args.onSelect("MS-A")}`), in an expression (`{args.invalid && …}`) or in JSX passed as a prop (`render={<Link onClick={args.onNavigate} />}`) stays `args.key` in a copy that has no `args`. Such a check goes in a story tagged `!manifest`, and a Playground whose code reads its controls that way is tagged `!manifest` too. `test/story-manifest.test.mjs` reads what the manifest prints (the story's render, a named render's body, the meta's render when the story has none, and the args they take) and every helper that code reaches.
- A `children` arg written as JSX in parentheses, as Prettier writes any JSX longer than a line, shows in the manifest with its parentheses as text (`<Alert>(<>…</>)</Alert>`). Write the children in the meta's `render` (`render: (args) => <Alert {...args}>…</Alert>`) and keep `args` for the props.
- `_lib` helpers (Matrix, Specimens, Pair) are story layout, not package exports. The MCP snippet lists every relative import under the package name, so a story file binds them locally (`import * as storyLayout from "../_lib/matrix"`, then `const { Matrix, Specimens } = storyLayout`); a locally declared name is left out of the snippet's import line.
- A story whose render shows a `_lib` helper (a Matrix or Specimens comparison), and every Don't, is tagged `!manifest`. It stays in the sidebar, on its page and in every test run, and leaves the manifest MCP reads, so `docs-show` never offers a comparison grid or a Don't as code to copy. A Don't an agent must know is also a sentence on the page (its Content, or a line under the Don't canvas), which `docs-show` returns under Docs. The token sheets are the exception: their stories are the Tokens pages' only examples, and they stay in the manifest with the sheet helpers bound locally.
- A deprecated part's stories leave the manifest together: its meta sets `tags: ["!manifest"]`, so MCP never offers the part as code to copy, while its page and its tests stay. A composition page whose stories are whole workspaces built from the file's own routes (Layout/Pages) does the same; its prose and the Recipes carry the composition.
- `!manifest` is the one tag a story sets. Storybook applies `dev`, `test` and `manifest` itself, and the layout checks measure every story, so no tag opts a story into a check.

## What to cover

- Every named part of the family, rendered. `ds:check` fails on an export with no story.
- Representative states, not every permutation: default, hover and pressed through the tokens, disabled, invalid, loading, empty, error, the sizes that change behaviour. The `_lib/matrix` **Matrix** and **Specimens** helpers lay a family's variants out for comparison.
- A Do beside a Don't wherever a misuse is likely: a wrong part (a Combobox for four values), a wrong word (a label that flips with the state, OK), a missing name (an unnamed group). **Pair** in `_lib/pair` lays them out with one line each on why. The story is tagged `!manifest`, and its `play` asserts what makes the Do right and the Don't wrong: the name, the role, the description or the state a reader meets. The family's page shows it under the section the misuse belongs to (When to use it, Content), beside a sentence that says the Don't. A family with no likely misuse has no pair; a pair is never filler.
- One playground covers the controls. Keep distinct regression cases as their own stories rather than folding them into the playground.
- A `play` function on every interactive story: drive it with `userEvent`, assert the visible outcome with role and label queries on `canvas`, and assert `fn` callbacks were called. Wait for a menu to mount before asserting `aria-expanded`.
- Render once. Josef switches the mode in the toolbar; a story never renders light and dark side by side.
- A story's frame is fluid: a wrapper takes `maxWidth`, not `width`, so it fits a phone and a panel. Inside a row that sizes its children to their content (Specimens, an Inline), give the width together with `maxWidth: "100%"`. A layout inside a story responds to its container (`@container` with `@md:`), not the window (`md:`). Set Frame to 320px container in the toolbar to see a story in a narrow container.
- A behaviour that exists only at a phone gets a story that pins `viewport` in its `globals` (`ledgerPhone` is 390px, `ledgerSmall` 340px), with a `play` that asserts it: no sideways scroll, the changed element visible, a folded item reachable. Pin only where the behaviour needs it: the layout checks measure a pinned story at the width it pins, not at theirs ([Testing and review](?path=/docs/guidance-testing-and-review--docs) says how).

  ```tsx
  export const Phone: Story = {
    globals: { viewport: { value: "ledgerPhone", isRotated: false } },
    play: async () => {
      const page = document.documentElement;
      await expect(page.scrollWidth).toBeLessThanOrEqual(page.clientWidth);
    },
  };
  ```

## What fails a story

- A console error, or a Base UI or React warning on `console.warn`. `test/storybook.setup.ts` fails any story that emits one.
- An axe violation in either mode. Fix semantic and structural violations directly; a contrast or spacing violation is a design decision, so raise it instead.
- Sideways scroll at a 390px phone, a word broken across two lines, or paint past a 320px frame (`npm run test:layout`). [Testing and review](?path=/docs/guidance-testing-and-review--docs) says what the check measures and when a story is exempt.
- A gate: a focus ring its container clips, a selected item that disappears in forced colours, a control under 24px or shown only on hover on a touch phone, an overlay control out of view in a short window, or long text that overflows (`npm run test:a11y` and `npm run test:gates`). A story that predates a gate is listed with its count in `test/gates-allow.json`, which may only shrink.
- A stale `api/public-api.json`: `npm run ds:api:check` when declarations changed, `ds:api:update` when they changed on purpose.
- Drift in `eslint-plugin/components.json` or `llms.txt`; the package build regenerates both.

## The MDX page

One `<Family>.mdx` beside the stories, attached with `<Meta of={Stories} />`, so its title is the stories file's. The first line under the title is the part's status: `**Status: Stable.**`, `**Status: Experimental.**` with why and who owns it, or `**Status: Deprecated.**` with what replaces it ([Upgrading](?path=/docs/guidance-upgrading--docs#status) says what each promises). A page that compares parts or describes a composition has none. Then the page says what the part is for in a sentence or two, then `<Canvas of={Stories.X} />` for the examples worth reading, `<ArgTypes of={Part} />` for each named part, and the usage and accessibility guidance that helps. No required heading set and no "Not applicable" filler. The page documents the current API; a deprecated spelling that still works gets at most one line naming its replacement. What an earlier spelling is written as now goes on [Upgrading](?path=/docs/guidance-upgrading--docs), under the family's name, and the page links it from Related.

`api/axis-policy.json` holds optional notes on package-specific meanings of `variant`, `size`, `tone` and the other shared axes; a new part or prop does not need an entry.

## What does not belong here

An application composition. A screen from the product is verified in the running app, never mounted in a package story; the package documents neutral contracts and the application's pattern contract decides how they are used there.

## After changing a story

Call `stories-changed`, then `stories-preview` for the stories that matter, then `test-run` for the family. Report the URLs. Add a `CHANGELOG.md` entry that names the story showing the change.
