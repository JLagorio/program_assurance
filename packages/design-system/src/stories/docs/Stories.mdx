# Writing stories

The Storybook is the package's test suite and its documentation at once: every story renders in both colour modes with its play function and an axe pass (`npm run test:a11y`) and again at a phone and in a narrow frame (`npm run test:layout`), every exported part must appear in one (`npm run ds:check`), and the family's MDX page draws its examples from the same file. The MCP tool `get-storybook-story-instructions` is the generic Storybook guidance (the package runs Storybook 10); this page is what this package adds to it.

## Shape of a stories file

```tsx
import type { Meta, StoryObj } from "@storybook/react-vite";
import { expect, fn, userEvent, within } from "storybook/test";

import { Badge, Button } from "../../components";
import { Inline, Stack } from "../../primitives";
import * as storyLayout from "../_lib/matrix";

// Story-only helpers, bound locally so the MCP snippet does not list them as package exports.
const { Matrix, Specimens } = storyLayout;

const meta = {
  title: "Components/Badge",
  component: Badge,
  parameters: { layout: "padded" },
  args: { children: "Featured", variant: "default" },
} satisfies Meta<typeof Badge>;
export default meta;
type Story = StoryObj<typeof meta>;

/** The usage to copy, first, with the controls. */
export const Playground: Story = {};

/** The six reference variants beside the icon positions. */
export const Variants: Story = { render: () => <Matrix rows={…} cols={…} render={…} /> };
```

- Imports come from `@storybook/react-vite` and `storybook/test`, never the `@storybook/test` or `@storybook/react` names.
- Parts are imported by relative path from `../../components`, `../../primitives`, `../../patterns`, `../../layout`. The package never imports its own root.
- `title` is `<Category>/<Family>`: Primitives, Components, Layout, Patterns, Tokens, Guidance. One family, one file, one `title`.
- The JSDoc comment above a story is its description on the docs page. Write it as the sentence the reader needs, not the story's name again.
- The first story is the usage to copy: plain parts and primitives, no `_lib` helper. MCP `docs-show` returns the first three stories' code, and an agent copies them.
- `_lib` helpers (Matrix, Specimens, Pair) are story layout, not package exports. The MCP snippet lists every relative import under the package name, so a story file binds them locally (`import * as storyLayout from "../_lib/matrix"`, then `const { Matrix, Specimens } = storyLayout`); a locally declared name is left out of the snippet's import line.

## What to cover

- Every named part of the family, rendered. `ds:check` fails on an export with no story.
- Representative states, not every permutation: default, hover and pressed through the tokens, disabled, invalid, loading, empty, error, the sizes that change behaviour. The `_lib/matrix` **Matrix** and **Specimens** helpers lay a family's variants out for comparison. **Pair** in `_lib/pair` puts a Do beside a Don't with one line each on why: give a family a Don't story wherever a misuse is likely (a wrong part, a wrong word, a missing name), not as a required section.
- One playground covers the controls. Keep distinct regression cases as their own stories rather than folding them into the playground.
- A `play` function on every interactive story: drive it with `userEvent`, assert the visible outcome with role and label queries on `canvas`, and assert `fn` callbacks were called. Wait for a menu to mount before asserting `aria-expanded`.
- Render once. Josef switches the mode in the toolbar; a story never renders light and dark side by side.
- A story's frame is fluid: a wrapper takes `maxWidth`, not `width`, so it fits a phone and a panel. Inside a row that sizes its children to their content (Specimens, an Inline), give the width together with `maxWidth: "100%"`. A layout inside a story responds to its container (`@container` with `@md:`), not the window (`md:`). Set Frame to 320px container in the toolbar to see a story in a narrow container.
- A behaviour that exists only at a phone gets a story that pins `viewport` in its `globals` (`ledgerPhone` is 390px, `ledgerSmall` 340px), with a `play` that asserts it: no sideways scroll, the changed element visible, a folded item reachable. Pin only where the behaviour needs it: the layout checks measure a pinned story at the width it pins, not at theirs ([Testing and review](?path=/docs/guidance-testing-and-review--docs) says how).

  ```tsx
  export const Phone: Story = {
    globals: { viewport: { value: "ledgerPhone", isRotated: false } },
    play: async () => {
      const page = document.documentElement;
      await expect(page.scrollWidth).toBeLessThanOrEqual(page.clientWidth);
    },
  };
  ```

## What fails a story

- A console error, or a Base UI or React warning on `console.warn`. `test/storybook.setup.ts` fails any story that emits one.
- An axe violation in either mode. Fix semantic and structural violations directly; a contrast or spacing violation is a design decision, so raise it instead.
- Sideways scroll at a 390px phone, a word broken across two lines, or paint past a 320px frame (`npm run test:layout`). [Testing and review](?path=/docs/guidance-testing-and-review--docs) says what the check measures and when a story is exempt.
- A gate: a focus ring its container clips, a selected item that disappears in forced colours, a control under 24px or shown only on hover on a touch phone, an overlay control out of view in a short window, or long text that overflows (`npm run test:a11y` and `npm run test:gates`). A story that predates a gate is listed with its count in `test/gates-allow.json`, which may only shrink.
- A stale `api/public-api.json`: `npm run ds:api:check` when declarations changed, `ds:api:update` when they changed on purpose.
- Drift in `eslint-plugin/components.json` or `llms.txt`; the package build regenerates both.

## The MDX page

One `<Family>.mdx` beside the stories, attached with `<Meta of={Stories} />`, so its title is the stories file's. It opens with what the part is for in a sentence or two, then `<Canvas of={Stories.X} />` for the examples worth reading, `<ArgTypes of={Part} />` for each named part, and the usage and accessibility guidance that helps. No required heading set and no "Not applicable" filler. A larger migration gets one focused guide the page links to.

`api/axis-policy.json` holds optional notes on package-specific meanings of `variant`, `size`, `tone` and the other shared axes; a new part or prop does not need an entry.

## What does not belong here

An application composition. A screen from the product is verified in the running app, never mounted in a package story; the package documents neutral contracts and the application's pattern contract decides how they are used there.

## After changing a story

Call `stories-changed`, then `stories-preview` for the stories that matter, then `test-run` for the family. Report the URLs. Add a `CHANGELOG.md` entry that names the story showing the change.
