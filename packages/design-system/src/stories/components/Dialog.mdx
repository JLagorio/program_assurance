# Dialog

**Status: Stable.**

A focused task over the page: a create or edit form, a review, a choice that needs more than a sentence. Built on [Base UI Dialog](https://base-ui.com/react/components/dialog) with [shadcn’s composition](https://ui.shadcn.com/docs/components/base/dialog) and Ledger's tokens.

<Canvas of={Stories.Form} />

## When to use it

- **A create or edit form**, titled with the operation: Create task, Edit member. The trigger, the title and the primary say the same words.
- **A task the reader finishes or abandons** before going back to the page.

Not for a decision that needs one sentence: that is an [AlertDialog](?path=/docs/components-alertdialog--docs). Not for a task at its button (a filter, a reason): that is a [Popover](?path=/docs/components-popover--docs). Not for work beside a list the reader keeps using: that is the Shell's panel. A modal edge panel is a [Sheet](?path=/docs/components-sheet--docs), and a phone's bottom sheet a [Drawer](?path=/docs/components-drawer--docs).

## Anatomy

```tsx
<Dialog open={open} onOpenChange={setOpen} pending={pending}>
  <DialogContent width="medium" initialFocus={firstField}>
    <DialogHeader>
      <DialogTitle>Create task</DialogTitle>
      <DialogDescription>Describe the work.</DialogDescription>
    </DialogHeader>
    <DialogBody>
      <form id={formId} noValidate onSubmit={submit}>
        …fields
      </form>
    </DialogBody>
    <DialogFooter>
      <DialogClose render={<Button variant="subtle" />}>Cancel</DialogClose>
      <Button type="submit" form={formId} variant="primary" isLoading={pending}>
        Create task
      </Button>
    </DialogFooter>
  </DialogContent>
</Dialog>
```

- **DialogContent** brings its portal, the blanket and a close button at the top end, an IconButton named Close with no tooltip. The close button is first in the Tab order, where it is drawn; the first field still takes focus when the dialog opens. It records the overlay surface as the current one, so a sticky header, a pinned cell or a scroll arrow inside paints the dialog's colour, not the page's.
- **DialogHeader** holds the title and the description; the title is the dialog's h2, a [Heading](?path=/docs/primitives-heading--docs) at `overlay` (15/22 medium), and headings inside the dialog start at h3. Both wrap an unbroken value, such as a record's code or a server's error, inside the popup.
- **DialogBody** is the one scrolling region, with the dialog's inset. Put the form in it and the buttons in the footer; never make a `fieldset` or a hand-written `div` the scroller.
- **DialogFooter** stays outside the scroll, on the dialog's own surface below a hairline, with Cancel, a subtle button, before the primary. `showCloseButton` adds a subtle Close in Cancel's place, before the children.
- DialogPortal and DialogOverlay are exported for a custom popup.

## Widths

`width` on DialogContent picks a step; do not set pixels in `style`.

| `width`      | Size                        | For                                  |
| ------------ | --------------------------- | ------------------------------------ |
| `small`      | 400px                       | A short question with a field or two |
| `medium`     | 520px, the default          | A form of a few fields               |
| `large`      | 760px                       | A form in two columns, or a table    |
| `xlarge`     | 960px                       | A table beside a preview             |
| `fullscreen` | The window, less the gutter | A task that needs the whole window   |

Every step keeps a `space.200` gutter on each side of the window, so a dialog on a phone is the phone's width less the gutter. Choose the width by the task, so dialogs of the same kind open at the same size. An [AlertDialog](?path=/docs/components-alertdialog--docs) takes the same words for the same widths, `small` by default, and `xsmall` 320px below them for a one-line question.

## Scrolling and short windows

The body takes the height the header and footer leave, at least 80px, and scrolls. Read-only content that overflows makes it a tab stop, named "Content, scrolls", so the keyboard can scroll what a pointer can.

<Canvas of={Stories.Scrollable} />

In a window under 30rem tall (a landscape phone, or a laptop at 200% to 400% zoom) the popup becomes the one scroller: the header scrolls away with the body, the footer stays at the bottom, and every field and the primary can still be reached and seen. The footer keeps its height as the popup's scroll padding, so a field that takes focus scrolls clear of it rather than under it.

## Pending

`pending` on the Dialog holds it while a save or another command runs. Every request to close is cancelled before `onOpenChange` hears of it (Escape, the blanket, the close button, any DialogClose), the close controls are disabled, the built-in close button and a DialogClose rendered as a kit Button stay focusable while they are (`aria-disabled`), and the popup is `aria-busy`. Close the dialog yourself when the command succeeds, with `open={false}`. `pending` does not disable the form: wrap the fields in `<FieldSet disabled={pending}>`, give the submit button `isLoading`, and move focus to that button before the fields lock, since it stays focusable while it loads.

A failed save keeps the dialog and the draft, ends the pending state and says what to change.

## Accessibility

- **A title names the dialog**; a DialogDescription, when there is one, describes it.
- **Focus moves in and comes back.** The first field takes focus through `initialFocus` on DialogContent, never through `autoFocus` on the field. A Dialog opened from state records the element that had focus as it opens and returns focus there when it closes, even when a field took focus as it mounted, as long as that element is still on the page and enabled; when it goes away with the task, pass `finalFocus`. Keep the opener enabled while its dialog is open.
- **Base UI owns** the focus trap, Escape, the outside press and nested popups: a Select or a DatePicker inside closes on its own Escape first.
- **One stack is allowed:** an AlertDialog over the Dialog that owns the decision, such as the discard prompt for a dirty draft. Render it inside DialogContent: the dialog under the prompt dims, so its buttons read as out of play, and the page keeps one blanket. An independent record workflow replaces the dialog instead of stacking.
- **Forced colours keep the edge.** The popup draws a CanvasText outline where its fill and shadow are replaced, and the blanket stays a veil of Canvas. A press on the blanket while the dialog is `pending` keeps focus where it was.

## Content

- The title is the operation and the singular noun; the primary says the same words, never OK, Submit or Save alone.
- Cancel, a subtle DialogClose, comes before the primary. A dialog whose choices apply as they are made has no draft to cancel, so its secondary is Close.
- Validate on submit with the primary enabled. Errors say what fixes the field; an [ErrorSummary](?path=/docs/components-errorsummary--docs) lists them all when the form is longer than a few fields.
- Button labels stay on one line.
- A title that names a record may hold its code; it wraps rather than running past the edge. Say a failure's cause in the body, through an Alert or a FieldError, not in the title.

## Props

Dialog takes Base UI Dialog's root props, `open`, `defaultOpen`, `onOpenChange` (its details say why: `reason` is `escape-key`, `outside-press`, `close-press` or another, and `cancel()` keeps the dialog open), `onOpenChangeComplete`, `modal`, `disablePointerDismissal`, `actionsRef` and `handle`, and Ledger's `pending`. DialogContent takes the popup's `initialFocus`, `finalFocus`, `render`, `className` and `style`, and Ledger's `width` and `showCloseButton`. DialogTrigger, DialogClose, DialogTitle and DialogDescription take Base UI's part props, `render` among them. Every part takes its element's native attributes, and its `data-slot` comes after them, so a caller's attribute never renames the part (Native attributes, below). The title and the description are the exception: another part renders as them through `render` (a PageHeader.Title as the title) and its `data-slot` names the element, as it does on a Button. The types are in [Base UI's API reference](https://base-ui.com/react/components/dialog#api-reference).

## Don't

The trigger, the title and the primary say the same operation, with Cancel before the primary, never a title that names no operation or an OK. A failure is said in the body with what retrying does, never in the title.
