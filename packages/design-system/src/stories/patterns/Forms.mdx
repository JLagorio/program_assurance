# Forms

**Forms is a pattern**, composed from Field, input controls, layout primitives and buttons. There is no standalone Form component. TanStack Form owns form state and validation; Ledger owns the presentation.

How the form controls go together: which control answers which question, how a form is laid out, how required fields and errors work, and where the buttons go. Each control has its own page; this one is the choice between them and the rules they share.

## Variants

| The answer                                               | The control                                                                                                       |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| One line of free text: a name, an email, a number        | [Input](?path=/docs/components-input--docs), with `type` for the value's kind.                                    |
| Several lines: a note, a description, a narrative        | [Textarea](?path=/docs/components-textarea--docs), with `rows` for the expected length.                           |
| A search box, a number with a unit                       | [InputGroup](?path=/docs/components-inputgroup--docs) around the Input.                                           |
| One answer from visible choices                          | [RadioGroup](?path=/docs/components-radiogroup--docs).                                                            |
| One of four to a dozen plain words                       | [Select](?path=/docs/components-select--docs).                                                                    |
| One of a short list whose options carry a Dot or a Badge | [Select](?path=/docs/components-select--docs).                                                                    |
| One of many, or names the reader would type              | [Combobox](?path=/docs/components-combobox--docs).                                                                |
| Several things that can each be true                     | [Checkbox](?path=/docs/components-checkbox--docs)es in a FieldSet with FieldLegend.                               |
| An on/off setting                                        | [Switch](?path=/docs/components-switch--docs), with an external label or Field.                                   |
| A day to schedule                                        | [DatePicker](?path=/docs/components-datepicker--docs). A remembered date is an Input with the format in the hint. |
| A record: a person, a control, a requirement             | Combobox, or a [RecordPicker](?path=/docs/patterns-recordpicker--docs) when the choice needs more than a row.     |

## Anatomy

Compose each [Field](?path=/docs/components-field--docs) from a FieldLabel, control and FieldDescription or FieldError. Native IDs and ARIA connect them. A group of choice controls uses FieldSet and FieldLegend. The Fields stack `space.200` apart, or sit in a Grid when the answers are short. The buttons come last.

| Part    | What it is                                                                                                                   |
| ------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Field   | Label, control, message. The label is a noun in sentence case; the hint a sentence; the error what fixes it.                 |
| Group   | FieldSet and FieldLegend: a legend over Checkboxes or a RadioGroup, with the hint and the error for the group.               |
| Section | Group related fields under a clear heading, with `space.300` between sections.                                               |
| Buttons | An Inline at the end of the form, aligned to the end: Cancel as a subtle Button, then the primary. The primary says the act. |

## Sizes

- **Labels above by default.** Horizontal and responsive fields support compact choices and settings rows.
- **Each field as wide as its answer.** In a six-column Grid, an acronym takes two columns, a name four, an owner three, a description the row. A field wider than its answer lies about the answer.
- **One column on a narrow screen.** The Grid collapses; the order stays.
- **`space.200`** (16px) between fields, **`space.300`** (24px) between sections, **`space.100`** (8px) between the choices of a group.
- **The first field takes focus** in a dialog or a sheet that exists to fill the form (`autoFocus`). On a page, nothing does.

## Modifiers

- **Required is marked, optional is not.** Add an aria-hidden asterisk to FieldLabel and `aria-required` to the control; the form checks on submit.
- **When most of a form is required, mark nothing**, and say "Optional." in the hint of the few that are. The rule is per product, not per form: the products' record forms mark required.
- **Choose one validation presentation.** Use `noValidate` when the application supplies its own error summary and inline messages. Native `required` remains available for native form validation; `aria-required` communicates the requirement on the control.

## States

- **TanStack Form owns state.** Create the form with `useForm`, bind each control through a `form.Field` render prop, and submit a native `<form>` with `form.handleSubmit()`.
- **Validate with Zod.** The main example uses `onDynamic` with `revalidateLogic({ mode: "blur", modeAfterSubmission: "change" })`: validate on blur initially, then on change after submission, with errors shown for touched invalid fields. One validation slot avoids stale messages from another mode. The example below uses only `onSubmit`, so validation runs when Save is pressed. Submit-only validation does not promise immediate feedback as the user repairs a value.
- **Keep Save available for incomplete values.** Disable it while submitting, using `form.Subscribe`; show success only after persistence completes. The examples save locally for demonstration.
- **Expose errors accessibly.** Render issue messages with FieldError. Set `data-invalid` on Field, `aria-invalid` on the control, and connect the message ID with `aria-describedby`. The main example focuses the first invalid control after submission.
- **Reset deliberately.** Use `form.reset()` for an explicit Reset action. Preserve the draft after a server failure.

## Content

- **Cancel, then the primary**, at the end of the row, aligned to the end. The primary's label is the act: Create program, Save statement, Assign. Never OK or Submit.
- **A form that saves as it goes has no buttons**: an [Editable](?path=/docs/components-editable--docs) value on a record, a Switch in a settings list.
- **A destructive act is not a form's primary**; it is a danger Button with an [AlertDialog](?path=/docs/components-alertdialog--docs).

## Accessibility

Use a visible label for every control. Connect FieldLabel using `htmlFor` and the control’s `id`; connect descriptions and errors using `aria-describedby`. Custom controls forward native IDs, ARIA and refs to their actual input. Groups use a fieldset and legend. On failed submit, focus the first invalid field and present all errors together when a form spans several sections. Keep submitted values after a server failure.

## Props

Not applicable: Forms is a composition pattern, with no component props of its own. Import `useForm` from `@tanstack/react-form` and `z` from `zod` (Zod 3.25+ or 4 supports Standard Schema). Applications declare these dependencies themselves; Ledger's controls do not depend on a form library.

### TanStack and shadcn anatomy

This follows the [shadcn TanStack Form guide](https://ui.shadcn.com/docs/forms/tanstack-form) and [TanStack validation documentation](https://tanstack.com/form/latest/docs/framework/react/guides/validation). Field uses the same flat label, description and error parts. FieldGroup, Stack or Grid supplies layout. The caller puts `data-invalid` on Field and `aria-invalid` on the actual control.

```tsx
const form = useForm({
  defaultValues: { title: "" },
  validators: {
    onSubmit: z.object({ title: z.string().trim().min(1, "Enter a title.") }),
  },
  onSubmit: async ({ value }) => {
    await saveRecord(value);
  },
});

<form
  onSubmit={(event) => {
    event.preventDefault();
    void form.handleSubmit();
  }}
>
  <Stack space="space.200">
    <form.Field name="title">
      {(field) => {
        const isInvalid = field.state.meta.isTouched && !field.state.meta.isValid;
        return (
          <Field data-invalid={isInvalid}>
            <FieldLabel htmlFor="title">
              Title
              <span aria-hidden className="text-danger">
                {" "}
                *
              </span>
            </FieldLabel>
            <Input
              id="title"
              aria-describedby={isInvalid ? "title-error" : undefined}
              name={field.name}
              value={field.state.value}
              required
              onBlur={field.handleBlur}
              onChange={(event) => field.handleChange(event.target.value)}
              aria-invalid={isInvalid}
            />
            {isInvalid && <FieldError id="title-error" errors={field.state.meta.errors} />}
          </Field>
        );
      }}
    </form.Field>
    <Button type="submit">Save</Button>
  </Stack>
</form>;
```

The live examples use `noValidate` to demonstrate schema errors. For production, retain native constraints such as `required`, `type` and `maxLength`; omit `noValidate` when native browser feedback is appropriate. Use `aria-required` and a visible label marker when only an accessible requirement is intended.

Bind Input, and Textarea with `value`, `onBlur={field.handleBlur}` and `onChange` passing `event.target.value`. Select and RadioGroup use `value` and `onValueChange={field.handleChange}`; Checkbox and Switch use boolean `checked` and `onCheckedChange`; a checkbox’s mixed presentation uses the separate boolean `indeterminate` prop. Combobox uses Root `value`/`onValueChange` and forwards blur through ComboboxInput; DatePicker uses `value`/`onChange`. Forward blur to the focusable control. For checkbox arrays, use `form.Field` with `mode="array"` and TanStack's `pushValue`/`removeValue` helpers.

### Existing forms

Application forms formerly using `useRequired` now use TanStack through the application-owned `useRecordForm` policy: Zod required checks, conditional requirements, validation on submit followed by validation on change, nested drafts, and command selection through submit metadata. Their controls bind through `form.Field`.

`useRequired` remains exported for compatibility with older consumers and component examples; it is a custom helper, not TanStack Form. Its legacy interaction examples verify required checks, custom control binding and focus recovery. New forms should use the TanStack pattern above.

## Don't

Do not disable submit merely because values are incomplete, discard a draft after failure, use placeholders as labels, or announce success before saving. Do not put a button inside a link. Keep essential instructions visible, and let long translated labels wrap.
