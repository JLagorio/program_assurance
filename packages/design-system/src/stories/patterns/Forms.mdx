# Forms

**Forms is a pattern**, composed from Field, input controls, layout primitives and buttons. There is no standalone Form component. TanStack Form owns form state and validation; Ledger owns the presentation.

How the form controls go together: which control answers which question, how a form is laid out, how required fields and errors work, and where the buttons go. Each control has its own page; this one is the choice between them and the rules they share.

## Variants

| The answer                                               | The control                                                                                                       |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| One line of free text: a name, an email, a number        | [Input](?path=/docs/components-input--docs), with `type` for the value's kind.                                    |
| Several lines: a note, a description, a narrative        | [Textarea](?path=/docs/components-textarea--docs), with `rows` for the expected length.                           |
| A search box, a number with a unit                       | [InputGroup](?path=/docs/components-inputgroup--docs) around the Input.                                           |
| One answer from visible choices                          | [RadioGroup](?path=/docs/components-radiogroup--docs).                                                            |
| One of four to a dozen plain words                       | [Select](?path=/docs/components-select--docs).                                                                    |
| One of a short list whose options carry a Dot or a Badge | [Select](?path=/docs/components-select--docs).                                                                    |
| One of many, or names the reader would type              | [Combobox](?path=/docs/components-combobox--docs).                                                                |
| Several things that can each be true                     | A [CheckboxGroup](?path=/docs/components-checkboxgroup--docs) of Checkboxes under a FieldLegend.                  |

| A day to schedule                                        | [DatePicker](?path=/docs/components-datepicker--docs). A remembered date is an Input with the format in the hint. |
| A record: a person, a control, a requirement             | Combobox, or a [RecordPicker](?path=/docs/patterns-recordpicker--docs) when the choice needs more than a row.     |

## Anatomy

Compose each [Field](?path=/docs/components-field--docs) from a FieldLabel, the control, a FieldDescription and a FieldError. The Field ties them together: no ids, no `htmlFor`, no `aria-describedby`. A group of choices is a Field around a FieldSet (or a CheckboxGroup) with a FieldLegend. The Fields stack `space.200` apart, or sit in a Grid when the answers are short. The buttons come last.

| Part    | What it is                                                                                                                   |
| ------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Field   | Label, control, message. The label is a noun in sentence case; the hint a sentence; the error what fixes it.                 |
| Group   | A Field around a FieldSet or CheckboxGroup: a legend over the choices, with the hint and the error for the group.            |
| Section | Group related fields under a clear heading, with `space.300` between sections.                                               |
| Buttons | An Inline at the end of the form, aligned to the end: Cancel as a subtle Button, then the primary. The primary says the act. |

## Sizes

- **Labels above by default.** Horizontal and responsive fields support compact choices and settings rows.
- **Each field as wide as its answer.** In a six-column Grid, an acronym takes two columns, a name four, an owner three, a description the row. A field wider than its answer lies about the answer.
- **One column on a narrow screen.** The Grid collapses; the order stays.
- **`space.200`** (16px) between fields, **`space.300`** (24px) between sections, **`space.100`** (8px) between the choices of a group.
- **The first field takes focus** in a dialog or a sheet that exists to fill the form (`autoFocus`). On a page, nothing does.

## Modifiers

- **Required is marked, optional is not.** Pass `required` to the Field: the control announces it and the label shows the asterisk, hidden from its name. The form checks on submit.
- **When most of a form is required, mark nothing** (`FieldLabel required={false}`), and say "Optional." in the hint of the few that are. The rule is per product, not per form: the products' record forms mark required.
- **Choose one validation presentation.** Use `noValidate` when the application supplies its own messages and [ErrorSummary](?path=/docs/components-errorsummary--docs). The Field's `required` is not a native constraint; native `required` on the control makes the browser and Base UI check it too, so leave it off when the form library validates.

## States

- **TanStack Form owns state.** Create the form with `useForm`, bind each control through a `form.Field` render prop, and submit a native `<form>` with `form.handleSubmit()`.
- **Validate with Zod, on submit, then on change.** The main example uses `onDynamic` with `revalidateLogic({ mode: "submit", modeAfterSubmission: "change" })`: nothing is marked until the first submission, then each field clears as the reader repairs it. One validation slot avoids stale messages from another mode. A product that validates on blur passes `mode: "blur"`. The Required on submit example uses only `onSubmit`, which does not update as the reader repairs a value.
- **Keep the primary available for incomplete values.** Disable it while submitting, using `form.Subscribe`; show success only after persistence completes. The examples save locally for demonstration.
- **Mark the field, say what fixes it.** Pass `invalid` to the Field and the messages to FieldError; the control is marked and described by them. After a failed submission, focus the first invalid control; when the form is long or spans steps, show an ErrorSummary above it instead, which takes focus and lists every issue.
- **Reset deliberately.** Use `form.reset()` for an explicit Reset action. Preserve the draft after a server failure.

## Content

- **Cancel, then the primary**, at the end of the row, aligned to the end. The primary's label is the act: Create program, Save statement, Assign. Never OK or Submit.
- **A form that saves as it goes has no buttons**: an [Editable](?path=/docs/patterns-editable--docs) value on a record, a Switch in a settings list.
- **A destructive act is not a form's primary**; it is a danger Button with an [AlertDialog](?path=/docs/components-alertdialog--docs).

## Style

| Form                                   | Where                                                                                                           |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| A focused create or edit task          | Dialog, with first-field focus and a DialogFooter outside the scrolling body.                                   |
| A multi-step setup                     | A page wizard when the workflow needs several stages.                                                           |
| One contextual filter or reason        | Popover at its trigger.                                                                                         |
| One value on a record                  | Editable, read in place and edited on activation.                                                               |
| A selection or parent-owned draft task | A specifically documented Sheet or RecordBrowser workflow; not a second default for ordinary create/edit forms. |

Use Cancel as a subtle button before the operation's primary. Preserve dirty drafts and pending saves when closing or navigating. In Program Assurance, the product contract names the closed exception list; field count alone never switches a create/edit task between Dialog and Sheet.

## Accessibility

Use a visible label for every control. Inside a Field the label, hint and error reach the control without ids; custom controls that render a Ledger control, or forward native props to one, take the binding too. Groups use a fieldset and legend. On failed submit, focus the first invalid field, or an ErrorSummary that lists every error when a form spans several sections or steps. Inline errors are not live regions; the summary is. Keep submitted values after a server failure.

## Form libraries

Forms is a composition pattern, with no component props of its own. Import `useForm` from `@tanstack/react-form` and `z` from `zod` (Zod 3.25+ or 4 supports Standard Schema). Applications declare these dependencies themselves; Ledger's controls do not depend on a form library.

### TanStack and shadcn anatomy

This follows the [Base UI TanStack guide](https://base-ui.com/react/handbook/forms#tanstack-form) and the [TanStack validation documentation](https://tanstack.com/form/latest/docs/framework/react/guides/validation). Field uses the flat label, description and error parts; FieldGroup, Stack or Grid supplies layout. The Field takes `invalid` from the field's meta and wires the rest.

```tsx
const form = useForm({
  defaultValues: { title: "" },
  validationLogic: revalidateLogic({ mode: "submit", modeAfterSubmission: "change" }),
  validators: {
    onDynamic: z.object({ title: z.string().trim().min(1, "Enter a task title.") }),
  },
  onSubmit: async ({ value }) => {
    await saveRecord(value);
  },
});

<form
  noValidate
  onSubmit={(event) => {
    event.preventDefault();
    void form.handleSubmit();
  }}
>
  <Stack space="space.200">
    <form.Field name="title">
      {(field) => {
        const invalid = field.state.meta.isTouched && !field.state.meta.isValid;
        return (
          <Field invalid={invalid} required>
            <FieldLabel>Task title</FieldLabel>
            <Input
              name={field.name}
              value={field.state.value}
              onBlur={field.handleBlur}
              onValueChange={field.handleChange}
            />
            <FieldError errors={invalid ? field.state.meta.errors : []} />
          </Field>
        );
      }}
    </form.Field>
    <Button type="submit" variant="primary">
      Create task
    </Button>
  </Stack>
</form>;
```

The live examples use `noValidate` and let the schema report every error. The Field's `required` announces and marks without a native constraint. Native constraints on the control (`required`, `type`, `pattern`) are also checked by Base UI inside a Field: after an Enter in the field, or on each change once the form has marked it invalid. Leave them off the control when the form library already checks the same rule.

Bind Input, and Textarea with `value`, `onBlur={field.handleBlur}` and `onChange` passing `event.target.value`. Select and RadioGroup use `value` and `onValueChange={field.handleChange}`; Checkbox and Switch use boolean `checked` and `onCheckedChange`; a checkbox’s mixed presentation uses the separate boolean `indeterminate` prop. Combobox uses Root `value`/`onValueChange` and forwards blur through ComboboxInput; DatePicker, DateRangePicker, TimeField and DateTimeField use `value`/`onValueChange` as well, reporting ISO strings. Forward blur to the focusable control. For checkbox arrays, use `form.Field` with `mode="array"` and TanStack's `pushValue`/`removeValue` helpers.

### Validation and recovery

The recovery example combines native inputs, an InputGroup, a custom input, Select and Combobox. TanStack owns editable values and metadata; native form submission also includes a control associated from outside the form. A failed submission shows an ErrorSummary, which takes focus and leads to each field. The Zod schema requires an owner only for Assigned status, so changing that status clears the obsolete error and the Field's `required` follows it. A local async validator simulates a server rejection for `taken@example.test`; the rejected value is kept until the reader changes it, because TanStack clears a submit-time error on the field's next blur. Reset clears the draft and validation state.

### Migrating from useRequired

`useRequired` is removed. Use TanStack's `useForm` and `form.Field`, schema validators, and `revalidateLogic({ mode: "submit", modeAfterSubmission: "change" })` for required checks that update as the user repairs a submission. Use `form.reset()` for Reset, and `onSubmitInvalid` with a form-scoped invalid-control lookup, an explicit ref, or an ErrorSummary for focus. Return field errors from `onSubmitAsync` for server validation. Package examples import TanStack directly.

## Don't

Do not disable submit merely because values are incomplete, discard a draft after failure, use placeholders as labels, or announce success before saving. Do not put a button inside a link. Keep essential instructions visible, and let long translated labels wrap.
