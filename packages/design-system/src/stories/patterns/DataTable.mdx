# Data table

**Status: Stable.**

The register with its state. [Table](?path=/docs/components-table--docs) is the markup and stays for a table with nothing to sort, filter, page or choose. `DataTable` is the same parts drawn from a TanStack Table 9 instance: the columns are declared by kind, the state has an owner, and every feature is one option on the hook and one part in the renderer. No route sorts, filters or pages by hand.

## Metrics

`DataTable.Metrics` wraps a toolbar, an optional summary region and the table. It starts closed. Put `DataTable.MetricsTrigger` in the toolbar actions and `DataTable.MetricsContent` directly below the toolbar. Compose the content with a `Stat.Grid` of `Stat.Tile`s, whose columns follow its own width rather than the window's.

Opening metrics only changes the disclosure. Search, filters, sorting and selection keep their state. The app supplies the values and decides whether they summarize all records or the filtered rows; make that scope clear in the content.

```tsx
<DataTable.Metrics>
  <Toolbar
    search={table.state.globalFilter}
    onSearch={table.setGlobalFilter}
    actions={<DataTable.MetricsTrigger />}
  />
  <DataTable.MetricsContent className="px-200 py-100">
    <Stat.Grid cols={3}>
      <Stat.Tile label="Total findings" value={findings.length} />
      <Stat.Tile label="Verified" value={verified} />
    </Stat.Grid>
  </DataTable.MetricsContent>
  <DataTable table={table} />
</DataTable.Metrics>
```

The root accepts [Collapsible](?path=/docs/components-collapsible--docs) props, including `defaultOpen` or controlled `open` and `onOpenChange`. The trigger accepts native button props and a ref, `size` and `variant`; its default is a small secondary button with a chart icon and the localized “Metrics” label. Children replace the label. The content accepts Collapsible content props, including `forceMount`, native props and a ref. Its default region name is localized “Metrics”; `aria-label` or `aria-labelledby` can name a custom summary.

## Group by

`DataTable.GroupBy` replaces a row of grouping pills with one toolbar menu. It shows the selected field, checks that choice in the menu, and offers **None** to return to an ungrouped list. The active treatment matches Metrics. `options` supplies `{ value, label }` fields; `value` and `onValueChange` belong to the caller. The empty string means no grouping. Native button attributes and refs reach the trigger.

For `useDataTable`, pass the same value as `groupBy`: it is the grouping, however often it changes, and each new grouping opens its groups. Pagination returns when grouping is cleared; search, filters, selection and column settings retain their existing owners. A grouped table with no rows left draws the filtered empty.

```tsx
const [group, setGroup] = useState("");
const table = useDataTable({ columns, data, groupBy: group || undefined });
// Inside the toolbar actions:
<DataTable.GroupBy options={groupOptions} value={group} onValueChange={setGroup} />;
```

The menu also works with a collection drawn without DataTable: its `value` and `onValueChange` are the caller's.

`DataTable.Filters table={table} columns={["status", "owner"]}` collects multiple filters in one toolbar popover. It reuses each column's existing checkbox, text or range fields. The trigger shows the number of filtered columns; **Clear all filters** clears column filters while retaining search, grouping and selected records. `DataTable.Filter` remains available for a single exposed filter chip.

Facet choices and counts follow the current data, search and other column filters, including rows loaded or replaced after mount. A facet with nothing in it says **No values to filter by** rather than opening blank.

<Canvas of={Stories.LiveFilters} />

What a facet holds:

- **Its order holds.** A status map's order, else the alphabet; the counts never reorder the list under the reader's pointer.
- **A chosen value stays.** When the search or another filter removes its rows, a checked value is still listed, at 0, so it is unchecked where it was checked.
- **A long facet takes a search.** Above eight values a search field sits over the checkboxes ("Search Assigned to"); Escape clears it first. The popover never runs past the window: a long list scrolls inside it.
- **Several values in a row facet one by one.** A `list` column (the people on a task, the types of a control) lists each item once, counted per row that holds it, and a row matches when it holds any item chosen; `emptyLabel` lists the rows with none. Never join an array into one string to get checkboxes: the facet then lists the combinations, and choosing one value misses the rows that hold it with another.

<Canvas of={Stories.FacetsStory} />

A number or date column filters by a range, either end open. A date's ends are two DatePickers, the one limiting the other, and the chip says the range as the cells say dates ("Mar 1 – May 31, 2026"); a number's placeholders are the lowest and highest values in the reader's numerals. A start after the end is flagged at the end, in words.

<Canvas of={Stories.RangeFiltersStory} />

For filters owned outside the table, pass `additionalFilters={{ content, count, onClear }}`. The supplied fields appear first, contribute to the active count, and reset with **Clear all filters**, as a scope filter kept in the URL does.

**A table the server filters** (`manual`) holds one page of rows, so it cannot build a facet or count a saved question from them. Pass the server's values as `options` (`{ value, label, count }`, in the order to show) to `DataTable.Filter`, or by column to `DataTable.Filters`, and each question's count by id as `counts` to `DataTable.Presets`. While the next page, sort, search or filter is on its way, pass `state="refreshing"`: the rows the reader has stay under `aria-busy` with the quiet bar, rather than standing as the answer to a question they no longer answer. With a query library that keeps the last page while the next loads, that is while the rows shown are the kept ones (see Server).

<Canvas of={Stories.ServerFacets} />

`DataTable.Presets` with `variant="menu"` is one button that reads the question in force and its count ("All findings 150"). Those visible words are its name, so a speech user says what they see; `aria-label` (the locale's "Saved questions" unsaid) is its description, and on the strip it names the group. A question is in force when the table's filters ask it, however they were set: a facet's values in any order, or one value on its own against a list of one.

## Sort menu

`DataTable.Sort table={table}` is the sort as a toolbar menu: the column under **Sort by**, then the direction, in words that follow the column: **Oldest first** and **Newest first** for a date, **Lowest first** and **Highest first** for a number, **A to Z** and **Z to A** for an id, a name or a person, and **Ascending** and **Descending** for a status, a column with its own `sortBy` and a custom sort. The trigger reads the sort ("Sort: Due") with the direction's arrow, and its accessible name starts with those words and adds the direction ("Sort: Due, Oldest first"). Choices keep the menu open, so the column and the direction are set in one visit; Escape closes it and focus returns to the trigger. While nothing is sorted the direction waits, disabled, for a column.

Use it in every register that folds columns (every table but one with `responsive={false}`), and wherever the reader should see the order without reading the headers. A responsive table folds lower-priority columns into each row's More fields, and a folded column has no header to sort by or to carry the arrow; the menu offers every sortable column the reader shows, folded or not. It writes the table's sorting, so a drawn header keeps its arrow and `aria-sort`, the view store and `useTableQuery` see the change, and no header claims a sort it does not have. Put it among a [Toolbar](?path=/docs/patterns-toolbar--docs)'s display controls, before Columns and Settings, where it folds into More with them. A table that never folds does not need it: the headers sort, and their column menus do too. With `enableMultiSort` the menu shows and replaces the first sort.

`columns` limits and orders what it offers; `label` is the trigger's words before anything is sorted. Native button props and a ref reach the trigger.

```tsx
<Toolbar search={table.state.globalFilter} onSearch={table.setGlobalFilter}>
  <DataTable.Sort table={table} />
  <DataTable.Columns table={table} />
  <DataTable.Settings table={table} />
</Toolbar>
```

## Keeping the question

The view store keeps the reader's layout. `useTableQuery` keeps their question: the search, the sort, the column filters and the page, so a register still asks it after the reader opens a record and comes back. Call it right after `useDataTable`; the layout is restored first, then the question.

- **`useTableQuery(table, { storage: "session" })`** keeps it in this tab's session storage, under `ledger.table.<view>.query`; `key` names it when the table has no `view`. It survives opening a record and pressing Back, and ends with the tab.
- **`useTableQuery(table, { search, onSearchChange, prefix })`** keeps it in the URL through the product's own router, so it can be shared and bookmarked. Pass the route's current search (an object, `URLSearchParams` or a query string); in `onSearchChange`, merge the parameters over the route's search and replace the history entry. `undefined` removes a parameter. Back, Forward or a followed link applies its question to a register that is already open.

```tsx
const search = route.useSearch();
useTableQuery(table, {
  search,
  onSearchChange: (params) =>
    navigate({ search: (previous) => ({ ...previous, ...params }), replace: true }),
});
```

The parameters are `q` (the search), `sort` (column ids, `-` before a descending one: `-due,name`), `filters` (one JSON object keyed by column id) and `page` (from 2); `prefix` keeps two tables on one route apart. A slice at the author's default is left out, so a fresh register has a clean URL. What arrives is validated: a malformed parameter is dropped rather than applied in part, and a column the table does not have, cannot sort or cannot filter is ignored. A restored page waits until its rows exist, and lands on the last page when fewer arrive. Refetched data still returns a client-paged table to its first page, as it does without the hook. A router that commits its search later than the reader types gives back each earlier question on the way; the hook knows the questions it wrote and does not apply those echoes, so the search box never loses a letter, while Back, Forward and a followed link still apply theirs.

The helpers underneath are pure and know no router: `tableQueryToSearch(query, { prefix })` and `tableQueryFromSearch(search, { prefix })` convert both ways, `tableQueryToString` gives a query string for a link, `readTableQuery(table)` reads the question as it stands, and `tableQueryParamNames` names the parameters for a route that declares its search.

Do not keep the question of a table in a dialog, a sheet or a picker: it ends with the task, and the table's own state is enough. Do not put the layout in the URL; `view` keeps it per browser.

## Variants

Which table first: a table sorts, filters, pages, chooses, pins, nests or scrolls inside itself, `DataTable`; otherwise `Table`. Then the modes, each one option on the hook:

| The register                       | Option                                         | Role       |
| ---------------------------------- | ---------------------------------------------- | ---------- |
| Sorted, filtered, paged, chosen    | `pageSize`, `selectable`                       | `table`    |
| One record chosen from a list      | `selectable: "single"`                         | `table`    |
| A hierarchy with columns           | `tree`                                         | `treegrid` |
| A hierarchy whose rows open too    | `tree` with `detail` and `detailColumn: false` | `treegrid` |
| A record that opens into more      | `detail`                                       | `table`    |
| Records under headings             | `groupBy`                                      | `table`    |
| Rows held above and below          | `pinRows`                                      | `table`    |
| Rows in the reader's order         | `reorderRows`                                  | `table`    |
| A thousand rows                    | `virtualize` with `maxHeight` or `fill`        | `table`    |
| The register that is the page      | `fill` on the renderer                         | `table`    |
| The server sorts, filters or pages | `manual` with `rowCount`                       | `table`    |
| Cells the reader edits in place    | `editable` on a column                         | `table`    |

A table draws a bounded number of rows. A collection that can hold more than about 200 rows sets `pageSize` (a page of 25 to 100) or `virtualize`, in a dialog, a sheet or a picker as on a page; a collection the server holds in thousands is `manual` with `rowCount`. Every row drawn at once makes each click, each checkbox and each keystroke in the search wait on all of them.

There is no per-column filter row under the header: filters are chips in the toolbar, built from the columns. There is no zebra and no expand-all; see Table. Choosing one record is a radio per row (Opening and choosing). There is no third component for a tree: it is a mode of this one.

## Sizes

Rows are `dimension.row` 40px, and `dimension.row.compact` 36px through the reader's density setting: not a DataTable prop, but the hook's `density` for the first height and the reader's Settings after it; the header `dimension.row.header` 32px. Virtualization uses that density as its initial estimate, then measures each mounted record together with any disclosed detail rows. Widths come from the kind (id 92, or 116 with `preview` to hold the eye, status 120, person 160, date 112, number 96, actions 32) as minimums; the author gives `width` for fixed columns and the rest take the slack: in a responsive table the columns left unsized share it in proportion to their minimums, and only when every column is sized does the identity take it. `resizable` or `reorderable` switches the layout to `fixed`, so a change to one column leaves the others alone; `layout` sets it by hand. `maxHeight` makes the frame scroll inside itself; `fill` takes the rest of the window instead, and wins when both are given.

## Opening and choosing

A row does one of two things, and never both.

- **It opens.** `onRowClick` opens the record, as the row's name link does; the eye opens the preview. A click on a control or a link in the row is that control's, and a click that ends a text selection (a reader copying a code) opens nothing. With Cmd, Ctrl or Shift, or the middle button, the row opens its link in a new tab: `rowHref`, else the first link in the row, so give the name a real link. A focused tree row opens on Enter. The handler gets the click as its second argument.
- **It is chosen.** `selectable: true` is a checkbox per row and a select-all, for acting on several records at once. `selectable: "single"` (or `true` beside `enableMultiRowSelection: false`) is a radio per row and no select-all, for a picker that takes one record: Tab reaches the chosen radio, the arrow keys move the choice from row to row, and a click on the row chooses it when the table opens nothing. `value` and `onValueChange` own the chosen id; the table keeps it unsaid. Choosing never opens the record, and opening never chooses it.

## Modifiers

The hook's options, each one feature:

- **`rowLabel`**: a row's readable name, its code or its title. Its controls say it: "Select REQ-001", "Row actions for REQ-001", "Reorder REQ-001", "Preview REQ-001", "Show details for REQ-001", "Show 3 more fields for REQ-001", and a row that moves is said by it. Unset, the name is the tree's `label`, else the text of the identity column (the one with the lowest `priority`, else the first) or of an `id` column, so a row keyed by a UUID is still named by what the reader sees. The row's id is never the name: a row with no readable text keeps the generic names ("Select row" and the id, "Row actions"). Give `rowLabel` when the identity's text is not the name a reader knows the row by, as when the name cell holds only a link element or the row reads best as its code and title together. **`selectable`**: the checkbox column, or `"single"` for a radio per row (Opening and choosing); a function says which rows can be chosen. **`value`** and **`onValueChange`** own the chosen id of a table that chooses one. **`getRowId`** keys each row, a record's own `id` unsaid, so a refresh never moves a selection or an open row to another record; rows with no unique `id` are keyed by position and the hook says so in the console. **`rowHeader`** names the column whose cell names its row, drawn as `th scope="row"`, so a screen reader says the row's identity with each cell. Unset, it is the identity column, the one a responsive row keeps longest, unless the row has only that one cell; `false` draws every cell as a `td`, for a table whose rows have no single name. **`preview`**, `{ onPreview, activeId }`, puts the eye on each row's first value and marks the open row, as an id column's `preview` and `active` do, but held by the table, so the columns stay at module level and a preview step redraws the two rows it changes, never the column model. Give a preview to the hook rather than to `c.id`, and keep the name a `c.text` rather than declaring it an id to get the eye; `displayedRows(table)` gives the rows the search and filters leave, in order, on every page, for a preview's previous and next, and `showRow(table, id)` turns the table to the page that holds one. **`pageSize`** pages, and **`pageSizes`** are the sizes the reader can choose from in the Pagination (`10, 20, 50, 100` unsaid); the choice persists with `view`. **`label`** names the table. **`manual`** with `rowCount` hands sorting, filtering or pagination to a server.
- **`pinnable`, `hideable`, `resizable`, `reorderable`, `columnMenu`, `layout`, `view`**: the columns the reader owns. The column menu on a header's hover sorts, moves, pins and hides, and is always shown where any pointer is coarse; `DataTable.Columns` in the toolbar shows and hides, and under Wrap text lets the reader wrap a column whose values are cut (text, a name, a person, a custom cell; each item is named "Wrap Owner"), so its values run to several lines on any device; the gear beside it, `DataTable.Settings`, holds the rows' density and Reset view, which ends every wrap too. With `reorderable`, a column's grip drags it within the middle band, and its menu's Move left and Move right move it one place each way, disabled at the band's edges: a way to reorder that needs no drag, for the keyboard, a touch screen or a single pointer. After a move, focus is back on the column's menu, scrolled clear of the pinned columns, and a polite status says where the column stands ("Finding, 3 of 5"). A pinned column and the row actions keep their band. In a right-to-left table the words follow the screen, so Move right moves a column towards the start. With `resizable`, the handle drags, and the column's menu sets the width with one press each, a way that needs no drag (WCAG 2.5.7): **Wider** and **Narrower** step 32px and keep the menu open for another press, stopping at the column's minimum and maximum, and **Reset width** returns to the author's width; the same polite status says the width the column now has ("Finding, 272 pixels wide"). A column's `width` is also its floor, so Narrower stops there. The checkbox, the disclosure, the handle and the detail chevron are always the first columns and always pinned; the row's actions are always the last and always pinned to the end, so the kebab sits at the table's trailing edge however far the columns scroll; a pinned column keeps its hairline while the frame is scrolled, and the frame's scroll padding is the pinned bands, so a heading, a cell or a menu that scrolls into view for focus lands clear of them; a band's heading sticks to the frame's leading edge. Pins give way to a narrow frame: while the pinned columns would take more than 60% of it, they are drawn unpinned from the middle outward, the end band first and then the start column nearest the middle, so the id is the last to go and the middle keeps room to scroll; they return as the frame widens, and the reader's pins, the column menu and the export do not change. The preview eye sits at the end of the row's first value cell: it appears on the row's hover and on focus in the cell, stays on the row whose preview is open, and is always shown where any pointer is coarse; while it shows, the value beside it keeps the eye's 24px clear and ends in an ellipsis before it. An id column with `preview` is 24px wider by default to hold both. The row-actions kebab is always shown where any pointer is coarse. A column's `pin` is the author's default and `hideable: false` keeps it on screen. `view: "risks"` names the table, and the reader's order, widths, visibility, pins and wrapped columns persist in this browser under `ledger.table.risks.view`. `view: { id, version, scope }` also says the author's version, and raising it discards every layout stored under an older one, so a changed set of columns never inherits a stale layout; `scope` (a tenant or a user) keeps two readers in one browser apart. A column added since a layout was stored takes the author's place, visibility and pin, and a column the reader cannot hide always shows. The stored layout applies before the first paint; `useTableQuery` keeps the question (search, sort, filters, page) beside it, in the URL or the session (see Keeping the question).
- **`tree`**: `children` reads a row's parts, `label` names the row for the chevron, `hint` is the muted text after a folded row's first value, `initialExpanded` says which open first; a filter or a search keeps a matching row's ancestors, so a child never shows without its parent. The chevron is a leading column of its own, always first and always pinned, so the disclosure never moves when the reader reorders, hides or pins a column. It is one narrow width at every depth, so opening and closing a row never shifts the columns; the nesting reads as an indent on the row's first value. Set `guides: true` to move the existing disclosure into the first value cell alongside vertical ancestor guides. Each guide starts below its parent and spans only its descendant rows; there are no horizontal branches. The chevron, icon and label then indent together at each depth; the separate leading disclosure column is omitted. Guides are decorative, and the disclosure retains its expand/collapse label and keyboard behavior. **`detail`** opens a row into what it returns, a child table included; its open rows are its own state, so a tree's row opens its parts and its detail apart and neither closes the other. **`initialDetails`** says which details start open (ids, or `true` for every row); a table with no tree also reads `initialState.expanded`. It draws a leading chevron column of its own, which **`detailColumn: false`** leaves out: in a treegrid two chevron columns read as twins, so the row is opened from a cell instead, a `list` column with `opens: "detail"`. **`groupBy`** puts the rows under a band per value, and is the grouping however often it changes; each new grouping opens its groups; pagination is off while it is on, and so is `virtualize`. **`pinRows`** lets `row.pin("top")` and `"bottom"` hold rows under the header or above the footer. **`reorderRows`** puts a handle on every row and tells you which row moved next to which; sorting is off while it is on. The row actions menu gains **Move up** and **Move down**, one press each, disabled at the ends, and a polite status says where the row now stands ("FND-2200, 2 of 6"): the way to reorder that needs no drag. Give a reorderable table an actions column, `c.actions(() => [])` when the rows have no actions of their own, so every row has that menu.
- **`virtualize`**: only the rows in view are drawn; give the renderer a `maxHeight` or `fill` and leave `pageSize` off.
- **A number column's `footer`** totals the rows the filters leave on every page: sum, mean, min, max, count, or your own. In a tree it counts the rows with no parts (`footerRows: "leaves"`), or the top-level rows (`"top"`) where a parent's value already sums its parts, so the total never moves as a row opens.
- **A date column's range filter** reads each value on the day the reader sees: an instant counts on the day it falls on in the LedgerProvider's time zone, and both ends are inclusive, so "up to today" keeps today.
- **`editable`** on a text or status column: `onChange` commits the value at once, `save` settles it (the cell shows saving, saved or the error and rolls back on failure), `validate` blocks a bad value. `onDraftChange(row, draft)`, `onEditingChange(row, editing)` and `onCancel(row)` are the Editable's own reports with the row: a host keeps the rows that hold an unsaved draft (`null` once a draft is saved, put back, discarded or unmounted) and feeds its draft guard from them, never from the cells' DOM events. A status column's `options` are its menu: each value reads as its label in `statuses`, or an option is `{ value, label }`, so the menu searches and announces the words the badge shows and commits the stored value; `emptyLabel` offers a first choice that clears it.

The renderer's: **`toolbar`**, **`state`**, **`empty`**, **`narrowed`**, **`noun`**, **`error`**, **`onRetry`**, **`onRowClick`**, **`rowHref`**, **`loadingRows`**, **`maxHeight`**, **`fill`**, **`responsive`** (on unsaid), **`className`**, and the native attributes and the ref of its root `div`, whose `data-slot` is `data-table` whatever the caller passes. `toRows(table)` and `toCsv(table)` export the rows the filters leave, in the sort chosen, every page, whatever is open or folded, with the columns the reader shows: a tree's rows lead with their level, a group's rows follow without their heading, and a custom column exports what its `text` says. A CSV cell that starts with `=`, `+`, `-`, `@`, a tab or a return, and is not a plain number, is written as text, so a spreadsheet never runs a name as a formula (`keepFormulas` turns that off). `downloadCsv(table, filename)` saves it with the byte order mark a spreadsheet needs to read it as UTF-8. The kit has no router: `useTableQuery` binds the search, sort, filters and page to the URL through the product's router, or to the session (see Keeping the question).

**`fill`** is for the register that is the page: a collection route, a record's register tab, anywhere the table is the one block of content and only a page header, a section heading or a note sits above it. The register takes the rest of the window below its own top edge, the header sticks to the frame, the rows scroll inside it, and the pagination sits at the bottom of the page's inset whether the page has three rows or three thousand; below a header, six rows and the pagination the page scrolls again. Do not fill a table in a dialog, a sheet, a panel, a rail or a card, or one stacked above other content: give those `maxHeight` or let them scroll with the page. The document keeps scrolling for every other page.

Every kind takes `priority` (smaller numbers stay visible longer in responsive mode), `header`, `width` (pixels; also the minimum), `minWidth`, `sortable: false` and `cell(row)` to draw the value its own way while keeping the kind's behaviour. An absent value is `Absent`. Headers are one or two words in sentence case; a number's header ends with its numbers; the id first, the name second, actions last; a status is a Badge and a person a Person. Cells truncate, and a cut value shows whole in the table's one tooltip, on hover, while the keyboard is on the cell or its link, and after a long press on a touch screen (see [Table](?path=/docs/components-table--docs)); a column that must wrap says `wrap: true` and is never the one sorted by eye.

A `list` column's filter lists each item once, counted per row that holds it, and a row matches when it holds any item chosen: a task of two people is found under either, and the facet never lists the pairs the rows hold. Never join an array into a text column to get a facet. `emptyLabel` ("Unassigned", "Not recorded") lists the rows with no items under a value of their own, as the cell's `empty` says them, and `searchable: true` lets the table's search find a row by any of its items. Past thirty items the filter is a text field that matches any item holding the text. See Facets that hold.

A name that needs more than its words, the kind's icon, a mark such as Library, a path under it, takes `icon`, `badge` and `description` on `c.text` or `c.id`, each read from the row; the cell is drawn as [Table.Name](?path=/docs/components-table--docs) around the value, or around what `cell` draws, the record's link. Build it this way, never as an Inline or a Stack in `cell`, so every register cuts the name, keeps the badge and says the second line the same way. A name that opens a preview is a `c.text` with the table's `preview`, not an id column taken for its eye.

```tsx
c.text("name", {
  header: "Element",
  priority: 0,
  minWidth: 220,
  icon: (row) => <Icon label={row.kindLabel}>{iconFor(row.kind)}</Icon>,
  badge: (row) =>
    row.library ? (
      <Badge size="xsmall" variant="secondary">
        Library
      </Badge>
    ) : null,
  description: (row) => row.path,
  cell: (row) => <RecordLink record={row}>{row.name}</RecordLink>,
});
```

A status vocabulary that appears in more than one place is one map, kept beside the product's own status badge and passed to every column that shows it: `c.status("state", { statuses })`, with `statuses` a `StatusMap` of each stored value to `{ label, tone, rank }`. The badge shows the label in the tone. The column sorts by rank, the map's order unless an entry's `rank` says otherwise, and a value the map does not know sorts after the known ones (before them when the sort is descending) in a neutral badge with its value as the words. The search finds a status by its label as well as by its stored value, the filter lists the labels in that order, and export writes the labels. A `tone` function still wins for a row that needs its own, and `sortBy` still wins over the rank. Use `tone` alone for a column whose statuses appear nowhere else.

```tsx
const taskStatuses = {
  overdue: { label: "Overdue", tone: "danger" },
  in_review: { label: "In review", tone: "information" },
  done: { label: "Done", tone: "success" },
} satisfies StatusMap;

c.status("state", { header: "Status", statuses: taskStatuses });
```

## Accessibility

- **The role follows the mode.** A DataTable is a `table`: Tab moves through the interactive elements in reading order and that is enough. A `tree` is a `treegrid`, with the ARIA treegrid keys (see Tree keys). Its rows hold one tab stop: the first visible row, or the row or cell last focused while it remains visible, drawn with the kit's ring inside its edge. Every link and button in the rows is out of the Tab order except those in the cell that holds the stop, so Tab from the stop reaches that cell's controls and then leaves the table, however many rows it has. On a row, Down and Up move between rows, Right opens a closed row or enters its first cell, Left closes an open row or moves to its parent, Home and End reach the first and last row, and Enter opens the row as its name's link, or its click, does. On a cell, Right and Left move along the row and Left from the first cell returns to the row, Down and Up keep the column, Home and End reach the row's ends and Ctrl+Home and Ctrl+End the column's, Enter presses the cell's link, else its first control, and Space its checkbox. A control that takes arrow keys of its own, a menu's button or a field, keeps them. An editable table stays a `table`: Enter accepts a valid text commit and moves down the column; validation failures and IME composition confirmations keep focus in the editor. Tab keeps its meaning and moves across, so the table does not claim a grid, whose arrow keys it does not have; a screen reader's own table keys read it cell by cell. The treegrid role is the ARIA pattern for what a tree adds.
- **Named.** `label` names the table and, through it, its pagination ("Findings pagination"). The header checkbox is "Select all rows on this page". Each row's controls carry its name ("Select REQ-001", "Row actions for REQ-001", "Reorder REQ-001", "Preview REQ-001", "Show details for REQ-001", "Show 3 more fields for REQ-001"): the `rowLabel`, else the tree's label, else the identity column's text, never a raw row id. Only a row with no readable text keeps the generic names ("Select row" and the id, "Row actions", "Preview row", "Show 3 more fields"). The identity column's cell is a `th scope="row"` (`rowHeader` names another, `false` none), so the row's identity is said with every cell; the tree's chevron names its row; the detail row's chevron carries `aria-controls`; a column's grip is "Reorder" and its header ("Reorder Status column"), and is hidden from assistive technology while the column's menu moves it; the resize handle is a vertical `separator` named by its column ("Resize Status"); the Rows per page select is named so. A drag says a row by its label and a column by its header, never by a raw id, and where it would land: "Status moved to position 3 of 8." A table that neither reorders columns nor rows mounts no drag context, so it has no drag instructions or live region of its own.
- **Sorting** reports `aria-sort`; the chevron shows on hover and on focus. Only a drawn header reports it: while the sorted column is folded into More fields no header claims the sort, and `DataTable.Sort`'s name says it ("Sort: Due, Newest first"), in words, not only by its arrow. A new sort is said once it settles, from a header, the Sort menu or a column menu alike, through the page's polite announcer: "Sorted by Due, Newest first". **Filtering** reads on the chips (pressed or expanded, the value in the text) and in the presets' counts; the saved-question menu is named by the question and count it shows. **Paging** keeps focus: at the first or last page Previous or Next is `aria-disabled` and stays a tab stop, so a reader who presses Next to the end is still on Next. **Selection** is the checkbox, never the row's click; one at a time it is a radio, which the row's click chooses in a table that opens nothing. The SelectionBar is a region named "Selection" whose count is said as it changes, from its first: the bar appearing says the count and its verbs ("1 selected. Actions: Reassign and Clear."); Escape inside the bar clears it and goes no further, so an enclosing panel or dialog stays open; after Clear focus is on the select-all. **Results** are said (see States), and so is a load that outlasts half a second. **A partial table** says its size: while a virtual window or a server page draws only some rows, the table carries `aria-rowcount` and each drawn row its `aria-rowindex`.
- **Loading never removes the header** or changes the height of what is already there, so nothing jumps under a screen reader's cursor. A failed load's error, the filtered empty and a server page left empty sit under the header; a refresh keeps the rows it has, under `aria-busy`, and a refresh that fails keeps them too, with the error above the table. With no records at all there is no table: the region is the Empty and its action, so a screen reader meets the message first and the way forward second, not eight empty column headers.
- **A thousand rows may be chosen one at a time**: a row is memoized on what it shows, so one checkbox redraws one row and a preview step the two rows it changes. The leading columns, the fitted layout and the handlers the rows get are stable, and `onRowClick` is read through a ref, so an inline handler costs nothing; new `data` or new column definitions redraw every row, so keep both stable (module level or `useMemo`). A cell, a `detail` and a tree's `hint` draw from their row; state they read from outside it reaches the rows through new column definitions, so put it in the `useMemo`'s dependencies. A responsive table redraws when its frame folds or returns a column or a pin gives way, never on the pixels between: the columns that take the slack are sized through custom properties outside React, so a panel that opens or a splitter that drags costs the rows no render. The row actions menu and the id's glance are one menu and one card per table, which each row's trigger opens with its row, so a closed menu costs a row nothing. The Render budget story counts the rows each change redraws.
- **The name keeps its focus ring.** A link in a cell that is cut cuts itself at the cell's width, ends in its own ellipsis and draws its ring inside its box, so the clip that cuts the value never cuts the ring; the id's glance is a hover card with no tab stop of its own, and a name link inside the id opens it on focus.
- **Reordering and resizing take the keyboard from the column's menu.** A column's grip and its resize handle are for the pointer and are no tab stops, so a header costs the keyboard two stops, its sort and its menu. A table with `columnMenu: false` has no menu to do this, so there the grip takes Space and the arrow keys and the handle takes the arrow keys (see Columns without a menu). A grip from `useColumnDrag` in a header drawn by hand keeps its keys too; pass `pointerOnly` when that header's menu moves the column. The menu moves the column one place with Move left or Move right, one press each, which is also the way on a touch screen, and a status says where it went; a resizable column's menu sets its width by single presses (Wider, Narrower, Reset width), with the width said in the same status. A row's handle takes Space and the arrow keys, and its menu's Move up and Move down move it one place. A header or a row slides aside on the motion tokens while another is dragged past it, and under reduced motion it moves at once, with no slide after the drop and no smooth scrolling.

## Responsive containers

A DataTable fits its container unless it says `responsive={false}`. Set `priority: 0` and a readable minimum width on the primary identity; the renderer retains it and row actions, then fits other columns by priority, in order: the first column that does not fit folds, and every column after it, so a lower-priority column never outlasts a higher one. Once everything fits, the author's widths hold and the columns left unsized share the spare width in proportion to their minimums; with every column sized, the identity takes it. An id column is sized unless it has a `minWidth` and no `width`: a code keeps its width, and a name given only a minimum grows with the others. Lower-priority fields appear in each row's More fields disclosure with their labels and original cell renderers, as one [KeyValue.Group](?path=/docs/components-keyvalue--docs): the labels share one column, and stack over their values where the row is too narrow for both, as in a narrow panel. The disclosure is a count, never a chevron, since a chevron opens a tree's branch or a group: "+3", the 20px row control, named by what it does, how many and whose ("Show 3 more fields for REQ-001", "Hide 3 more fields for REQ-001" while open), with `aria-expanded` and `aria-controls` on the row it opens. Its focus ring is drawn inside its edge so its narrow cell never clips it. A reader-hidden column stays hidden. Resizing does not change the table's column-visibility state, view persistence, selection, sort, filters or export. The observer follows the container, including a neighbouring panel, rather than a viewport breakpoint.

Responsive mode uses fixed column geometry and keeps virtualization active. Expanded fields contribute their measured height to the same virtual record; scrolling away and back preserves its disclosure state. Column or container changes invalidate cached heights, including records outside the rendered window. Paging remains an independent choice. `c.id` honours an explicit `minWidth` when no width is supplied.

`responsive={false}` is for a wide comparison, whose reader reads across every column (pinned columns and a frame that scrolls sideways), and for a table whose cells hold drafts of their own: a field that moves between its cell and the More fields disclosure remounts its renderer, so a local inline editor's uncommitted draft is not kept through that move. Record lists whose drafts belong to a form outside the cells stay responsive.

In a responsive table Move left and Move right step only among the columns the row draws, so every move shows, and the last one drawn cannot move past a folded one. Columns without a `priority` rank by their place, so a move can change which of them fit: when the moved column folds into More fields, focus stays in the header row, on the column it passed, and the status says where it went.

On a phone nothing waits for a hover: the eye and the row-actions kebab are always shown, the value beside the eye ends in an ellipsis before it, and every control smaller than 24px takes a 24px hit area wherever a pointer is coarse. A header's column menu and grip sit beside the heading; beside a menu that sorts, the heading drops its up-down hint. A table that scrolls sideways draws the column that much wider there (24px for one, 46px for both), so the heading keeps the room it has at rest on a desktop. A responsive table keeps the author's widths, so a menu never folds a column into More fields on a phone: the heading gives the controls its room, ends in an ellipsis and shows whole on hover and while its sort button has focus. A table with `responsive={false}` redraws on a resize of its frame only when a pin gives way or returns.
