# RecordBrowser

Find, compare and select related records without leaving the current record. Use this for evidence, assessment objectives and other collections where a compact picker cannot show enough information to make a decision.

<Canvas of={Stories.BrowseAndLink} />

## Anatomy

A Base UI Dialog occupies 90% of the viewport. Its header names the relationship task; the body is a DialogBody holding the results and the preview side by side. The optional `context` opens the results and scrolls with them; the Toolbar (search, column filters, Columns and the permanent `actions`) sits above a selectable, responsive DataTable. The results take the height the dialog leaves them: the toolbar and the pagination stay in view and the rows scroll under the table's sticky header. The eye on each row's naming cell opens the preview pane, which holds a readable code, previous and next, the way back to the results, the record's name as its heading, the complete record, and a Select checkbox. The footer keeps the selection count, Cancel and the linking action visible.

The caller supplies eligible records, columns, the record's name (`recordTitle` and, when that is markup or the ids are database keys, `recordLabel`), preview content and the linking callback. The pattern owns the temporary search, filters, sort, pagination, selection and preview state. Business rules and record content stay in the application.

## Names, never keys

A record's `id` keys its row and nothing else: the reader never sees it or hears it. `recordLabel` names the row's checkbox and eye ("Select Firewall ruleset export"), the preview's Select checkbox and what previous and next say; it defaults to `recordTitle` when that returns a string. `recordCode` is the readable identifier shown over the preview's name, such as EV-0412. `previewColumn` names the column that names the record: it leads the row and its cell carries the eye. Give that column `priority: 0` and a readable width (about 180 to 220px), so a narrow browser keeps it in the row and moves the other fields into each row's More fields.

## Behavior

Previewing never selects or links a record. Checkboxes select; only the footer confirms. Selection survives search, filtering, pagination and preview navigation. Clear selection resets it. By default, closing the dialog discards the selection; each opening starts a new session, and the last one stays drawn through the dialog's exit. Callers can retain selection across a related creation workflow with `selectedIds` and `onSelectionChange`. Link failures show a danger Alert and preserve selection for retry.

While confirmation is pending, Cancel, Escape, the close control and outside clicks cannot dismiss the browser: the Dialog's `pending` lock marks the browser `aria-busy` and Close and Cancel `aria-disabled`. The results are inert and `aria-busy`, and the preview's Select checkbox and Clear selection wait, so the records being linked are the ones on screen. Confirmation is serialized. If the application closes the browser itself, a late completion from that session cannot close or update a subsequently opened session.

## Nothing to link, loading and failure

`state` says where the records are. `loading` draws skeleton rows under the toolbar; `refreshing` keeps the rows while new ones arrive; `error` shows the caller's `error` in place of the rows. With no eligible records at all, the browser says so with `empty` in place of the table: a title, one line on why and what makes a record, the caller's `actions` as its step (or `empty.action`), and an optional quieter `secondary`. The context stays above it. A search or a filter that matches nothing is not this: it is the table's own filtered state, with Clear filters.

## Preview navigation

Previous and next walk every row the search and filters leave, in the table's order, across its pages: a step past the last row of a page turns the table to the next one. A polite status names the record and its place ("Verification artifact 21, 21 of 24 records"). At either end the control keeps focus and says it is unavailable. When the previewed record is outside the filtered results, both are unavailable, the status says so, and its selection remains available. Closing the preview returns focus to the eye of the record being read.

## Narrow and short windows

Below the split container size (`dimension.container.split`, 50rem) the preview replaces the results while keeping the table mounted. The way back leads the preview's header as a chevron, Back to results, away from the dialog's Close; beside the results it is the X at the end of that header.

<Canvas of={Stories.Phone} />

In a window under 30rem tall (a landscape phone, 400% zoom) the whole dialog scrolls as one, with the footer held at the bottom: the title and Close come back into view when it is scrolled up, the results are not squeezed behind fixed rows, and a control that takes focus scrolls clear of the footer. The preview scrolls with it.

The table fits its pane: the fields that do not fit beside an open preview move into each row's More fields instead of a sideways scroll.

## Accessibility

The dialog uses the existing [shadcn Base UI composition](https://ui.shadcn.com/docs/components/base/dialog) and [Base UI focus management](https://base-ui.com/react/components/dialog). Opening a preview focuses its heading; closing it restores the eye of the record being read. Escape closes the internal preview first, then the dialog. Nested filter menus and a focused control's tooltip consume their own Escape. Closing the dialog returns focus to its opener. The preview is a region named by the record; its body is a tab stop only while it overflows with nothing focusable in it.

The words are the locale's: Search records, Back to results, Previous record, Next record, the position, the count, Clear selection, Cancel and the failure come from the LedgerProvider's messages (`recordBrowser…`, `recordPositionNamed`, `selectedCount`).

## Props

<ArgTypes of={RecordBrowser} />

`records` contains eligible records with stable IDs. `columns` uses `defineColumns`; `filters` names filterable columns. `onConfirm` receives all selected records, including selections hidden by filters or pagination; it may return a promise. `confirmLabel` names the action. `searchPlaceholder` names what is searched. `context` is optional relationship context; `actions` holds permanent controls such as Create evidence artifact.

`selectedIds` and `onSelectionChange` optionally let the caller own selection. This supports a sequential create flow that closes the browser temporarily and returns with the earlier selections intact. The caller decides when to clear its controlled selection. The default behavior is unchanged when these props are omitted.
