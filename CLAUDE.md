# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Program Assurance: a TanStack Start / React 19 app over a local Supabase stack (Postgres, Auth, private Storage). It is an npm workspace with two halves:

- **The app** (`src/`): the Equinox prototype at `/` for daily work, plus a schema inspector at `/schema` and `/records/:collection` over the same rows. The prototype is the design system's first consumer and its test vehicle: when a screen breaks, the kit is what gets fixed.
- **The design system** (`packages/design-system`, published name `@ledger/design-system`, "Ledger"): tokens, primitives, components, layout, patterns and colour mode. Its Storybook is the contract. Read `packages/design-system/AGENTS.md` before touching it: it points at `README.md`, `docs/guides/component-library.md`, the Storybook's Guidance/Agents page and the checks. `packages/design-system/llms.txt` is the Storybook as one generated file for when it is not running.

The project is connected to Lovable. Never force-push, rebase, amend or squash commits that are already pushed; keep the connected branch in a working state.

## Screens

Every screen follows the product pattern contract in `docs/guides/product-patterns.md`: which Ledger part this application uses for each shape (register, preview, record, form, states, titles), the closed exceptions, the file to copy and what checks it. Read it before creating or changing a screen; do not infer a shape from a neighbouring screen. It is imported below so it is always in context.

## Architecture

### App layer (`src/`)

- **Routing**: TanStack Router file routes in `src/routes/` (`routeTree.gen.ts` is generated; do not edit). `__root.tsx` composes `QueryClientProvider → ModeProvider → WorkspaceProvider → AppLayout`. Vite config comes from `@lovable.dev/vite-tanstack-config`, which already includes the TanStack, React, Tailwind, tsconfig-paths and nitro plugins; do not add them again. `src/server.ts` wraps the Start server entry to turn swallowed h3 500s into an HTML error page.
- **Dependency direction**: domain code never imports the UI. `src/lib` holds data access, commands, rules and query hooks; `src/components` and `src/routes` render them. The kit never imports the app, and `src/lib` never imports the kit, `src/components` or `src/routes` (lint: `no-restricted-imports` on `src/lib`, with no exception: the workspace context and `useWorkspace` live in `src/lib/workspace-context.ts`, and `WorkspaceProvider` in `src/components/app/workspace` provides it). A domain concept that has one visual representation (a status, a record link, an identifier) gets one component that binds the domain vocabulary to a kit part, and every screen uses it.
- **Data**: `src/lib/database.ts` holds the single browser-side Supabase client (throws on the server) and `loadWorkspace`, which calls the `ensure_personal_tenant` RPC; the record schema (`app_schema`) loads on demand through `useSchemaCatalog`, `useCollection` and `useColumnChoices` in `src/lib/collections.ts`. `src/lib/models.ts` wraps TanStack Query hooks (`useRows`, mutations) over the generated `Database` types, with a few hand-typed projections for views. Reads are scoped on the server: ids as a list filter (`in`), a dotted key to filter through a reference (`programRequirementScope` in `src/lib/requirement-reads.ts`, `useSelectedControls` in `src/lib/control-reads.ts`), and `columns` for the fields a screen uses; a whole tenant-wide table is for small collections only. A register that can hold thousands of rows reads one page at a time: `serverRead` and `useServerRows` in `src/lib/server-table.ts` turn the table's question (search, sort, filters, page) and its fixed scope into one PostgREST request with `range`, `order`, filters, an `ilike` search and `count: "exact"`, and `useServerCollection` in `src/components/prototype/collection-question.ts` hands the table manual mode and the count. A read names in `models` the tables its view derives from, so a write to one marks the register's pages stale; a read whose preview edits the record names every column the record's form edits, since the generic form saves a column it was not given as empty; and a sort the reader chooses places empty values last ascending and first descending, as a client table does. `useServerPosition` counts where a record stands in a register's result, for a preview whose record left its page. Domain commands (program wizard, task/evidence create, requirement edits, library reuse, SSP assembly, system tree) are plain modules in `src/lib/*.ts`, each with a sibling `*.test.ts` that mocks the client. Most multi-table writes go through Postgres functions in the migrations (`create_program_wizard`, `create_program_system`, `author_tailored_profile`, `apply_library_source`, …), not through client-side sequences.
- **Tenancy and concurrency**: every tenant-owned table carries `tenant_id`; RLS keys off membership. Updates send `revision + 1` filtered by the previous revision, so stale writes fail instead of overwriting. Published reference/evidence/assessment revisions are immutable.
- **Runtime data boundary**: `scripts/tests/runtime-data-boundary.test.mjs` fails if anything under `src/` references the legacy POC, snapshot tables, demo fallbacks or `Math.random`. The app never invents example records; empty workspaces stay empty. Demo data is an explicit, provenance-tracked seed (`npm run seed:demo -- --tenant … --account … --apply`, then `seed:demo-baseline` and `seed:demo-showcase` with the same arguments; the showcase is an authored scenario for the screens the archive left empty, and `seed:demo-products` an authored business line, product and two customer programs, `docs/demo-seed-mapping.md`); reference publications (NIST OSCAL catalog/baselines, DISA CCI, the NIST SP 800-160 transcriptions) come from pinned files under `supabase/reference/` via `seed:reference`.
- **Screens**: `src/components/prototype/README.md` maps every feature composition and names the reference file for each shape. `src/components/app/` holds the product shell (`shell.tsx` composes the kit's Shell parts), workspace/sign-in, the program wizard, pickers and the record browser. `src/components/prototype/` holds the feature compositions (program record, requirements, system assurance, evidence, findings, work table, libraries, products). `src/components/ui`, `src/components/reui` and `src/components/examples` are look-only shadcn/reui reference installs, lint-ignored and excluded from product imports.

### Design system (`packages/design-system`)

- Layers, bottom up: `tokens/` (source of truth, ledger-css-v1 JSON) → `src/generated/` (committed Style Dictionary output: `tokens.css`, `theme.css`, `utilities.css`, `tokens.ts`, `utilities.json`) → `src/primitives/` (Box, Stack, Inline, Flex, Grid, Bleed, Text, Heading; token-typed props, no margins) → `src/components/` (Base UI–backed controls and display parts) → `src/layout/` (Shell regions, PageHeader, Section, PageSkeleton, StickyRail) → `src/patterns/` (DataTable, pickers, Composer, Editable, Inspector, Chart, Forms) → `src/mode/`. Components and primitives never import patterns or layout. The package never imports application source.
- Product code imports only the package root (`@ledger/design-system`) and never a file inside it; the package's named `@ledger/source` export condition maps to `src/index.ts`, and every other condition (the generic `development` included) to `dist/`. The app's `tsconfig.json` sets `customConditions: ["@ledger/source"]` and `vite.config.ts` adds the condition to the dev server's environments, so the typecheck and `npm run dev` read the kit's source and a kit edit hot-reloads; `vite build` bundles `dist/`, which needs a fresh package build to carry a newly added export.
- Styling is tokens only. The package ships an ESLint plugin (`@ledger/design-system/eslint`) with a `package` preset for itself and a `recommended` preset that the root config applies to product files (`src/routes`, `src/components/app`, `src/components/prototype`, `src/lib`, `src/router.tsx`). Its rules reject arbitrary values, non-token classes, margins, `dark:` variants, deprecated tokens/names, `<colgroup>`, local copies of kit parts (`ledger/no-kit-shadow`, with no exemption: the app shell composes the kit's Shell parts), a comment that turns a ledger rule off (`ledger/no-inline-config`), a `className` on a kit part that the lint cannot read (`ledger/readable-classes`) or that changes what the part sets itself (`ledger/no-restyle`), a literal colour in an SVG or chart prop (`ledger/no-raw-colour`), a raw `h1`–`h6` with type classes where a `Heading` belongs (`ledger/use-heading`, product files only) and a few more; see the table on the Storybook's Guidance/Lint rules page (`packages/design-system/src/stories/docs/Lint.mdx`). A product config adds nothing about the kit.
- Every exported catalog part needs a story that renders it in `<Family>.stories.tsx` and one `<Family>.mdx` page whose first line under the title is its status (`**Status: Stable.**`, `Experimental` or `Deprecated`; `test/family-status.test.mjs`); `scripts/ds-check.mjs` enforces the story and the page and `scripts/ds-check.allow` may only shrink. Renames ship with an `@deprecated` alias for one version and a `ledger/no-deprecated-name` fixer. Optional props are spelled `?: T | undefined` (`exactOptionalPropertyTypes` is on in both tsconfigs).
- Contribution checklist and versioning rules: "Adding to the kit" in `docs/guides/component-library.md`; changes go in `packages/design-system/CHANGELOG.md`.

### Database (`supabase/`)

Migrations in `supabase/migrations/` (Postgres 17, `public` schema only, Realtime/Edge/pooler disabled). Layers: tenancy → reference schema (shared, read-only publications) → assurance schema (programs, systems, requirements, implementation, assessments, findings, risks, POA&M) → workflow schema (tasks, reviews, activity, packages) → later feature migrations (program wizard, canonical systems, library reuse, program setup v2, products, server-paged registers, control overlays, the assurance chain reads, the NIST SP 800-160 frameworks and the reads and commands over them). A server-paged register's derived columns come from a view `<register>_rows` with `security_invoker = true`, `grant select … to authenticated` and `revoke all … from public, anon`: `catalog_control_rows` and `cci_item_rows` (migration `20261003135644_server_paged_reference_registers`), and `program_requirement_rows`, `risk_rows`, `operational_issue_rows`, `assessment_finding_rows`, `evidence_artifact_rows` and `task_rows` (migration `20261003151023_server_paged_registers`; `task_rows` gives the people assigned as one text column, `assignee_names`, for the search, from `20261003195635_task_rows_assignee_names`), and the Findings & assets page's `observation_rows` and `inventory_item_rows` (migration `20261113211630_server_paged_findings_registers`). The Review queue reads `review_queue_rows` (migration `20261113215841_review_queue`, `src/components/prototype/review-queue.tsx`): one row a record waiting on a reviewer across the workspace, by the record's own id (an evidence artifact's latest version whose latest review is pending, a draft assessment results revision or product assessment that holds determinations, a lifecycle gate in review, a package's latest published version submitted with no decision, an open review discussion), with its `kind` and `kind_rank`, its program, who it waits on, who asked and since when. Assessment results to publish leave it through `publish_assessment_results` (migration `20261114025500_publish_assessment_results`, `src/lib/assessment-results.ts`), the queue preview's primary, an item of the campaign record's Actions menu and the primary of a draft's preview in the campaign's Assessment results (`src/components/prototype/campaign-results.tsx`, which lists the campaign's results revisions newest first): it publishes a draft results revision at the revision the reader saw and holding the findings the reader was told, records who published it (`published_by_party_id`), refuses results already published, changed since, holding no finding or not in the workspace, and answers a request id once (private receipts, `assessment_results_requests`); since migration `20261114072513_publication_activity_event` it also writes one activity event naming the publisher's party, the program and the campaign (an event may name a record's program beside the record, which a trigger keeps the record's own), which the Portfolio's Recent activity and the program's Activity read ("… published assessment results of <campaign>", linked to the campaign). A direct update of the revision's state still publishes, as the seeds and tests do, and writes no event; results published before that migration have none. The Portfolio's Recently updated programs reads `program_activity` (migration `20261113211631_program_activity`): one row a program with the latest moment anything in it was recorded or changed (its activity events, its published assessment results, a change to its requirements, operational issues, risks and their assessments, tasks and evidence artifacts), else its own last edit. A status a register sorts by has a `_rank` column in the product vocabulary's order, which `src/lib/server-table.test.ts` checks against `src/lib/status.ts`. Every view needs a noun in `src/lib/product-records.ts`, since the product-records test enumerates every view. A read over several hops of the assurance chain is a `security invoker` function that answers in one request (migration `20261111090000_assurance_trace`): `assurance_trace` for the chain around one record, through `src/lib/assurance-trace.ts` (seven stages since migration `20261113211500_assurance_trace_findings`: controls, requirements, evidence, assessment findings, operational issues, risks, remediation; a finding judges the control of its part, cites evidence, became the issue resting on an observation it rests on and raised the risks it names, a walk reaches findings of published results only, and a remediation item also answers the risks its latest commitment cites), and `program_posture` and `program_posture_cell` for a program's elements by control family, through `src/lib/program-posture.ts`; a write to a model they read marks their answers stale (`useStaleOnWrite` in `src/lib/server-table.ts`). An operational issue reaches a requirement through the evidence it cites and through the requirements it names, `issue_requirements` (migration `20261113200615_operational_issue_requirements`, `src/lib/issue-requirements.ts`): the trace walks it both ways and the posture, by family and by technique, places the issue on what it names, each record once. NIST SP 800-160 is reference data beside the catalog (migration `20261111130000_reference_frameworks`): `frameworks`, `framework_revisions`, `framework_items`, `framework_item_links` and `framework_control_links`, with the read views `framework_rows`, `framework_item_rows`, `framework_item_link_rows` and `framework_control_link_rows`, hold the cyber resiliency constructs with Table E-1 (`nist-sp800-160v2r1-cref`), Appendix F's ATT&CK techniques (`nist-sp800-160v2r1-attack`), Appendix G's ATT&CK for ICS techniques (`nist-sp800-160v2r1-attack-ics`, a framework of its own, since ATT&CK for ICS numbers its own tactics, techniques and mitigations; its rows name Table F-1's effects by title, and a risk may name a technique of either appendix) and the system life cycle processes (`nist-sp800-160v1r1-processes`). NIST publishes them only as PDFs, so each is a pinned transcription under `supabase/reference/`, re-derived by a script in `scripts/reference-transcribe/` (`docs/reference-seeding.md`). The app reads them through `src/lib/frameworks.ts`, a framework by its code and an item by its `code`, since a publication read again is a new revision whose items have new ids. A goal's, an objective's, a technique's and an approach's guidance (Tables 2, 3 and D-4) is on the item: `prose` is its definition, `props.discussion` its Discussion and, for an approach, `props.informal_description` and `props.examples` (the printed bullets, in order); `itemGuidance` reads the four. Table D-5's architectural layers are items (`architectural-layer`) an approach links to (`used-at`), read by `useApproachLayers`. On top of them: `program_resiliency_choice` (what a program chose for SA-24, `src/lib/resiliency-choice.ts`), `program_resiliency_posture` and `program_resiliency_posture_cell` (the Posture by technique, `src/lib/program-posture.ts`), `add_gate_security_outcomes` with `gate_criteria.outcome_item_id` and the view `gate_criterion_rows` (`src/lib/gate-criteria.ts`), and `risk_attack_techniques` with the read `risk_threats` (`src/lib/risk-threats.ts`). The program's Cyber resiliency view derives its ladder from the same rows and the baseline stack on the client (`src/lib/resiliency-ladder.ts`). A program's values for a control's parameters, which the control's text prints on the program's record in place of the catalog's placeholders, are the read `program_control_parameters` (migration `20261113213853_program_control_parameters`, `src/lib/control-parameters.ts`): for every stack that selects the control, each parameter's effective values, resolved as `author_tailored_profile` resolves them, and the layer or the catalog they come from. One status for each control of a program's control baseline (no requirement, no evidence, not assessed, or a determination: an assessor's latest published one, else the worst a product assessment made where every product variant of the program inherits the control, which the control's `determined_by` and `product_assessments` say) is the read `program_control_status` (migrations `20261111150000_program_control_status` and `20261113195606_control_status_inherits_product`, `src/lib/control-status.ts`), which the program's Overview and its Control status view draw. A requirement maps a whole control or some of its assessment objectives, one mapping an objective (`requirement_control_links.control_part_id`, which the guard takes as a statement of the control's text or one of its objectives, never another control's), and the control climbs by its objectives (migration `20261114030116_objective_level_derivation`): a control counts its leaf objectives and each heading that prints a sentence of its own besides the objectives under it (migration `20261114051136_objective_headings_count`, the rule `objective_prints_own_sentence`: nine headings, so 2,785 objectives over 1,014 controls; 26 for AC-2), a mapping covers the objective it names and every one under it, and one that names no part or a statement covers them all, so the control stays no requirement until every objective is covered and no evidence until each is covered by a requirement that cites evidence; every system counts (migration `20261114072913_every_system_counts`): an objective, or a control with none, is covered only once covered on every authorization boundary of the program whose control baseline selects the control (`system_effective_baselines`), a mapping on an element counting on its boundary and one that names no system on every boundary, and a control no boundary selects is covered by any mapping; each control answers `objectives`, `objectives_mapped` and `objectives_evidenced`, and `program_control_objectives` answers one control's objectives in reading order with their labels, text and the systems each is covered on, the systems that select the control with what each covers and how many requirements are allocated there, and the requirements that cover it with whether each owes evidence (`src/lib/control-objectives.ts`; Map a requirement filters by `program_requirement_rows.allocated_boundaries`), both from the internal `program_control_objective_cover`, which `risk_threats` (each countering control's `objectives` and `objectives_mapped`) and `control_objective_counts` (one control in each program named, for the catalog control's table) count from too (migration `20261114051138_objective_counts_on_screens`); what a reader does next about a control at each status, and which gap of a trace carries a fix, is derived in `src/lib/next-steps.ts`. Its counting is the internal `program_control_status_lines`, and the variant delta it reads is `variant_control_delta_answer`, neither of which asks who calls, so the daily posture snapshot counts as the read does (migration `20261113223837_posture_snapshots`): `program_posture_snapshots` keeps one row a program and UTC day of the six status counts and their total, written only by `take_program_posture_snapshots` (an upsert, every program at 23:55 UTC through the pg_cron job `program-posture-snapshots`, removed with `select cron.unschedule('program-posture-snapshots')`) and by `ensure_program_posture_snapshots`, which takes today's of a program that has none before a trend reads `program_posture_trend` (`src/lib/posture-trend.ts`), so change the counting in the internal reads, never in the public ones. A program's overlays change after creation through `set_program_baseline_overlays` (migration `20261113204617_program_baseline_overlays`, `src/lib/program-overlays.ts`): the tailoring stays last, the systems that adopted the old top move to the new one, and every SSP revision keeps the baseline it was pinned to; `delete_control_overlay` deletes a draft overlay no stack applies. An overlay also sets parameter values, `control_overlay_parameters` written through `set_control_overlay_parameters` (migration `20261113220543_overlay_parameters`, `src/lib/control-overlays.ts`): applied, a value for a control the layer selects becomes the layer's own `profile_parameter_settings`, so `program_control_parameters` and `program_resiliency_choice` read it as the nearest layer that sets the parameter. A published overlay changes through its next version, `create_control_overlay_version` (migration `20261113223331_overlay_versions`): each version is an overlay row chained by `previous_overlay_id` and numbered `version` under one code, a program keeps the version it applied, and `set_program_baseline_overlays` takes a newer one in its place. A stack may start from two reference baselines combined (migration `20261113224637_combined_baselines`): the second is the layer right above the first, authored by `combine_reference_baselines` with what it adds and named in `profile_baseline_combinations`, so every read of the stack reads their union, and `create_program_wizard` takes it as `combinedResolutionId`. Assign owner, the verb a register offers while rows are chosen, is one command, `assign_record_owner` (migration `20261112090000_assign_record_owner`, `src/lib/owner-assign.ts`), for risks, operational issues, evidence artifacts, remediation items and requirements: every chosen record takes the owner or none does. A requirement's owner is on its current details (`requirement_revisions`), which the command writes at their next revision, so `audit_requirement_edit` records each change in the requirement's history as an edit of the owner is recorded, and a requirement with no details stops the request (migration `20261113223727_assign_requirement_owner`). A control's next step for evidence no assessor has determined puts it into an assessment, from the control's own record (migration `20261113222212_control_assessment_commands`, `src/lib/control-assessment.ts`): `add_controls_to_assessment_plan` adds the chosen controls to a campaign's draft plan at the plan revision the reader saw, and `plan_control_assessment` plans a new campaign whose first plan, a draft on a published SSP of the program, holds them; each answers a request id once (private receipts, `assessment_plan_requests`), and a control the plan's SSP does not select is refused. Both write a control as the assessment objectives it counts, one plan objective each, titled by its label and text and aimed at its part, and a control that counts none as one objective aimed at its statement (migration `20261114073741_plan_by_objective`, through the internal `add_control_objectives`, whose parts are `control_assessment_parts`): a plan holds a control once it holds every objective the control counts, or its statement, as every plan written before that migration does, an objective aimed at a heading holds those under it, and a plan that holds some takes only the rest; `plan_control_holdings` answers how many objectives a control counts and what each plan named holds of it, which the control's next step and Add to assessment campaign read. Map a requirement, the step before it, writes the requirement's own control mappings, many in one insert (`mapRequirementsToControl` in `src/lib/requirement-links.ts`). A product is judged once and read by configuration (migration `20261112130000_product_assurance`, `docs/products.md`): `business_lines` over products and programs, `product_assessments` with `product_determinations` an element and control, what a program changed in an inherited element through `declare_product_element_change`, the reads `product_control_status` and `variant_control_delta`, `plan_delta_assessment`, which plans a campaign over the controls a variant owes, `variant_version_changes` and `take_product_version`, which review and take a newer product version into a variant, and `product_assessment_sheet` and `record_product_determinations`, behind the product assessment's record (`src/lib/product-assessment.ts`). A customer's requirements document (migration `20261112140000_customer_requirements`): `requirement_sources`, a requirement's `source_id` and `source_reference`, `requirement_compliance`, the command `import_customer_requirements` and the read `requirement_source_compliance`. Both are read through `src/lib/product-assurance.ts` and drawn by the Business lines register and record, the product's Assessment tab and its product assessment record, the program's Product delta and Compliance matrix views and the trays on both Overviews (`docs/products.md`, Screens); a delta assessment's campaign names its variant in `assessment_campaigns.variant_system_id`, and a requirement's answer is written through `src/lib/requirement-compliance.ts`. ERD and constraints: `docs/schema-erd.md`, `docs/assurance-schema.md`, `docs/workflow-schema.md`. After adding a migration: `npm run local:start` applies it, then `npm run models:generate`.

## Conventions worth knowing

- TypeScript is strict with `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` (so `import.meta.env["VITE_X"]`), `exactOptionalPropertyTypes`, `noImplicitReturns`.
- Prettier: 100 columns, double quotes, trailing commas. It runs as its own step, `npm run format:check`, not inside ESLint.
- Do not use the Next.js `server-only` package; name server modules `*.server.ts`.
- Procedures are skills, rules are here: `/ledger-add-part` walks the kit contribution checklist and `/verify-screen` the screen verification checklist; both point at the guides rather than restating them.
- Feature docs live in `docs/` (`program-wizard.md`, `control-baseline.md`, `products.md`, `system-assurance-workflow.md`, `requirement-workspace.md`, `reference-seeding.md`, `demo-seed-mapping.md`). `docs/next.md` is the living list of what is open and which decisions are waiting, and `docs/next-archive.md` is what landed: when a batch lands, add its entry to the archive and leave in `docs/next.md` only what it left open. Design audits and plans are under `docs/guides/`.
- The design-system package's Storybook (port 6007) is the only Storybook; app compositions are verified in the running app, not in stories.
