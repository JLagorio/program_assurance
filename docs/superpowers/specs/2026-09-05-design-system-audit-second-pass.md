# Ledger design-system audit: second pass and remediation plan

Date: 2026-09-05. Scope: Ledger, its consuming application, the first-pass audit, and the supplied professional reference systems. This is an audit and proposed plan; it does not implement the recommendations.

**The largest deficiencies are unreliable behavior, incomplete product interactions, and insufficient evidence behind accessibility and distribution promises. Fix those before undertaking a system-wide prop rename.** The first pass identifies useful vocabulary problems, but several of its claims are already stale, and some of its proposed rules would add migration cost without improving usability.

Ledger already has valuable foundations: semantic tokens, generated outputs, shared component recipes, substantial documentation, reusable layout primitives, Radix-based controls, both-mode contrast checks, and a working automated accessibility test setup. ## Findings that should determine the implementation order

Priority definitions: **P1** = release, data correctness, essential interaction, or accessibility contract failure; **P2** = systemic usability/integration gap; **P3** = maintainability or optional standardization. “Confirmed” means the stated source or command evidence was verified; it does not imply a manual browser reproduction.

### Release and data correctness

**DS-01 · P1 · Confirmed by build: the package cannot currently complete its release build.** `npm run build` fails with TS4023 at `packages/design-system/src/components/toaster.tsx:74`: the inferred `toast` export references Sonner's unnameable `PromiseIExtendedResult`. `tsc --noEmit` passes because declaration emission exercises a different contract. The app build never reaches Vite. Give the facade an explicit, emit-safe public type and validate the promise overloads rather than casting away the error. **Acceptance:** root production build and package declaration generation pass, and consumer type fixtures exercise `toast.promise` success/error result variants.

**DS-02 · P1 for externalized Node SSR · Confirmed import failure: emitted ESM is not directly Node-resolvable.** `build/dist.mjs:15` invokes TypeScript; `tsconfig.build.json` inherits bundler resolution. Emitted `dist/index.js` contains extensionless relative imports. Direct Node import of these emitted files fails at `dist/generated/tokens`; this was not a successfully packed release, because DS-01 prevents that. A bundler can resolve these imports, so this is not proof all SSR integrations fail. State the supported runtime contract; generate Node-compatible ESM or explicitly require documented bundling. **Acceptance:** a separate installed consumer builds and SSR-renders using the advertised configuration, outside workspace aliases and the `development` export condition.

**DS-03 · P1 · Confirmed source: DatePicker's native form contract loses the submitted value.** `components/date-picker.tsx:24` promises a hidden form input, but the input is rendered inside popover content at line 95. `components/popover.tsx:53` portals that content out of the form and unmounts it while closed. Place the hidden input beside the trigger inside the owning form, with correct disabled/reset behavior and an explicit external-form association if supported. **Acceptance:** `new FormData(form)` contains the selected ISO date while closed and open; clearing, disabling, reset, controlled values, and uncontrolled values behave as documented.

**DS-04 · P1 · Confirmed source: overlapping optimistic edits can restore stale data.** `components/editable.tsx:61` captures the previous value; a rejected save unconditionally calls `onChange(previous)` at line 71. The resting control can immediately reopen at line 171, so a second save can succeed before the first rejects. Success timers also lack operation identity. Define serialization or latest-operation ownership, coordinate server ordering, and prevent obsolete completions from changing the current value or state. **Acceptance:** deferred-promise tests cover A→B followed by B→C, both completion orders, earlier failure after later success, later failure, and unmount.

**DS-05 · P1 product integration · Confirmed source: success messages claim changes that never occur.** In `src/routes/programs.$programId.tsx:831`, archive closes the dialog and announces success without changing program state. At line 853, assessment save validates one field, closes, and announces a saved SCTM result without storing the assessment; method/result fields are uncontrolled. `src/routes/risks.tsx:303` implements Save draft as close; Create risk at line 308 validates then closes. `src/routes/risks.$riskId.tsx:238` similarly closes Add treatment without persisting it. These are prototype completion gaps with a serious feedback consequence, not purely component-library defects. **Acceptance:** each promise corresponds to a command and observable persisted state; reopen/reload proves the change. Until implemented, the preview must communicate its limitation instead of claiming success.

**DS-06 · P2 · Confirmed source: persisted table preferences are trusted without structural validation.** `patterns/data-table/view-store.ts:27` checks only object-ness and `v`; line 69 calls `.filter` on `stored.order`, and subsequent code assumes sizing, visibility, and pinning structures exist. A malformed or older stored object with the same version can throw during mount. Validate the complete shape, finite size bounds, allowed density, and column IDs; discard invalid records safely. **Acceptance:** corrupt JSON, `{v:1}`, wrong field types, obsolete column IDs, and changed view keys cannot break the table.

### Interaction and accessibility

**DS-07 · P1 · Confirmed source/dependency contract: controlled overlays lack a reliable return-focus path.** `components/dialog.tsx:50`, the analogous Sheet/AlertDialog/Command dialog wrappers, and their props omit a Radix Trigger or a return-focus hook. Installed Radix's `react-dialog/dist/index.mjs:154` prevents default close autofocus, then focuses `context.triggerRef.current`; no registered trigger means that path has no destination. Preserve the opener, support a trigger composition or `returnFocusRef`, and define the fallback when an item is removed. **Acceptance:** keyboard open/close by Escape, Cancel, success, and outside dismissal returns focus to the opener or the next meaningful item; nested overlays also work. Manual reproduction is still required.

**DS-08 · P1 · Confirmed source: slotted button behavior can bypass disabled/loading promises.** `components/button.tsx:82` uses Radix Slot; loading is guarded in the wrapper's `onClick` at line 98. Installed Slot merges handlers child-first (`react-slot/dist/index.mjs:90`), so a child's side effect can run before the loading guard. `disabled` also does not disable an anchor's native navigation. Both Button and IconButton advertise `asChild`. Define link/action composition separately or enforce the contract before child handlers execute. **Acceptance:** a loading or disabled slotted anchor/custom child performs neither its handler nor navigation by mouse or keyboard; enabled child handlers run exactly once. Ref and event types must match the rendered element.

**DS-09 · P1 · Confirmed selector mismatch: reduced-motion overrides miss state-qualified animation classes.** `styles/motion.css:132` targets literal `.animate-dialog-in`, `.animate-enter`, etc. Dialog and other components use classes such as `data-[state=open]:animate-dialog-in`, which are different class names. A plain selector does not match the generated variant class. Move reduced-motion behavior into the utility definition or use an explicit, consistently applied motion-reduction variant. **Acceptance:** compiled CSS and browser-computed styles show reduced motion for opening/closing dialogs, sheets, menus, accordions, and responsive shell animations. Also review the deliberately continuous spinner separately; a progress label must remain understandable.

**DS-10 · P1 · Confirmed test selection defect: the accessibility gate omits important open states.** `vitest.config.ts:35` matches the displayed test name `/Matrix$/`. `Dialog.stories.tsx:152`, `Sheet.stories.tsx:179`, and `Drawer.stories.tsx:118` export `OpenMatrix` but name it `Open`; those are skipped. Their selected family stories initially render closed controls. The current run passes **103 tests and skips 443**. Use explicit test tags or a checked manifest, and deliberately open interactive examples. **Acceptance:** CI reports the included story IDs and state coverage; changing a story's display name cannot remove an intended test.

**DS-11 · P1 · Confirmed SSR HTML and automated console evidence: invalid composition is reaching app pages and examples.** The SSR crawl finds a button nested inside a link at `/` and five finding detail URLs. Source examples include `src/routes/index.tsx:130` and `src/routes/findings.$findingId.tsx:238`. The accessibility test run additionally logs `<p>` containing a Chip-rendered `<div>`. Use one interactive root for navigation, and make inline content actually render inline HTML. **Acceptance:** the affected SSR output has no nested interactive elements, the composition story produces valid paragraph content, and unexpected React DOM/hydration errors fail tests.

**DS-12 · P1 · Confirmed source: unnamed controls remain in the consuming app.** `src/routes/risks.$riskId.tsx:129` renders an empty Button with only a hidden icon and no accessible name. The NativeSelects at `src/components/app/control-matrix.tsx:142` and 158 have neither labels nor aria-labels; similar filters appear in `sctm-matrix.tsx:159` and 172 and the SCTM route. An option such as “All statuses” describes the current value, not the control's purpose. Use the required-label IconButton and associated labels for filters; identify repeated row controls by row context. **Acceptance:** role/name queries identify each control uniquely in a realistic page, including repeated editable cells.

**DS-13 · P2 · Confirmed source, interaction checks needed: Tree mixes imperative and declarative tab stops.** `components/tree.tsx:34` imperatively makes the first row tabbable; line 147 derives tabIndex from selection. Starting with no selection sets the first DOM row to 0 while its React prop remains -1. Selecting a different row can leave the first DOM attribute untouched because its React prop did not change, producing two tab stops. Removal also lacks explicit focus transfer; typeahead is absent. A flattened hierarchy sets aria-level but not explicit sibling position/set size. Use one owner for tab-stop state and supply hierarchy metadata where DOM nesting cannot convey it. Returning to the selected item is valid; requiring return to the last arrow-focused item would itself overstate the rule. **Acceptance:** reproduce the no-selection→select-second-row transition; preserve one appropriate entry point, predictable deletion/collapse behavior, announced hierarchy, and documented typeahead support. [ARIA tree pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/).

**DS-14 · P1 quality assurance · Confirmed scope gap: passing checks are being interpreted more broadly than they test.** `scripts/ds-check.mjs:30` excludes shapes/shell from page-template enforcement; export and Matrix detection use source-text patterns. The allowlist can be expanded in the same change, so the “only shrinks” claim is not enforced against the base revision. `.storybook/preview.tsx:86` defaults to light mode, while Vitest config specifies one Chromium instance. No interaction `play` functions were found in the package stories during this pass. **Acceptance:** manifest-based public-surface coverage, a reviewed baseline comparison for allowlist changes, explicit theme/state/browser coverage, and separately recorded manual keyboard/screen-reader evidence. Do not make 100% raw story execution the goal; make promised behaviors covered.

### Forms, content, and page patterns

**DS-15 · P2 · Confirmed contract limitation: Field depends on a narrow child structure.** `components/controls.tsx:62` clones only the immediate child; it recognizes RadioGroup by direct component identity. A Fragment, an application wrapper that drops props, or a group of independently labelled controls can break error/description propagation. `useId` creates message IDs; it does not create a universally associated control ID. Document accepted composition and expose a control/field context or explicit binding API where needed. **Acceptance:** native input, select, date picker, combobox, checkbox/radio groups, and a documented custom control all receive the correct accessible name, error, required state, and focus target.

**DS-16 · P2 · Confirmed source: required-field validation stops at the first error and does not manage recovery.** `components/form.ts:13` stores one missing key; `errorFor` continues returning the old error until another check/reset. The hook has no first-error focus or error-summary contract and handles requiredness only. Keep the small helper if its scope is explicit; add a complete form pattern for dirty/touched state, all errors, format checks, async errors, recovery focus, and preserved input. **Acceptance:** a long form explains all relevant problems, repaired fields stop reporting stale errors, Enter submits correctly, and failures keep user input.

**DS-17 · P2 product integration · Confirmed source: enabled controls imply unavailable capabilities.** The overview Export/Request evidence buttons have no action, `controls.tsx:99` has an inert Import catalog, and app shell search/help/notifications/settings have no implementation. The profile handler explicitly returns undefined. The source inventory found 31 raw buttons, but raw HTML alone is not a defect. Maintain an action inventory and classify every affordance as implemented, unavailable with explanation, or intentionally demonstrative. **Acceptance:** every visible enabled control has an observable result; search scope and behavior match its label; shortcut hints correspond to real shortcuts.

**DS-18 · P2 · Confirmed source: empty search results have inconsistent recovery.** `src/routes/controls.tsx:141` renders a table whose body simply maps `filteredControls`; no-result input leaves headers with no explanatory result. Similar legacy list surfaces need the same pass. Standardize first-use empty, filtered empty, loading, unavailable, and error states with specific recovery actions. **Acceptance:** zero-result filters explain the active condition, allow clearing it, announce result changes appropriately, and do not masquerade as load failure. [Carbon empty-state guidance](https://carbondesignsystem.com/patterns/empty-states-pattern/).

**DS-19 · P2 · Confirmed source: localization is not a supported end-to-end contract.** DatePicker formats English month names; Pagination embeds Previous/Next/Page; table selection embeds Selection/Select all; Toaster embeds Notifications/Close. Locale-dependent `toLocaleString()` calls do not share an explicit locale. Add a scoped provider or injectable strings/formatters for dates, numbers, pluralization, and direction, without embedding translation infrastructure into every app. **Acceptance:** a second-language and RTL fixture cover translated errors, calendars, plurals, long labels, keyboard behavior, and deterministic server/client formatting.

**DS-20 · P2 · Confirmed source, visual verification needed: responsive layout policies are fragmented.** Runtime-resizable widths are legitimate; unexplained fixed content widths and nonresponsive multi-column form grids need review. Examples: `controls.tsx:126` uses a 240px search width, `control-matrix.tsx:149` fixes a select to 188px, and the assessment form uses unconditional two-column grids. Define minimum viable layouts and overflow behavior per page family, rather than replacing every numeric dimension with a word. **Acceptance:** narrow viewport and zoomed layouts preserve the task, labels, controls, and focus; dense tables may scroll in their own region without forcing the whole page into two-dimensional scrolling. [Apple layout](https://developer.apple.com/design/human-interface-guidelines/layout), [web reflow criterion](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

**DS-21 · P2 design guidance · No measured failure claimed: target-size and focus-obscuration policies need explicit web acceptance criteria.** Control heights are 24/28/32px (`tokens/dimension.json:4`), and some embedded tree affordances are smaller. These values alone do not prove failure. Assess actual clickable bounds and spacing, not icon size. Adopt WCAG 2.2 AA as the web engineering target, including documented target-size exceptions and unobscured focus; test touch/coarse-pointer use separately. Apple's platform-specific point sizes must not be presented as a universal CSS-pixel rule. [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

### API grammar, tokens, and governance

**DS-22 · P2 · Confirmed source: public API semantics need a written grammar, with justified exceptions.** Button's `variant` expresses emphasis, AlertDialog's `tone` uses `primary|danger`, while other `tone` props represent status. Size means control height, typography, chart geometry, and sometimes density. These are opportunities to clarify axes; a different permitted subset of the same scale is not inherently inconsistent. Establish semantic definitions and document existing exceptions before choosing any rename. **Acceptance:** a component inventory maps each axis to its meaning, values, default, behavior, and migration rationale.

**DS-23 · P2 · Confirmed source: native props and closed composites have uneven integration affordances.** Button/Input already inherit native props, and Button has a ref. Dialog and many composites intentionally enumerate a much smaller surface. Some legitimate needs—focus restoration, accessible descriptions, form association, deterministic IDs—have no route through those closed APIs. Add capabilities where they are required and specify which DOM element receives them. Do not add `ref`, `className`, `style`, or arbitrary DOM spreading to every helper or multi-root composition. Prefer role/name queries; test IDs are a fallback, not a substitute for semantics. **Acceptance:** integration fixtures demonstrate each supported capability and reject ambiguous/unsupported placements.

**DS-24 · P2 · Confirmed source and DS-01 consequence: dependency exposure needs an explicit ownership policy.** Calendar, Command, toast, and table contracts expose portions of underlying libraries. Wrapping all of them is not automatically better; owning a stable facade entails maintaining behavior and documentation. Classify each dependency as a deliberately public adapter or a private implementation detail. Isolate unstable/unnameable types and offer supported subpath exports where useful. **Acceptance:** package API/declaration diffs expose dependency-driven breaks before release; representative consumers compile against the tarball.

**DS-25 · P2 interoperability · Confirmed source/spec mismatch: the token source is DTCG-shaped, but not 2025.10-conformant interchange data.** `dimension.json:6` stores `"24px"`; `motion.json:6` stores `"70ms"`; `font.json:82` stores string font size/line height. The 2025.10 format uses structured dimension/duration values and numeric typography line height. Existing custom transforms can work correctly while exported data fails an external conforming tool. Pick a supported format version, validate it, and convert at a deliberate boundary. **Acceptance:** schema/conformance validation and an actual import into the intended design tool, preserving aliases, typography, and both modes. [DTCG Format Module](https://www.designtokens.org/tr/2025.10/format/).

**Scope revision · 2026-09-06:** The user explicitly excluded design-tool token import. DS-25 retains schema and semantic validation of both exported modes; an actual Figma/design-tool import is no longer an acceptance requirement for this implementation.

**DS-26 · P2 · Confirmed test policy limitation: contrast checks cover declared pairs, not every rendered combination.** `test/contrast.test.mjs:76` constructs an explicit list; the passing result is **168 pairings across both modes**, not every possible foreground/background/state. Lines 98–101 intentionally permit 1.5:1 input-rest borders. Document the rationale and verify whether other visual information actually identifies each control in context; a comment or passing custom threshold is not conformance evidence. **Acceptance:** add relevant hover/pressed/selected/focus/overlay pairs and rendered checks where composition changes the background. Record exceptions with rationale and user evidence.

**DS-27 · P3 · Confirmed documentation gap: installation and lifecycle guidance are not self-contained in the package.** `README.md:3` references repository-only guidance, and line 40 sends installers to Storybook for installation/CSS order. CI packs a tarball but does not install it into an isolated consumer. `private:true` is not itself a deficiency for an internal workspace package, and publishing publicly is not a prerequisite for maturity. **Acceptance:** copied install/SSR/style setup works from the published artifact or internal tarball; document supported versions, stability, deprecation period, migration support, and contribution ownership.

**DS-28 · P2 governance · Confirmed mismatch between component volume and workflow proof: patterns need real compositions.** The system has many examples, but they do not establish a coherent workflow for validation, save/retry, navigation, destructive recovery, filtering, or inaccessible/empty content. Chart already offers a table twin (`components/chart/frame.tsx:297`), so “no chart alternative” would be inaccurate; test the fidelity and discoverability of the existing alternative. Add a small set of complete, stateful reference workflows and link individual components to them. **Acceptance:** keyboard-completable create/edit/filter/inspect/recover journeys demonstrate content, layout, and data contracts together.

## First principles translated into product rules

The supplied [first-principles essay](https://awiserworld.net/home/first-principles-a-brief-history/) is useful as a prompt to identify assumptions. It is historical/philosophical background, not empirical evidence for a UI rule. The following are this audit's operational hypotheses, to validate with people doing assurance work:

1. **An action label creates a promise.** Save, archive, export, and search must produce the stated observable outcome. This makes DS-05 and DS-17 more urgent than prop vocabulary.
2. **People need to know where they are.** Preserve navigation context, active filters, selection, and keyboard focus across dialogs and updates. DS-07/13/18 address this.
3. **Input is work the user has already done.** Preserve it through validation and failure; do not silently omit a date or roll back a later edit. DS-03/04/16 address this.
4. **Recovery should be proportionate to the consequence.** Reversible work can offer undo; irreversible work needs clear consequences and deliberate confirmation. Implement real reversibility before removing confirmation.
5. **Meaning must survive a different input method, viewport, or language.** Labels, feedback, order, and task completion matter more than matching another system's pixel values. DS-09/12/19/20/21 address this.
6. **A reusable API should make a correct implementation straightforward.** Semantic HTML, form ownership, cancellation, and error behavior belong in the contract. Uniform spelling alone does not establish that.

### API policy to use while implementing

| Concept                 | Recommended policy                                                                                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native element behavior | Retain familiar native props and event types. Preserve `disabled`/`required`/`readOnly` where native.                                                                                                    |
| Controlled state        | A documented `value/defaultValue/onValueChange` or native event contract as appropriate; `open/defaultOpen/onOpenChange` for open state. Do not offer uncontrolled variants when they serve no use case. |
| Loading and pending     | Distinguish progress indication, interaction blocking, and dismissal policy; explicitly state which events remain possible.                                                                              |
| Visual axes             | Separate semantic tone, emphasis, density, size, and representation. Keep existing names until a migration is justified.                                                                                 |
| Text slots              | Specify whether text is visible, accessible-only, helper text, or rich content. An accessible name must describe purpose and agree with a visible label.                                                 |
| Slots and composition   | Document element type, focusability, ownership, event ordering, and ref target. Do not accept arbitrary ReactNode where exactly one usable trigger is required.                                          |
| Escape hatches          | Support legitimate semantics and runtime layout needs. Document DOM targets; prevent arbitrary styling from undermining core states.                                                                     |
| Compatibility           | Additive support first; targeted deprecation, then removal in a chosen release. Codemods only where semantic transformation is safe.                                                                     |

### Required verification matrix
