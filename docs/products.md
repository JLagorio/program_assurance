# Products, configurations and variants

Products are the systems that get assessed. A product (Missile A) has an element tree of subsystems and components that is tracked, broken down and reused; it has configurations that make it slightly different (ground launch, air launch, each with its own launch subsystem); and a variant is what a program makes of a configuration plus the customer's own requirements. The library holds the first two. The third lives in the program, where it is assessed.

## Vocabulary

| Say | Meaning |
| --- | --- |
| **Product** | The stable identity in the library (`products`): code, name, description, active or retired. |
| **Version** | One published or draft state of the product's element tree and configuration membership (`product_revisions`). A published version is immutable; a program pins the exact version it was created from. **New version** copies the current tree and memberships into the next draft. |
| **Element** | One node of the tree in a version (`product_elements`): a subsystem or a component, with the same types as nested systems. An element may be pinned to a component of a published Components library version; its type then follows the component. |
| **Configuration** | A named way the product is built (`product_configurations`, stable across versions). Which elements it includes is explicit membership per version (`product_configuration_elements`); a child is only in a configuration its parent is in. An element that is in one configuration only is that configuration's own subsystem. |
| **Variant** | A program system created from a configuration: the boundary carries `product_revision_id` and `product_configuration_id`, each inherited element carries `product_element_id`. Customer-specific elements sit beside them with no lineage. The product record's **Variants** tab lists them across programs by reading the systems. |

There is no library-level variant record. Customer-specific content stays out of the library and lives where it is assessed; when a customer variant must be reused across programs, save it as a configuration.

## Authoring

`/library/products` is the register; a product's record has a version switcher and four tabs. With no version in its address it opens on the latest published version, and on a draft only while nothing is published; Create product version waits, and says why, while a version is still a draft.

- **Structure**: the element tree with Element, Code, Type, Library (the pinned definition and version) and Configurations (the memberships, or "All configurations"). In a draft version the row menu offers Edit, Add subsystem, Add component, Add from library… and Remove; the toolbar adds an element or one from the library. The element sheet carries the identity, a checkbox per active configuration (all ticked by default for a new element; a configuration the parent is not in is disabled; unticking cascades to the elements inside), and the library facts when pinned.
- **Configurations**: code, name, description, member count, variant count and state. New configuration includes every element of a draft version by default; a late configuration can include the missing elements from its row menu; Retire keeps history and stops new variants.
- **Variants**: Program, Variant (the system), Configuration, Version, and inherited versus added element counts.
- **Versions**: every version with Open version.

**Publish version** needs at least one element and one active configuration. **Export OSCAL** on a published version downloads a component-definition (below).

## What a program inherits

Reusable assessed content rides on the Components library. A product is structure plus configuration: a product element pinned to a library component brings that component's claimed control set exactly as Add from library does, seeded into the variant's draft SSP where the control is in the baseline and recorded as a library assignment with per-claim targets.

In the wizard's Systems & components step, **From a product…** picks a published version and one of its active configurations. The members of the configuration become the elements of a new system, parents remapped, library pins kept with the rationale "Inherited from Product vN · Configuration"; the system is named after the product and configuration and typed as a platform; its categorization and program profile are chosen on its sheet like any other system. Inherited elements can be removed (pruning is subtree-wise) and customer-specific elements added anywhere; the review's **From products** section shows inherited, removed and added counts. An existing program adds a variant the same way from the System tab (**From a product…**, then the dialog naming, categorizing and baselining it) through `add_program_system`, which shares `create_program_system` with the wizard.

The server checks the lineage: the version must be published and the product active; the configuration must belong to the product and be active; every inherited element must be in the version and the configuration, once, with its product type, its product pin and its place under its product parent. Lineage columns on `systems` are written only by these commands.

## Business lines

A business line (`business_lines`: code, name, owner, active or retired) is the level above a product: Air Defense holds the X800 Missile. A product names the business line it belongs to (`products.business_line_id`) and a program may name the one that runs it (`programs.business_line_id`). Both are optional. No screen draws business lines yet.

## A product assessed once

A product assessment (`product_assessments`) judges one published version against a control baseline; its determinations (`product_determinations`) are recorded for each element and control, or for the product as a whole. Because the determination sits where the product varies, on the element, one assessment answers for every configuration: a configuration's standing on a control is the worst determination on the elements it includes. A determination may cite the assessment finding of a program's campaign it was drawn from. A published assessment is immutable, and the latest published one is what the product gives.

`product_control_status(tenant, product version)` answers each control of that baseline for the core (the elements every active configuration includes) and for each configuration: satisfied, partially satisfied, other than satisfied, not assessed (an element claims the control through its library component and nobody judged it) or not covered (nothing claims it, so a program that takes the configuration owes it). Its totals say how many controls are satisfied in every configuration and how many stand differently from one configuration to another. A version with no published assessment answers the controls its elements claim, none of them assessed.

## What a variant changes

An inherited element is as the product delivers it until the program says otherwise. `declare_product_element_change` records what the program changed in it (software, firmware, hardware or data) and why, at the revision the reader saw; an empty list withdraws it. Only the command writes `systems.product_change_kinds`, `product_change_rationale`, `product_changed_at` and `product_changed_by`. An element of the configuration the variant does not hold is removed; an element with no lineage is the program's own.

`variant_control_delta(tenant, system)` reads each control of the variant's control baseline against what the product gives:

| Delta | Meaning | What the program owes |
| --- | --- | --- |
| `inherited` | The product covers it and no element behind it changed | Nothing: the product's standing holds |
| `shared` | The product covers part and leaves the rest to its consumer (a claim's coverage is partial or conditional, or it names a consumer responsibility) | Its own part |
| `changed_here` | An element behind it is modified or removed | A new assessment of that control |
| `program_only` | The product gives nothing for it in this variant | The whole control |

Beside the delta each control carries the product's standing on what the variant kept (`product_status`) and the modified or removed elements behind a change. The answer also counts the variant's elements (inherited, modified, removed, added) and names a newer published version of the product when there is one. The change says whether the program must assess; the product's status says what it inherits. The program's Product delta view draws it (see Screens).

A program's control status counts what its variants inherit (migration `20261113195606_control_status_inherits_product`). Where no assessor of the program has published a determination on a control and every product variant of the program inherits it with one (its delta is `inherited` and its `product_status` satisfied, partially satisfied or other than satisfied), `program_control_status` gives the control the worst of those determinations, says the product determined it (`determined_by`) and names the product assessments it was taken from, the deciding one first (`product_assessments`). The program's own published determination still wins, and a draft product assessment decides nothing. A control that is shared, changed here or program only in any variant, or that a variant's own baseline does not select, keeps the program's ladder (not assessed, no evidence, no requirement, which a control with assessment objectives climbs objective by objective since migration `20261114030116_objective_level_derivation`: no requirement until the program's requirements map every objective, no evidence until each is mapped by one that cites evidence), and so does every control of a program with no variant.

## Taking a newer version

A variant stays at the version it was created from until somebody takes a newer one. Elements are followed across versions by their code, which `copy_product_revision` keeps. `variant_version_changes(tenant, system, product version)` says what taking a published, later version of the same product would do, element by element, and changes nothing: an inherited element the newer version's configuration still has is **kept** (it follows the newer element, and what the program changed in it stays declared); an element new in the product whose place the variant holds (at the top, under a kept element, or under another element being added) is **added**, coded with the variant's own prefix; an inherited element the configuration no longer has is **released** and becomes the program's own; an element the variant left out **stays removed**, and what is new inside it is **skipped**. The answer names the newer version's latest published product assessment, or none, and counts the kept elements whose library pin differs, which the library's own Take version updates. `take_product_version(tenant, system, expected revision, product version, request id)` does it at the variant's revision the reader saw: it re-points the boundary and the kept elements, releases what left, creates the added elements with their library assignment and component (as Add from products does), and records one activity event. A variant already at that version is left as it is, so the same request sent again changes nothing; a draft, older or other product's version is refused, and only the command moves a variant's lineage.

## The delta assessment

`plan_delta_assessment(tenant, system, request id, title)` turns a variant's delta into work: an assessment campaign of the variant's program with a draft plan and one objective for each control that is changed here or program only. What the variant inherits or shares is left out, which is the work the product's assessment saves. A plan is pinned to a published SSP revision, as every assessment plan is, so the command refuses a variant whose SSP is still a draft and says to publish it first. The campaign takes the request's id, so the same request sent again answers the campaign it made. It also names the variant it assesses, `assessment_campaigns.variant_system_id`, which only the command writes, so a variant's delta can list the delta assessments already planned for it.

## Customer requirements

A program that takes a product is handed its customer's requirements. A requirements document (`requirement_sources`: code, title, the issuer's document number, the revision taken, the day received) belongs to a program, and a requirement names its document and its paragraph in it (`engineering_requirements.source_id`, `source_reference`); a paragraph is in a document once. `import_customer_requirements` writes a document's requirements in one request, all or none: a paragraph already there is passed over, so a request sent again, or a later one that carries more paragraphs, adds only the rest. A requirement the document gives no acceptance criteria for records "Not stated in the source document."

The program's answer to a requirement is its compliance statement (`requirement_compliance`): compliant, partially compliant, non-compliant or not applicable, how that is verified (inspection, analysis, demonstration, test, or similarity to an article already verified) and the statement given to the customer.

`requirement_source_compliance(tenant, document)` gives a document back as a compliance matrix in the document's order: each requirement with the program's answer, the controls it maps, the evidence it cites and what meets it, read from the elements it is allocated to. Product: all of them are product elements as delivered. Variant change: one is an inherited element the program modified. Program: one is the program's own. Not allocated: none. A requirement nobody has answered is counted apart as unanswered, never as non-compliant.

The typed reads and commands for all of this are in `src/lib/product-assurance.ts`; the words are `productControlStatuses`, `variantDeltas`, `complianceStatuses` and `requirementMetBy` in `src/lib/status.ts`.

## Screens

These screens draw the reads, each from one request.

- **Business lines** (`/library/business-lines`) is a destination of the navigation beside Products: a register, and a record a business line with its products and its programs. The Products register says each product's business line and filters by it.
- **The product record** opens with what the version gives: one tray counts the controls satisfied in every configuration over a card for the core and each configuration. Its Assessment tab shows the same by control: a band (controls, satisfied in every configuration, differ by configuration, covered by none), a card a configuration with a mark a control, and the List with a status column a configuration. A version nobody assessed says so and links to the version that was. Under them, Product assessments lists the version's assessments with Create product assessment.
- **A product assessment** has a record (`/library/product-assessments/:id`) where an assessor works the sheet (`product_assessment_sheet`): an element, or the product as a whole, is chosen above the baseline's controls, each with what the element's library component claims and what is determined; chosen rows take one determination (Record determination, with a rationale short of satisfied) or lose it (Clear determination) in one request (`record_product_determinations`, a draft only), and Publish product assessment freezes it.
- **The program** shows a variant on its Overview as a tray: the controls to assess, and how many stand on the product. The focused Product delta view (`/programs/:id/product-delta`) gives the four deltas as a band, the elements the program changed with the controls behind each, the controls by family or as a list, and the delta assessments planned for the variant with Plan delta assessment. On the System tab an inherited element is marked as modified from its row or its preview (Mark as modified: what changed and why), and marked as inherited again to withdraw it. Where a newer version of the product is published, the view says so and offers Take version, which reviews what the version would change, element by element, before it takes it. The program's Control status counts the product's determinations where every variant inherits a control: its List's Determined by says Product assessment, and the control's Details link each product assessment, where its Next step leads short of satisfied.
- **Customer requirements** show on the program's Overview as two trays a document (by the program's answer, and by what meets them) and in the focused Compliance matrix view (`/programs/:id/compliance`): the document's requirements in its order with Compliance, Met by, Elements, Verification, Controls and Evidence. A requirement's preview holds the customer's statement beside the program's compliance statement, which is created and edited there. Import requirements reads a CSV, the first sheet of an Excel workbook that holds anything, a ReqIF file, or rows pasted from a spreadsheet, into a new document or one the program holds; `src/lib/requirement-import-file.ts` finds the Reference and Statement columns by their headings, and an Elements column allocates each requirement to the program's elements it names by code.

## OSCAL

A published product version exports as an OSCAL 1.2.2 component-definition (`product_component_definition`): `metadata` names the product and version; `components` has one component per element (uuid = the element id; type from the pinned component or the element type; props under `urn:program-assurance:product` carry the element code, type, position, parent, the pinned defined component and its definition code and version; a link `rel="library-version"` points at the library version; `control-implementations` carry the pinned component's claims per catalog, with `implementation-status` and `coverage` props and statement-level claims as `statements`); `capabilities` has one capability per configuration with `incorporates-components` listing its members. The document is built on demand and validated against the pinned NIST schema in `scripts/tests/fixtures/oscal-component-definition-1.2.2.schema.json`. The program's variant is the OSCAL SSP's system; the export does not claim SSP conformance.
