# Products, configurations and variants

Products are the systems that get assessed. A product (Missile A) has an element tree of subsystems and components that is tracked, broken down and reused; it has configurations that make it slightly different (ground launch, air launch, each with its own launch subsystem); and a variant is what a program makes of a configuration plus the customer's own requirements. The library holds the first two. The third lives in the program, where it is assessed.

## Vocabulary

| Say | Meaning |
| --- | --- |
| **Product** | The stable identity in the library (`products`): code, name, description, active or retired. |
| **Version** | One published or draft state of the product's element tree and configuration membership (`product_revisions`). A published version is immutable; a program pins the exact version it was created from. **New version** copies the current tree and memberships into the next draft. |
| **Element** | One node of the tree in a version (`product_elements`): a subsystem or a component, with the same types as nested systems. An element may be pinned to a component of a published Components library version; its type then follows the component. |
| **Configuration** | A named way the product is built (`product_configurations`, stable across versions). Which elements it includes is explicit membership per version (`product_configuration_elements`); a child is only in a configuration its parent is in. An element that is in one configuration only is that configuration's own subsystem. |
| **Variant** | A program system created from a configuration: the boundary carries `product_revision_id` and `product_configuration_id`, each inherited element carries `product_element_id`. Customer-specific elements sit beside them with no lineage. The product record's **Variants** tab lists them across programs by reading the systems. |

There is no library-level variant record. Customer-specific content stays out of the library and lives where it is assessed; when a customer variant must be reused across programs, save it as a configuration.

## Authoring

`/library/products` is the register; a product's record has a version switcher and four tabs. With no version in its address it opens on the latest published version, and on a draft only while nothing is published; Create product version waits, and says why, while a version is still a draft.

- **Structure**: the element tree with Element, Code, Type, Library (the pinned definition and version) and Configurations (the memberships, or "All configurations"). In a draft version the row menu offers Edit, Add subsystem, Add component, Add from library… and Remove; the toolbar adds an element or one from the library. The element sheet carries the identity, a checkbox per active configuration (all ticked by default for a new element; a configuration the parent is not in is disabled; unticking cascades to the elements inside), and the library facts when pinned.
- **Configurations**: code, name, description, member count, variant count and state. New configuration includes every element of a draft version by default; a late configuration can include the missing elements from its row menu; Retire keeps history and stops new variants.
- **Variants**: Program, Variant (the system), Configuration, Version, and inherited versus added element counts.
- **Versions**: every version with Open version.

**Publish version** needs at least one element and one active configuration. **Export OSCAL** on a published version downloads a component-definition (below).

## What a program inherits

Reusable assessed content rides on the Components library. A product is structure plus configuration: a product element pinned to a library component brings that component's claimed control set exactly as Add from library does, seeded into the variant's draft SSP where the control is in the baseline and recorded as a library assignment with per-claim targets.

In the wizard's Systems & components step, **From a product…** picks a published version and one of its active configurations. The members of the configuration become the elements of a new system, parents remapped, library pins kept with the rationale "Inherited from Product vN · Configuration"; the system is named after the product and configuration and typed as a platform; its categorization and program profile are chosen on its sheet like any other system. Inherited elements can be removed (pruning is subtree-wise) and customer-specific elements added anywhere; the review's **From products** section shows inherited, removed and added counts. An existing program adds a variant the same way from the System tab (**From a product…**, then the dialog naming, categorizing and baselining it) through `add_program_system`, which shares `create_program_system` with the wizard.

The server checks the lineage: the version must be published and the product active; the configuration must belong to the product and be active; every inherited element must be in the version and the configuration, once, with its product type, its product pin and its place under its product parent. Lineage columns on `systems` are written only by these commands.

## Business lines

A business line (`business_lines`: code, name, owner, active or retired) is the level above a product: Air Defense holds the X800 Missile. A product names the business line it belongs to (`products.business_line_id`) and a program may name the one that runs it (`programs.business_line_id`). Both are optional. No screen draws business lines yet.

## A product assessed once

A product assessment (`product_assessments`) judges one published version against a control baseline; its determinations (`product_determinations`) are recorded for each element and control, or for the product as a whole. Because the determination sits where the product varies, on the element, one assessment answers for every configuration: a configuration's standing on a control is the worst determination on the elements it includes. A determination may cite the assessment finding of a program's campaign it was drawn from. A published assessment is immutable, and the latest published one is what the product gives.

`product_control_status(tenant, product version)` answers each control of that baseline for the core (the elements every active configuration includes) and for each configuration: satisfied, partially satisfied, other than satisfied, not assessed (an element claims the control through its library component and nobody judged it) or not covered (nothing claims it, so a program that takes the configuration owes it). Its totals say how many controls are satisfied in every configuration and how many stand differently from one configuration to another. A version with no published assessment answers the controls its elements claim, none of them assessed.

## What a variant changes

An inherited element is as the product delivers it until the program says otherwise. `declare_product_element_change` records what the program changed in it (software, firmware, hardware or data) and why, at the revision the reader saw; an empty list withdraws it. Only the command writes `systems.product_change_kinds`, `product_change_rationale`, `product_changed_at` and `product_changed_by`. An element of the configuration the variant does not hold is removed; an element with no lineage is the program's own.

`variant_control_delta(tenant, system)` reads each control of the variant's control baseline against what the product gives:

| Delta | Meaning | What the program owes |
| --- | --- | --- |
| `inherited` | The product covers it and no element behind it changed | Nothing: the product's standing holds |
| `shared` | The product covers part and leaves the rest to its consumer (a claim's coverage is partial or conditional, or it names a consumer responsibility) | Its own part |
| `changed_here` | An element behind it is modified or removed | A new assessment of that control |
| `program_only` | The product gives nothing for it in this variant | The whole control |

Beside the delta each control carries the product's standing on what the variant kept (`product_status`) and the modified or removed elements behind a change. The answer also counts the variant's elements (inherited, modified, removed, added) and names a newer published version of the product when there is one. The change says whether the program must assess; the product's status says what it inherits. The program's Product delta view draws it (see Screens).

A program's control status counts what its variants inherit (migration `20261113195606_control_status_inherits_product`). Where no assessor of the program has published a determination on a control and every product variant of the program inherits it with one (its delta is `inherited` and its `product_status` satisfied, partially satisfied or other than satisfied), `program_control_status` gives the control the worst of those determinations, says the product determined it (`determined_by`) and names the product assessments it was taken from, the deciding one first (`product_assessments`). The program's own published determination still wins, and a draft product assessment decides nothing. A control that is shared, changed here or program only in any variant, or that a variant's own baseline does not select, keeps the program's ladder (not assessed, no evidence, no requirement, which a control with assessment objectives climbs objective by objective since migration `20261114030116_objective_level_derivation`: no requirement until the program's requirements map every objective, no evidence until each is mapped by one that cites evidence), and so does every control of a program with no variant.

## Taking a newer version

A variant stays at the version it was created from until somebody takes a newer one. Elements are followed across versions by their code, which `copy_product_revision` keeps. `variant_version_changes(tenant, system, product version)` says what taking a published, later version of the same product would do, element by element, and changes nothing: an inherited element the newer version's configuration still has is **kept** (it follows the newer element, and what the program changed in it stays declared); an element new in the product whose place the variant holds (at the top, under a kept element, or under another element being added) is **added**, coded with the variant's own prefix; an inherited element the configuration no longer has is **released** and becomes the program's own; an element the variant left out **stays removed**, and what is new inside it is **skipped**. The answer names the newer version's latest published product assessment, or none, and counts the kept elements whose library pin differs, which the library's own Take version updates. `take_product_version(tenant, system, expected revision, product version, request id)` does it at the variant's revision the reader saw: it re-points the boundary and the kept elements, releases what left, creates the added elements with their library assignment and component (as Add from products does), and records one activity event. A variant already at that version is left as it is, so the same request sent again changes nothing; a draft, older or other product's version is refused, and only the command moves a variant's lineage.

## The delta assessment

`plan_delta_assessment(tenant, system, request id, title)` turns a variant's delta into work: an assessment campaign of the variant's program with a draft plan that holds each control that is changed here or program only as the assessment objectives it counts, one plan objective each, titled by its label and text and aimed at its part (one aimed at its statement for a control that counts none), as Add to assessment campaign writes a control; each objective says why its control is owed. `delta_assessment_objectives(tenant, system)` counts the controls and objectives a plan made now would hold, which Plan delta assessment's Dialog says before it runs. What the variant inherits or shares is left out, which is the work the product's assessment saves. A plan is pinned to a published SSP revision, as every assessment plan is, so the command refuses a variant whose SSP is still a draft and says to publish it first. The campaign takes the request's id, so the same request sent again answers the campaign it made. It also names the variant it assesses, `assessment_campaigns.variant_system_id`, which only the command writes, so a variant's delta can list the delta assessments already planned for it.

## Customer requirements

A program that takes a product is handed its customer's requirements. A requirements document (`requirement_sources`: code, title, the issuer's document number, the revision taken, the day received) belongs to a program, and a requirement names its document and its paragraph in it (`engineering_requirements.source_id`, `source_reference`); a paragraph is in a document once. `import_customer_requirements` writes a document's requirements in one request, all or none: a paragraph already there is passed over, so a request sent again, or a later one that carries more paragraphs, adds only the rest. A requirement the document gives no acceptance criteria for records "Not stated in the source document."

The program's answer to a requirement is its compliance statement (`requirement_compliance`): compliant, partially compliant, non-compliant or not applicable, how that is verified (inspection, analysis, demonstration, test, or similarity to an article already verified) and the statement given to the customer.

`requirement_source_compliance(tenant, document)` gives a document back as a compliance matrix in the document's order: each requirement with the program's answer, the controls it maps, the evidence it cites and what meets it, read from the elements it is allocated to. Product: all of them are product elements as delivered. Variant change: one is an inherited element the program modified. Program: one is the program's own. Not allocated: none. A requirement nobody has answered is counted apart as unanswered, never as non-compliant.

The typed reads and commands for all of this are in `src/lib/product-assurance.ts`; the words are `productControlStatuses`, `variantDeltas`, `complianceStatuses` and `requirementMetBy` in `src/lib/status.ts`.

## A component assessed once

A product's determinations sit on its elements, so they answer for that product alone. A library component that more than one consumer is built from is assessed once, on the component itself (migration `20261115070043_component_assessments`). That migration changed nothing `product_control_status` or `program_control_status` answer; since `20261115140023_component_inheritance` the status reads inherit a component's determinations ([What a consumer inherits](#what-a-consumer-inherits)).

**The component version.** A component of the library lives in one version of its definition: a `defined_components` row in a `component_definition_revisions` row, with an integer `version_number`. That row is the component version. A component has no identity of its own across versions, so it is followed by its name, as Take version follows it: the versions of a component are the components of that name in the revisions of its definition.

**Who answers for it.** A component definition names its owner, a person or an organization, and the business line it belongs to (`component_definitions.owner_party_id`, `business_line_id`). Both are optional. One component of a set may name an owner of its own (`component_owners`, migration `20261115082948_component_offers`): one row a component, by the name it has in the versions of its definition, which a guard checks is a component of some version. A component's effective owner is its own, else its set's, so every component starts with its set's owner and naming another party hands it on. `component_rows`, `component_control_status`, `component_consumers` and `system_upstream` answer the effective owner as `owner_party_id` (the set's own stays readable as `definition_owner_party_id` in the three reads), through the internal `component_owner_party`.

**The assessment.** A component assessment (`component_assessments`) judges one published component version against a published control baseline; each determination (`component_determinations`) is an assessor's finding on one control for one component of that version: satisfied, partially satisfied or other than satisfied, with a rationale and, where the work was done in a program's campaign, the assessment finding it was drawn from. A component may be judged on a control it does not claim. A published assessment and its determinations no longer change.

| Command | What it does |
| --- | --- |
| `record_component_determinations(tenant, assessment, defined component, controls, determination, rationale)` | Records one determination for many controls of one component of a draft, all of them or none; no determination clears them. Recording what is already recorded changes nothing, so the same record sent again is safe. A published assessment, a component of another version and a control outside the baseline are refused. |
| `publish_component_assessment(tenant, assessment, expected revision, expected determinations, request id, completed on)` | Publishes a draft at the revision the reader saw and holding the determinations the reader was told. An assessment already published, changed since, holding no determination or not in the workspace is refused. The request id keeps a private receipt (`component_assessment_requests`), so the same request sent again answers as it first did and the id sent for another assessment is refused. A direct update of the state still publishes, as a product assessment's does. |

**Where a component version stands.** `component_control_status(defined component)` answers each control the component claims through its library implementations or was judged on: the latest published determination on that component version, or not assessed for a claimed control nobody judged, with the totals and the published assessments those determinations were taken from, the newest first. The latest published determination on a control stands, control by control: a later assessment decides the controls it judges and leaves the others to the assessment before it. A draft decides nothing. A determination on one version stands on the next, carried forward, unless that version's change affects the control ([A component's versions](#a-components-versions)).

**Where it is used.** `component_consumers(defined component)` follows the component through every version of its definition and lists who is built from any of them, each with the version it took and how many published versions of the definition are newer (`behind`):

- each product element pinned to it, with its product and version, whether that is the product's current version (its latest published one, else its latest) and the configurations that include it;
- each system component built from it, with its program, system and element (the element the component names, else the one a single inventory item gives it, `system_component_element_links`, else its system), its pin in the system's latest configuration baseline (the latest published, else the latest; the pin's `version` is the program's own text) and, where the element was inherited from a product, whether the program declared it modified (`change`: `inherited` or `modified`, with the kinds and the rationale `declare_product_element_change` recorded);
- each product variant whose configuration includes such an element and that holds no element for it: the program left it out (`change`: `removed`).

The totals count a product by its current version, so a published version nobody can change is not counted as behind for ever: `behind` is the current product elements and the system components built from an older version than the latest published one.

**What a system takes from above.** `system_upstream(system)` answers, for an authorization boundary whole or for one element and what is inside it: the product the system was created from where it is a variant (the version and configuration taken, the newest published version and how many versions behind), and each library component it is built from with the version taken, the latest published version of its definition, how many versions behind, the program's declared change, its pin and the component version's standing as `component_control_status` counts it.

**The register's view.** `component_rows` is one row a component of each definition's latest published version, else of its latest: its definition by code and name, its type, version and state, its owner and business line by name, how many products (by their current version) and programs use it in any version, how many of those consumers are behind or sit on an element the program declared modified (`consumers_behind`, `consumers_modified`), and this version's standing: the controls it claims, how many hold a published determination, its own or one carried forward, and how many of those are satisfied, with the assessment they were taken from (the version's own newest, else the newest one a carried determination came from), and how many controls a change left to review (`controls_to_review`, its last column).

### What a consumer inherits

A component version is judged once, and what it was judged on stands for everything built from it, unmodified (migration `20261115140023_component_inheritance`; Josef, 2026-11-14 and 2026-11-15). Four rules:

1. A component determination names a whole control, so it covers every assessment objective the control counts.
2. Where a product's own assessment and its component's both judge one element and control, the product's own stands.
3. A program inherits per element, with nothing to do. The determination stands for the element built from the component; an objective counts as judged for the program where its requirements place it only on elements that inherit the control; the rest stays with the program's assessor, whose own determination always stands over an inherited one.
4. The product's assessor marks the controls no single component can show and judges them on the product. Anyone using a component version unmodified inherits its determinations.

Nothing moves without a published component assessment: an answer changes only where a determination is inherited or a control is marked for integration, and the keys that say so are written only there.

**A product.** What stands on each element of a product version for each control is one internal read, `product_element_standing`: the determination of the product's latest published assessment on that element (or on the product as a whole, which stays as it was); else, where the element is pinned to a library component, that component version's standing determination (`component_standing_lines`), marked with the component assessment it came from. `product_control_status` and `variant_control_delta` read it, so a variant, and the product branch of its program's control status, follow. A control of `product_control_status` with a cell a component's determination stands in says so in `inherited` (the scope, `core` or a configuration's id, with the component assessments behind it), and the answer names those assessments in `component_assessments`. A version nobody assessed is read over what its elements claim, what their components were judged on and what is marked for integration, with `assessment` still null. A control of `variant_control_delta` that a component's determination stands behind names the assessments (`component_assessments`, each with its worst there) and says whether the product's own assessment judged it too (`product_determined`).

**The integration set.** `product_integration_controls` is the controls of a product version that only integration can show: one row a version and control with why (`rationale`, required), the workspace's to read and write as `product_determinations` are, the control the catalog's or the workspace's own, and neither the version nor the control changes on a row. The set stays open after the version is published, since a product is assessed once it no longer changes. For such a control the component's determination does not stand on the product's elements, and until the product's own assessment judges it, on an element or on the product as a whole, it reads `not_assessed`, never `not_covered`. In a variant it reads as the product gives it: `program_only` with no product status where nothing of the product claims or judges it yet, the product's determination once there is one.

**A program.** An element inherits a control when at least one system component sits on it (the element it names, else the one its single inventory item gives it, `system_component_element_links`, else its system), every system component on it is built from a library component version whose standing holds a determination on that control, and the program has not declared the element modified (`systems.product_change_kinds`). Its determination is the worst among those components. That is the internal `program_element_inheritance`. So an element that also holds a component that is not from the library, or one whose version nobody judged on the control, inherits nothing for it.

An objective the control counts (or the control itself, where it counts none) is judged by inheritance when the program's assessors have not judged it themselves, the program's mappings place it on at least one element, and every element it is placed on inherits the control. It takes the worst of those elements' determinations. Where a mapping stands is the posture's rule, one read for both (`program_objective_placement_answer`, which `program_objective_placement` now answers from): on the element the mapping names where that element's control baseline selects the control, and one that names none on each element its requirement is allocated to. The placement read is planned for the program it is asked about on every call (`plan_cache_mode` `force_custom_plan`, migration `20261117185710_placement_planned_for_its_program`): from a session's sixth call Postgres may otherwise switch it to a generic plan estimated for an average program, and on 2026-11-15 that plan took WS-X90's whole placement from about 45 ms to about 960 ms and the posture reads from about 150 ms to 1 to 2 s on a pooled connection. Today's statistics give a generic plan as fast as the custom ones, so nothing measured moves: about 60 ms for the placement, 145 to 160 for `program_posture`, about 125 for `program_resiliency_posture` and 65 for a Posture cell, each call alike. An objective placed on one element more, which does not inherit, stays with the assessor. That is the internal `program_objective_inheritance`, and `program_control_objective_judgments` reads it and marks what is inherited (`inherited`, with the component assessments behind it), under the program's own determinations.

Because the counting lives there, the rest follows by itself. An inherited objective counts among `objectives_assessed`; a control is decided once every objective is judged or inherited, by the worst of them, and is then the program's (`determined_by` keeps its two values, `program` and `product`); the counts (`program_control_status_counts`), the daily posture snapshots, `risk_threats`, `control_objective_counts` and `plan_control_holdings` read the same judgments; and Add to assessment campaign and Plan an assessment leave an inherited objective out, as they leave out one an assessor judged (only what is left). A control inherited on every objective is written whole, as one judged on every objective is. Inheritance asks nothing of evidence: a control whose requirements cite none can be decided by what its component was judged on.

`program_control_status` says, on a control a component's determination stands behind and on no other, how many of its objectives are judged by inheritance (`objectives_inherited`) and the component assessments they came from (`component_assessments`, each with its title and its worst determination, the worst first). Where the product's determination decides a control and rests on a component's, the same key names that component assessment, and `product_assessments` names a product assessment only where it judged the control itself. The order is as before: the program's own standing first, judged or inherited, then the product branch, then the ladder.

**Where used and Upstream.** Each system row of `component_consumers` and each component of `system_upstream` says how many controls the version taken is judged on (`controls_judged`) and how many of them its element inherits (`controls_inherited`: those the element's control baseline selects, where the element inherits the control by the rule above, so none on an element declared modified, on one that holds a component nobody judged, or on a row the program left out). `system_upstream`'s totals count each such control once.

**What the demo moves.** With the shared components seed applied, one existing read moves: WS-X90's control status. The Audit Log Collector's element (CN-109118) is the only place the program's requirements put all of an objective, so five objectives of two controls, AU-7 and SI-4(2), are judged by inheritance and both controls read satisfied: satisfied 174 to 176, no evidence 235 to 234, not assessed 90 to 89. The Mission Computer's element (CN-109101) inherits the 50 of the component's 54 judged controls that WS-X90's control baseline selects, and no objective stands on it alone. The products and their variants do not move, since their own assessments judge every element and control the components were judged on. The seed's `--check` says what moves, with the totals both times and the controls and objectives inherited.

**What the screens owe.** No screen draws any of this yet. A control decided by inheritance has no assessment finding of its own in the program, so its next step and its trace need a destination on the component: Open assessment findings leads nowhere for it, and the trace's Assessment findings stage says No assessment finding. The Control status, the SSP assembly and the Posture read the new status without saying it is inherited.

### What flows up: offers

Until now what a program found on a shared component counted in that program alone. Josef decided on 2026-11-14 that a program's result on an unmodified shared component is offered to the component's owner, reviewed once and then published as the standing for every consumer, that consumers stay pinned to the version they took, and that a finding then shows in every consumer's Findings at once, a row a fix: each program answers its own row with its own POA&M item. Migration `20261115082948_component_offers` is the schema half.

**The offer.** A `component_offers` row is a program's offer of something it holds on a system component built from a library component (`system_components.defined_component_id`) to that component's owner. It names the component version it was found on, the program, the system and the system component, a kind, a title and a note, who offered it and when, its state (`offered`, then `accepted` or `returned`, or `withdrawn` by the offering side), and who reviewed it, when and with what note. Its items are in `component_offer_items`:

- `finding`: one or more operational issues of the offering program;
- `determinations`: one or more assessment findings of the offering program's published assessment results, each offering that finding's determination on the control it judges (`assessment_finding_rows.control_id`), one finding a control. The offer says the findings were made on this component; the owner's review is the check.

An offer is refused, in words, when the system component is built from no library component, when the program declared its inherited element modified (`systems.product_change_kinds`: the decision is an unmodified component), when an item is not the offering program's, when a finding's results are a draft or it reached no determination, when two findings judge one control, and when the same item already waits in an offer for that component version or was accepted for it. A returned or withdrawn offer frees its items. Clients read the three offer tables and write none of them.

| Command | What it does |
| --- | --- |
| `offer_to_component(tenant, system component, kind, items, title, note, request id)` | Makes the offer and its items, all of them or none, by the caller's party, and writes one activity event for the program ("offered a finding on Mission Computer to Priya Raghavan"). An offer with no title takes its first item's. |
| `withdraw_component_offer(tenant, offer, expected revision, request id)` | Withdraws an offer that still waits, at the revision the reader saw, with one activity event for the program. |
| `review_component_offer(tenant, offer, expected revision, decision, note, request id)` | Accepts or returns an offer that still waits, at the revision the reader saw; a note is required to return. Any member who may write can review; the Review queue says whom it waits on. |

Each is `security definer` behind `can_write_tenant` and keeps a private receipt (`component_offer_requests`), so a request id sent again answers as it first did and the id sent with another choice is refused.

**An accepted finding** stands on the component version. The offering program's operational issue is its source, and every other program that holds a system component built from the same component version (not a newer or an older one) gets one operational issue of its own for each issue offered: title, description and severity copied, open, nobody's, opened at the review. `component_offer_issues` links each to the offer, the offering program's as `source`; a program that already holds one for the item is passed over, so none is opened twice. One activity event is written a program touched, and one for the offering program saying the offer was reviewed. A program that declared its element modified still gets its row: whether the finding applies to its build is its own answer.

**Accepted determinations** are published in the same transaction as one component assessment of that component version, against the offering system's control baseline (`system_effective_baselines`), with one determination a finding citing it (`component_determinations.assessment_finding_id`) and the finding's description as its rationale. A control outside that baseline, a baseline still a draft and a component version still a draft refuse the review, and the offer keeps waiting. The latest published determination on a control stands, so the component's standing changes for every consumer at once, as [above](#a-component-assessed-once). Until an offer is accepted its result counts in the offering program alone.

**The reads.** `component_offer_rows` is the offers' register, one row an offer: the component by name with its set and version, the program, system and system component, the kind and state with their ranks, how many items, who offered and when, the effective owner and, while the offer waits, that owner as who it waits on, who reviewed and when, the component assessment accepted determinations were published as and how many issues an accepted finding opened elsewhere. The Review queue lists an offer still offered as the kind `component_offer` (Offer to review, `reviewQueueKinds`), by the offer's own id, last in the kinds' order: it belongs to the component version, waits on the effective owner since it was offered, was asked by the party that offered it, and counts the determinations accepting it would publish. `component_consumers` gains `findings` (each issue of an accepted offer with the version it stands on, how many programs hold a row for it and how many of those are still open), `findings_open` and `offers_open`, and each of its system lines the program's own open issues for the findings on the version it took (`findings`, `findings_open`); `system_upstream` gains the same on each component, with `offers_open` for that version, and `findings_open` and `offers_open` beside its totals. The totals of both keep slice 1's keys. `component_rows` gains `offers_open`, its last column: the offers that wait on the owner for any version of the component.

What this slice leaves for the next: the status reads still take none of a component's determinations, a finding that stands on a version does not follow a consumer onto a newer version, an accepted finding's consumer issue is tied to its component through `component_offer_issues` alone (no observation is written, since an assessment subject needs a plan), and no screen offers, reviews or lists an offer: the Review queue's screen lists the row and has no handling of its own for the kind yet.

### What a component is made of: SBOMs and CVEs

Josef decided on 2026-11-14 that CVEs and SBOM components are both stored as records, tied to asset, controls and POA&M item, and that a new CVE or finding shows in every consumer's Findings at once, a row a fix. Migration `20261115090429_sboms_vulnerabilities_and_cyber_tests` is the schema half; no existing read answers differently for the data that was there.

**The SBOM.** An `sboms` row is one software bill of materials of exactly one subject, a library component version (`defined_component_id`) or an asset (`inventory_item_id`): its title, its format (`cyclonedx`, `spdx`, `other`) and the version of the format's specification, the document's own serial, the day it was generated and, where the document was captured, its evidence artifact. `sbom_components` is one row a component it lists: its name and version (once each pair in an SBOM), its kind (library, application, operating-system, firmware, container, device, file), supplier, purl, cpe, license and hash, and the component of the same SBOM it sits inside. A subject may hold several SBOMs over time. Its **standing SBOM** is its latest by the day it was generated, and of two generated the same day the one recorded last (the internal `standing_sboms`); every read below reads the standing one, so a newer SBOM takes the older one's place everywhere at once. Members read both tables and writers write them, row-level security deciding; an SBOM's subject never changes, and a component cannot sit inside itself.

| Command | What it does |
| --- | --- |
| `import_sbom(tenant, defined component, inventory item, title, format, spec version, serial, generated on, evidence artifact, components, request id)` | Writes an SBOM and its components in one transaction, all of them or none: between 1 and 5,000 components, each a name with its version, kind (library where none is given), supplier, purl, cpe, license and hash, the document's own reference for it (`ref`) and, where it sits inside another, that one's reference as its `parent`. Refused, in words: no subject or two, a subject or an evidence artifact that is not in the workspace, a component with no name or of an unknown kind, a name and version given twice, a ref given twice, a parent that names no component of the document, and a component inside itself. It answers whether the SBOM now stands for its subject. `security definer` behind `can_write_tenant`, with a private receipt (`sbom_import_requests`): a request id sent again answers as it first did, and the id sent with another choice is refused. |

**The CVE.** A `vulnerabilities` row is one record a CVE in a workspace: its `cve_id` (once in the workspace, shaped CVE-YYYY-N…), title and description, its severity in the product's levels (low, moderate, high, critical) beside its CVSS score and vector, the day it was published, what fixes it (`fixed_in`), a source URI and whether it is known exploited. Three tables tie it to the rest, each once a pair, written as their neighbours are:

- `sbom_component_vulnerabilities`: the CVE on a component of an SBOM, with its state in VEX's words (`affected`, `not_affected`, `fixed`, `under_investigation`; `vulnerabilityStates`) and a note. Through the SBOM's subject this ties the CVE to a library component version or to an asset.
- `vulnerability_controls`: the controls it bears on.
- `issue_vulnerabilities`: the operational issue that is a program's row for the CVE. The issue's POA&M item answers it as today (`issue_poams`), so a CVE reaches its POA&M item through the program's own issue.

A CVE **affects** a component version or an asset where a component of its standing SBOM carries it in the state affected. That is what `vulnerabilities_open` counts wherever a read says it of one version.

A CVE is **open** on a component while it affects a version still in use: the component's newest version (its definition's latest published version, else its latest), or any version a consumer is built from, a product element of a product's current version or a system component. Josef decided it on 2026-11-16 (proposal decision 16): a CVE stays open, and counted, while any consumer still runs an affected version, after the fix is published. So a version 2 whose SBOM marks the CVE fixed leaves it open while a program stays on version 1, and it closes once every consumer has moved to version 2; a CVE on the newest version counts whether or not anybody runs it yet. Each CVE counts once, whichever versions it affects. That is what the component's own `vulnerabilities_open` counts, in the register and in `component_consumers` (migration `20261117185712_open_cves_while_in_use`).

**In every consumer at once.** A CVE recorded on a component version's SBOM shows against every consumer before anybody acts: `component_vulnerabilities` lists each program built from the version with the issue it holds for the CVE, or none. `open_vulnerability_issues(tenant, vulnerability, request id)` (migration `20261115145833_open_vulnerability_issues`) then gives each of them its row, with no offer needed. For every program that holds a system component built from a component version the CVE affects (`component_open_vulnerabilities`) and holds no operational issue for the CVE yet, whatever that issue's status, it opens one: titled by the CVE's identifier and title (CVE-2024-11111 A race in sshd), described by the CVE's description, where it was found (each affected component by name and version with the SBOM components that carry it: Found in Shared unit version 1 (libssl 3.0, sshd 9.6).) and what fixes it where the CVE says, at the CVE's severity, open, nobody's and opened now, linked in `issue_vulnerabilities`, with one activity event a program in the feeds' shape ("… opened an operational issue for CVE-2024-11111" over the CVE's title and where it was found, linked to the issue). It is one issue a program, however many of its components or component versions are affected. It answers `componentVersions` (how many library component versions the CVE affects), `programs` (how many it opened an issue in), `issues` (each with its program) and `held` (how many programs already held one); a CVE that affects no component version through a standing SBOM, one marked not affected or carried only by an SBOM a later one replaced, opens nothing and answers `componentVersions` 0 rather than failing. It is `security definer` behind `can_write_tenant` and keeps a private receipt (`vulnerability_issue_requests`): a request id sent again answers as it first did, and the id sent for another CVE is refused. Run again later with a new id, it opens issues only for the programs exposed since (a program that took the component, a version a new SBOM shows affected), so it is safe to repeat.

An offer carries a CVE the same way, and never opens a second row. `review_component_offer` gives the operational issue it opens in a consumer the CVEs the offered issue is the row for, so a finding that names a CVE, once the component's owner accepts it, leaves every program built from that component version with a row of its own for the CVE, each answered there with its own POA&M item. A consumer that already holds an issue for one of those CVEs (the command opened it, or the program recorded it) keeps that issue: the review links it in `component_offer_issues` for the item, its open one first, else its latest, opens nothing in its place and counts it in `skipped`, and a program in which nothing was opened gets no activity event. The kept issue takes no CVE it did not name: where the offered issue is the row for a second CVE the consumer holds nothing for, `open_vulnerability_issues` for that CVE opens its row.

**The reads.**

- `vulnerability_rows` is the CVEs' register, one row a CVE: the record, `severity_rank` in the product's order and `cve_order` (the identifier with numbers by their value), how many components of standing SBOMs it affects (`sbom_components_affected`), how many library component versions and how many assets those SBOMs describe (`components_affected`, `assets_affected`), how many programs hold an open operational issue for it and how many such issues are open (`programs_open`, `issues_open`: neither resolved nor closed), and how many controls it bears on.
- `sbom_component_rows` is one row a component of each subject's standing SBOM: the component, its SBOM's title, format and day, its subject (`subject_kind` component or asset; `subject_name`; `subject_version`, the component set's version, for a library component; `subject_code`, the set's code or the asset's id; an asset's system and program), the component it sits inside by name, and how many CVEs affect it with the worst severity among them and its rank.
- `component_vulnerabilities(defined component)` answers in one request, as its caller: the version's standing SBOM, each CVE that affects the version through it, the worst first, with the SBOM components affected and the controls it bears on, and under each CVE every program that holds a system component built from this version (as `component_consumers` finds them, by `system_components.defined_component_id`, for this version alone) with the issue it holds for the CVE (its open one first, else its latest, with its status and how many POA&M items answer it), or none: a program that holds none is exposed and has not answered. Its totals count the CVEs, the programs and the answers still owed.
- `component_consumers` gains `vulnerabilities_open` for the component, the CVEs open on it whichever version names it, and on each product and system line for the version it took; `system_upstream` gains it on each component and, beside its totals, across what the system takes, each CVE once; `component_rows` gains it as its last column (before `controls_to_review`), the CVEs open on the component the row lists. The component's two counts were the listed or asked-for version's alone until `20261117185712_open_cves_while_in_use` counted every version still in use; the counts of one version (a consumer's line, a component of `system_upstream`, `component_version_review`'s taken and latest, `component_vulnerabilities`) are as they were, and `vulnerability_rows` counts the component versions a CVE affects, used or not. Every other key and column answers as it did.

What this slice leaves for the next: no command records a CVE or says where it is found (the three tables are written directly, row-level security deciding), no feed matches a CVE to SBOM components by purl or cpe, a program has no read of its own of the CVEs on everything it takes with its issue for each (the Findings screen's read), nothing runs `open_vulnerability_issues` on its own (a CVE's rows are opened when somebody asks, not as the CVE or an SBOM is recorded), a CVE that affects only an asset's SBOM opens no issue in the asset's program, and no screen draws an SBOM, a CVE or its consumers.

### A component's versions

Josef decided on 2026-11-14 that consumers stay pinned to the version they took, that affected controls are flagged for review and that Take version reviews before it writes; and on 2026-11-15 that a new component version carries forward every determination except on the controls its owner lists as affected, which read not assessed until re-judged. Migration `20261115172957_component_versions` adds that, and changes nothing while no set holds a second published version.

**What a version changes.** `component_version_changes` is one row a component of a version of its set (the `defined_components` row of that revision): what this version changes against the version before, as kinds (`software`, `firmware`, `hardware`, `data`, the words `systems.product_change_kinds` uses) and a summary. `component_version_change_controls` lists the controls the change affects, once each. Both are content of their version: written while the revision is a draft and frozen once it is published, by the guard that freezes its components and their claims (`guard_published_parent`). A change is recorded against the version before, so a component a version holds for the first time records none (`guard_component_version_change`), and a control is the catalog's or the workspace's own. The app writes them as rows, row-level security deciding; no command wraps them.

**What carries forward.** The rule lives in one internal read, `component_standing_lines`, which every read of a component's standing counts from. A line a component version and control is, in this order:

| Line | When | What it says |
| --- | --- | --- |
| Its own | A published assessment judged this version on the control | The latest such determination and its assessment |
| Carried | Else, the same component, by its name, was judged on the control in an earlier published version of its set, and neither this version nor a published version between the two lists the control as affected | The determination of the nearest such version, the assessment it came from, and that version (`carried_from_version`, `carried_from_component_id`) |
| To review | Else, an earlier published version was judged on it and a change stopped the carry | `not_assessed`, no assessment, `to_review`, the version whose change stopped it (`affected_in_version`) and what the earlier version read (`earlier_version`, `earlier_determination`) |
| Not assessed | A control the version claims that nobody ever judged | `not_assessed` |

A version's own determination always stands over a carried one. A control stays to review in every later version until one of them is judged on it. A draft version reads what it would carry, so its owner sees what the change leaves to review before publishing; nothing is built from a draft version, so that hands nobody anything. A published version's standing rests on published things only: the version asked about lists what its own change affects whatever its state, and between it and the version judged only published versions count.

**What follows by itself.** `product_element_standing` and `program_element_inheritance` take the lines that hold an assessment, so a product element pinned to the new version and a program's element built from it inherit what carried and the version's own determinations, and stop inheriting a control left to review until it is re-judged. `program_element_inheritance` is redefined only so that its first question, whether anything the program takes from the library was ever judged, follows a component through its earlier versions. A consumer that did not take the new version reads as it did, and as behind.

**The reads.** `component_control_status` says of each control whether its determination is carried and from which version (`carried`, `carried_from`) or is to review (`to_review`, `review`), counts both in its totals, names with each assessment the version it judged, and answers `change`, what this version changes with the controls that affects. `system_upstream` counts `carried` and `to_review` in each component's standing. `component_rows` gains `controls_to_review` as its last column and counts a carried determination among those that stand. Where used (`component_consumers`) keeps its body: the controls a version is judged on are the lines that hold an assessment.

**Take version.** `component_version_review(system component)` is what Take version shows before it writes, in one request: the version the system component is built from and the latest published version of the same component, how many published versions it is behind and how many newer ones are still drafts; each published version after the one taken with what it changes; the controls those changes affect, each with what the version taken and the latest read on it, the program's control status on it and whether the element inherits it today; how many determinations stand on the version taken and on the latest (carried forward, its own, to review); the CVEs the latest fixes, those that affect the version taken through its standing SBOM and not the latest, whose standing SBOM says so, each with the program's issue for it; and `blocked`, why the version cannot be taken where it cannot.

`take_component_version(tenant, system component, defined component, expected revision, request id)` moves a system component to the component of the same name in a newer published version of its set, at the revision the reader saw. It writes the pin, the component's version text and who took it and when (`applied_by`, `applied_at`), and one activity event of the program ("took version 2 of Mission Computer for LRU-001", then the set, the version before and how much carried forward). Nothing else is written: what the program inherits follows from the reads. The request id keeps a private receipt (`component_version_requests`), so the same request sent again answers as it first did and its id sent with another choice is refused.

| Refused | In the reader's words |
| --- | --- |
| A target that is another component, not published, or not newer | Choose a version of the same component; Only a published version can be taken; Choose a newer version than the one in use |
| A component that came through a library assignment (`system_components.assignment_id`) | It moves with its claims, through the Library tab's own Take version (`update_library_assignment`) |
| A component on an element inherited from a product (`systems.product_element_id`) | A variant takes a newer component version through its product |
| A component built from no library component | It has no version to take |
| A component changed since it was read, or gone | Review it again; reload |

The review answers the same reasons before the reader tries (`component_version_refusal` holds the words). Today the wizard and Add from library always record a library assignment, and a variant's elements are a product's, so the command serves the components linked to the library without one, as the shared components seed links WS-X90's LRU-001 and LRU-018.

**What the demo holds.** The shared components seed writes version 2 of the X800 Missile component set and publishes it on 2026-11-12: version 1's 18 components and 473 claims, a change on the Mission Computer (software; OpenSSH server 9.8p1 in place of 9.6p1; its owner, Priya Raghavan, lists AC-17(2), SC-23, SI-2 and RA-5 as affected) and its SBOM, dated 2026-11-12, with CVE-2024-6387 recorded as fixed. The Mission Computer claims neither SI-2 nor RA-5, so those two change nothing on it; version 1 was judged satisfied on AC-17(2) and SC-23, so, nobody having assessed version 2, it reads 61 controls: 52 carried forward (42 satisfied, 6 partially satisfied, 4 other than satisfied), 2 to review and 7 not assessed, 42 of 61 satisfied. Nobody takes it: the X800's GS-MC, Customers A and B and WS-X90's LRU-001 stay on version 1, each one behind (4 consumers behind), and no consumer's status read moves (WS-X90 stays at 176 of 560 satisfied). The register's Open CVEs for the Mission Computer stays 1, since its consumers still run version 1. Take version on LRU-001 shows 52 determinations carried, AC-17(2) and SC-23 no longer inherited (50 to 48 controls inherited) and CVE-2024-6387 fixed beside WS-X90's open issue; taken, WS-X90's control status would not move.

**What this slice leaves for the next.** No typed module or screen: the review, the command, the change's form on a draft version and the carried and to-review marks on a component's status are all owed. A variant has no way to take a newer component version (its product must pin it in a new product version, and Take version of a product does not review component changes). A component that came through a library assignment still moves through `update_library_assignment`, which shows no change, carried count or CVE. Nothing tells a consumer that a newer version is published but the behind counts.

### Cyber T&E: an assessment's kind

Josef decided on 2026-11-14 that Cyber T&E is a kind of assessment under Assessments, with its results on the same chain and reusable on a component. So it is no new record: `assessment_campaigns.kind` is `control_assessment`, as every campaign is unless it says otherwise, or `cyber_test`, and a cyber test names its phase in `cyber_test_phase`: `cvi` (cooperative vulnerability identification), `acd` (adversarial cybersecurity DT&E), `cvpa` (cooperative vulnerability and penetration assessment) or `aa` (adversarial assessment). A cyber test names a phase and nothing else does. Its plan, objectives, results and findings are the records every campaign has: a cyber test's finding is an assessment finding, judges the control of its part and stands on the chain as any other. `component_assessments.kind` takes the same two values, so a component's Cyber T&E is recorded once for everything built from the component version, and its determinations stand as a component assessment's do. Every command that writes a campaign or a component assessment keeps the default. `assessment_objective_rows` gains `campaign_kind` as its last column; the words are `assessmentKinds` and `cyberTestPhases` in `src/lib/status.ts`.

The typed commands and the sheet (`component_assessment_sheet`, one assessment as its author works it) are in `src/lib/component-assessment.ts`; the three reads and the register's read (`componentRegisterRead`) are in `src/lib/component-reuse.ts`. No screen draws them yet, and the offers, the SBOMs and the CVEs have no typed module yet: it waits on the generated types. The demo's shared components are a seed of their own, written and not applied ([Shared components scenario](demo-seed-mapping.md#shared-components-scenario)); it leaves one finding offered and waiting, the Mission Computer's SBOM with CVE-2024-6387 recorded on its OpenSSH server, and one Cyber T&E campaign planned for WS-X90.
