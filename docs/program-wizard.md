# Program creation walkthrough

Program creation uses a dedicated page at `/programs/new`. The four steps write the same records the Catalog, Profiles and Components pages read, and the program page, the element records and the profile pages show what was written. The wizard does not import the old demonstration workspace.

## Steps

1. **Program.** Enter the name, stable code, and mission. Sponsor, responsible parties, and dates are optional; the party pickers contain workspace records.
2. **Catalog and profiles.** Choose one published catalog edition and the published base profiles this program starts from; each row links to its record under Libraries. Catalogs and profiles are named by the short title on their stable record (NIST SP 800-53 Rev 5, NIST SP 800-53 Rev 5 Low baseline) with the version beside it; the OSCAL document's own title stays on the revision for provenance and export. Each chosen base becomes a *program profile*: the base adopted as-is, or, through **Tailor for this program**, an overlay layered on it. The editor shows what is tailored out of the base, what is tailored in from the catalog, the parameter overrides, a by-family breakdown, and the effective control set that results; every decision carries a rationale.
3. **Systems and components.** One tree. A system carries its identity, owner, categorization (confidentiality, integrity, availability with a rationale) and the program profile it adopts; the categorization suggests a profile but never chooses it. Subsystems and components are elements inside the system. **Add from library** pulls a published component definition in as an element of the tree, typed from the component, with the definition's claimed controls shown as *will seed* or *not in baseline* against the system's profile. **From a product…** creates a system as a variant of a published product configuration: the configuration's elements arrive as the system's elements with their library pins kept, inherited elements can be pruned and customer-specific ones added (see `docs/products.md`). Row actions sit behind one kebab per row and in the panel the selected row opens.
4. **Review and create.** A checkout summary, not a restatement: one card per step, each two or three lines (the program's name, code and catalog; each program profile with what was tailored; each system with its categorization, profile, element count and product lineage) and an Edit action back to that step. What was entered in full stays on its step. The final action saves everything atomically; a rejected save retains the draft.

## Reference and tailoring semantics

A tailored program profile is a real OSCAL profile layered on its base: import 0 is the base profile document with `include-all` and one `exclude-controls` entry per control tailored out; import 1, present only when controls are tailored in, is the catalog with explicit `include-controls`; the merge is `as-is`; this layer's parameter overrides sit under `modify/set-parameters`, inherited settings arrive through the import. Rationales are recorded as `profile_rules.rationale`, in `selection_provenance`, and as props under `urn:program-assurance:profile-authoring`. The authored profile, its normalized rows and its resolution (`program-assurance-layered-profile`, with `base_profile_resolution_id`) are published at creation so systems can adopt it and a system can tailor further on top of it. Layering is bounded at three levels on the reference profile.

An inclusion or exclusion affects the selected identifier only; it never silently adds or removes enhancements, and the preview says so when an excluded parent still has selected enhancements. Unsupported profile operations are reported instead of silently approximated. The same authoring path serves the wizard and the element's **Change baseline** dialog (`author_tailored_profile`), and the same resolver (`resolve_base_controls`) accepts a reference profile or a layered one as a base.

## What creation writes

The program and its roles; one `program_reference_choices` row per program profile (the base resolution, or the overlay); one `systems` row per system with `adopted_profile_resolution_id` set, and one per element written straight into the tree; a draft SSP per system with planned implementations for every selected control; for each library element, the pinned `system_components` instance, a `library_assignments` row and its per-claim targets, contributions seeded where the control is in the baseline, and library evidence proposed as uses. A system from a product carries `product_revision_id` and `product_configuration_id`, and each inherited element carries `product_element_id`. No scopes are created at setup; scopes are an assessment register. The creation request has an idempotent receipt. Each system is written by `create_program_system`, which `add_program_system` reuses to add a system to an existing program.

## Downstream surfaces

- The program's Overview rail lists its catalog edition and program profiles with links.
- The program tree marks an element that carries a library component with a **Library** badge; Add from library post-create also creates the child element by default. A system created from a product carries a **Variant** badge and its inherited elements a **Product** badge; the rails link to the product version, the program's References list the products, and the product record's Variants tab lists the programs.
- A profile page's Tailoring tab shows the chain it derives from and the same out/in diff, read-only; the Derivation tab names the base profile or catalog each import points at.
- The Catalog page is scoped to one edition (`?edition=`) and shows which published profiles select each control.

## Validation

`npm run test:app` covers the reference logic (chain walking, overlay inspection, the preview) and the runtime data boundary. With the local stack and the app on port 8080, `npm run test:program-wizard` runs the backend transaction checks (`scripts/test-program-wizard-backend.mjs`: layered authoring, idempotency, elements, library seeding, rejections, permissions, CAS, a system tailoring on top of the overlay) and the browser walk (`scripts/test-program-wizard.mjs`: the four steps, failure recovery, then the program page, the profile page and the catalog page). `scripts/test-system-baselines-backend.mjs` covers layered adoption and the depth limit; `scripts/test-library-reuse-backend.mjs` and `scripts/test-add-from-library.mjs` cover components created as elements; `npm run test:products` covers products, configurations and variants. Authored profiles are validated against the pinned NIST OSCAL 1.2.2 JSON schema. Every operational test record lives in a disposable workspace and is removed afterward.
