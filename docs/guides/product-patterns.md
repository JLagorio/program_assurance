# Product pattern contract

The application's composition guide. Read it before creating or changing a screen. Ledger's Storybook documents what each part does; this guide decides which part this application uses for each shape, names the exceptions, and points at the file to copy. Do not infer a shape from a neighbouring screen, and do not keep a second copy of these rules anywhere else. A screen that needs a shape this guide does not cover gets a written recommendation (kit part or bespoke) before it is built. When a rule changes, change this guide and its reference file together.

## Registers

A standalone register is one `PageHeader` with the name in `PageHeader.Heading` / `PageHeader.Title`, followed by a frameless `DataTable` with `fill`. Nothing else: no sentence under the title, no `Section` around the only table, no create button in the page header (the toolbar carries it). Reference: [WorkTable](../../src/components/prototype/work-table.tsx). All product collections compose [ProductCollection](../../src/components/prototype/product-collection.tsx); domain adapters retain their typed columns and relationships, and delegate the toolbar, query recovery, responsive table and empty region to it. Pass the collection's queries as `queries` rather than wrapping it in `QueryState`: a first load keeps the toolbar over skeleton rows, and a failed refresh keeps the rows under one alert with Retry. ProductCollection draws `DataTable.Sort` and keeps the reader's question (search, sort, filters, page) for the tab's session; a collection inside a dialog, sheet or picker passes `keepQuestion={false}`, since its question ends with the task, and one whose order is its meaning passes `sort={false}`.

The toolbar is the kit `Toolbar`: search first, saved views in `views`, filters in `filters`, Columns and Settings as its children, and one small primary in `actions`. Optional collection commands such as Export belong in the labelled Collection actions overflow beside Columns and Settings. This is the recommended home for secondary collection operations: the primary still creates the record, and export remains available without a second visible toolbar action. Because Columns, Settings and the Collection actions overflow are children, they fold into More after the filters when the row runs out of room; the search, the saved views and the one primary never fold, and on a phone the kit keeps the toolbar to two rows, a third only when More and a long primary cannot share a line (Patterns/Toolbar, Phone). Row actions, the eye and a header's column menu are always shown on a touch screen, and pinned columns give way while they would take most of a narrow frame. When a collection has a second way to create its record, the primary is a `ButtonGroup`: the one create action, then a labelled icon menu for the other paths ("More ways to create a system" in [ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx)); a single path stays a plain small primary. Omit a capability the collection or the reader's role has no use for. Never rebuild the row with an `Inline` or a second wrapper.

Columns come from `defineColumns` by kind. A date is `c.date` with the raw value; formatting never becomes the sort value. The record's name is a `TextLink` rendering a router `Link` to its record page, through `RecordLink` in [record-preview](../../src/components/prototype/record-preview.tsx); a model without a dedicated page links to its schema record. A row click follows the name's destination and is never the only opener. When a join row's visible name is another record with a page (an allocation names its system), the name links to that record and the eye previews the join row. A collection with a preview gives its id column `preview` and `active`, which draws the eye. The eye remains visible on devices without hover and stays keyboard accessible. Buttons act; links navigate.

A tab whose only content is a collection starts with its toolbar and table. The tab already names the collection: do not repeat its heading or put explanatory prose above it. Multiple distinct collections in a record body use `Section` headings, h2, or h3 under a dialog title; never a second page h1. Authored descriptions belong in labelled record properties. Baseline provenance, counts and derivation belong in a collapsed Details section; genuine warnings, missing prerequisites and instructions inside a picker or form remain visible where they affect the task. A shared adapter carries table and data rules only, never a copy of a kit part; headings are an explicit decision of the caller (`Section`, `showHeading`, or `section` for a domain collection), and default to absent; a new adapter needs a domain responsibility beyond renaming the table's props.

Record collections use `DataTable` even when embedded: component Structure and Program uses, product Variants, and requirement Adopted by follow this shape. Two named uses keep the kit `Table`: component/product version history selects the current version with an explicit button, and a profile's Source imports describes its ordered lineage and selection rules. These are version-selection and definition lists, not collection previews. Preserve their meaningful order; do not add search, sorting or an eye merely to resemble a register. This exception depends on the task, not an assumed small row count.

Every product `DataTable` explicitly sets `responsive`. The shared renderer measures its actual container, including space lost to an Aside or Panel, and retains the primary identity and row actions while moving lower-priority fields into a labelled More fields row disclosure. Give the primary name `priority: 0` and a readable width/minimum (usually 180–220px); lower numbers stay in the row longer. No field disappears: resize must not change stored column visibility, filters, sorting, selection, preview state or export. Do not solve narrow tables with a page overflow rule or a smaller font. Reference: [ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx).

Every empty collection supplies an illustration, a title, a one-line explanation and the same create action as its toolbar, under the same role check. A filtered result with nothing in it uses the table's built-in Clear filters unless the collection needs different copy. Empty data and an empty filter result are different states.

## Collection previews

The eye opens a `Shell.Panel` with two distinct headers. The outer preview header contains only global preview navigation: Back when a nested frame is open, previous/next, the full-record link and Close. The panel's name is the record type and "preview" in sentence case (Operational issue preview), which Close and the splitter repeat (Close Operational issue preview). The outer header never shows the record name and holds no record actions. The collection stays mounted, so filters, sort, selection and drafts survive preview navigation. A preview belongs to the tab its collection sits in: choosing another tab ends it, and coming back shows the collection as it was without reopening the preview or moving focus (a collection in a retained tab panel calls `useEndOnHide` from [record-preview](../../src/components/prototype/record-preview.tsx) with the setter that closes its preview). `RecordPreviewProvider` owns one panel across registers; `RecordPreviewPanel` replaces a nested record frame while keeping its parent mounted for Back. Shell owns the panel's placement at every width.

Close and Escape end the whole preview from any frame, and focus returns to the shown record's eye in the collection, else to the control the reader last used there. Back is the only way to leave one frame: it shows the parent frame as it was and returns focus to the control in it that opened the nested one. Opening a preview or a nested frame moves focus to the panel at every width, so the next Tab reaches its navigation. A tooltip open on a header control takes the first Escape and the preview the second. A modifier or middle click on a row opens the name's destination in a new tab and leaves the preview and the collection as they are.

Every collection preview passes `RecordPreviewActions` from [record-preview](../../src/components/prototype/record-preview.tsx) to `RecordPreviewPanel.navigation`: it renders the kit `PreviewNavigation` with previous, next, the announced record and position and a real open-in-new-tab link to the full record. Feed it the table's displayed rows from `useDisplayedRecords`: every row the current search, filters, sort and tree state leave, across all pages, so the position counts the whole result ("REQ-001 Access control, 21 of 62 records") and a row that has left the displayed order is shown as outside the results. When a step crosses a page, the table turns to the page that holds the shown record, and every step brings the marked row into view; turning the page by hand leaves the preview where it is. The table keeps its page only while its rows and columns keep their identity, so memoize what the collection passes. Previous and next change the frame's content, never the frame: key the content by its record, not the component that renders `RecordPreviewPanel`, so focus stays on the control the reader pressed. At an endpoint the control the reader used stays focused and says it is unavailable, and Escape still closes the preview. The status names the record from the frame's title; pass `recordLabel` when the title draws no plain words. The kit control takes callbacks, availability, position and a caller-supplied link; the application composition owns row order and destinations; Shell owns placement. Neither the kit nor Shell imports application routing. Reference: the requirement preview in [requirements-table](../../src/components/prototype/requirements-table.tsx).

The body starts with one inner record `PageHeader`: the record's name is its h2 title, and its domain actions belong in `PageHeader.Actions`. `RecordPreviewPanel` supplies this header from `title` and `recordActions`; consumers do not render a second copy. Use one small primary (Edit system) and, when there is more than one action, an overflow `DropdownMenu` behind a subtle icon button for the rest. Keep the title readable as the inner header reflows at narrow widths. Status, owner, dates, identifiers and editors are labelled properties below it. Do not add a separate body action row or repeat the full-record link at the bottom; a property repeats the name only to edit it. A collection with no domain-specific preview uses `RecordSummaryPreview` in [record-summary-preview](../../src/components/prototype/record-summary-preview.tsx), which requires the `fields` the reader asks for, never every column. Long authored text (a description, a provenance, a rationale) is a labelled `Prose`, not a truncated value. Reference: [the system preview in ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx).

The one modal preview is the evidence artifact's version review, where the task must hold focus: a `PreviewSheet` with global navigation in its outer header, identity and record actions in its inner record header, labelled properties below, and a real full-record destination. A preview inside `PickerSheet` or `RecordBrowser` belongs to the selection task and never becomes a second record workflow. `RecordPreviewPanel.navigation` is required. A panel for a task that is not a collection explicitly passes no collection navigation and names the task in its label; its record identity still belongs in the inner header.

## App navigation

The app uses `Shell collapsedSideNav="icons"`: minimizing the desktop navigation keeps a compact rail of destination icons and the account avatar. Keep the active destination visible, give every top-level destination an icon, and expose its label on hover and keyboard focus. The app mark stays in place; in the minimized header, the expand control appears over that mark on hover or keyboard focus. Expanding restores the labels and the reader's chosen width; the preference survives a reload. The desktop sidebar smoothly changes width in both directions; the phone overlay slides in and out with its scrim. Closing content stops accepting input immediately, and reversing an animation continues from its current position. Use Ledger's motion tokens and honor reduced motion; restoring the saved layout does not animate. Reference: [the app shell](../../src/components/app/shell.tsx). The Shell icon-rail story and the responsive app workflow check this behavior.

The top nav holds the app mark, the record search and the end actions. The search is `Shell.TopNav.Search` opening a `SearchDialog` over programs, risks and assessment findings, each result its code, name and status; ⌘K opens it too, and nothing loads until the reader reaches for it. End actions are `Shell.TopNav.Item`s, so the top nav folds them on a narrow screen. The account is a menu in the side nav's footer, with Sign out last. `Shell locationKey` takes the resolved pathname, so a page change moves focus to Main and announces the page, and choosing a search result hands focus to the new page.

Sign-in, the workspace and the session end follow [workspace](../../src/components/app/workspace.tsx). The sign-in form stays up while it is pending and says what fixes a failure beside its field. While the workspace opens there is a loading screen; when it cannot open, the screen is Workspace unavailable with Retry and Sign out. Sign out first asks every open draft, as a route change does. A session that ends on its own keeps the page, its drafts and its place behind a Sign in again prompt; signing in again as the same person carries on.

## Record pages

One page-level h1 names the record. The breadcrumb goes in `PageHeader.Lead` as a `RecordTrail` of `TrailLink`s from [record-trail](../../src/components/prototype/record-trail.tsx), which matches exactly and marks only its last level current; the name goes in `PageHeader.Title`, and one primary action or an Actions menu in `PageHeader.Actions`, where Inspect record (the schema record) is the last item. A code goes in the trail or in Details, never in place of the name. The header has no back-chevron row, sentence description, status badge, property editor or second action row. Reference: [the task record](../../src/routes/tasks.$taskId.tsx).

State, owner, identifiers and dates sit in an `Inspector` group named Details. A tabbed record renders `Shell.Aside` on Overview; a tab that is a register fills the work area without the rail. A record without tabs keeps its Details rail. A supported inline edit is an `Editable`; a larger change follows the form contract. Comments and activity are a `Timeline` in a `Section` of the record body, newest first, each time with its minutes through the reader's locale and zone.

A missing record is an `Empty` with the search illustration, a clear title, an explanation and a route back. It is never an error alert or an empty title. Loading and failure are different states from not found.

## Dashboards

A dashboard says what needs attention across registers and leaves the work to them. It is one `PageHeader` that holds only the name, a Stat band, then its widgets in the page's own columns: the top-N widgets take two thirds and the activity feed one third while Main has room (an `@container` grid, never the viewport), and they stack in one column when a panel or a phone narrows it. Reference: [the Portfolio](../../src/routes/index.tsx).

The Stat band is one `Stat.Grid frame="band"`, a named group of up to four linked `Stat.Tile`s. Each tile counts one thing a reader acts on (open risks, open operational issues), its note names the part to look at first ("12 high or critical"), and its `link` opens the register it counts; where the register reads its question from the address, the link carries the tile's filter. The value is the number itself, which the tile writes in the reader's locale and mutes at zero. `isLoading` holds its place while it loads; a count that cannot load is `Absent` with a "Could not load" note, under one alert with Retry above the band. A linked tile holds no other control.

A top-N widget is a `Section` whose title says which records and in what order (Highest open risks, Recently updated programs) and whose action is a View all `TextLink` to the register. Its body is a `DataTable` with `responsive` and no toolbar: at most five rows in the order the title names, the record's name as its `RecordLink`, and a row click that follows it. It has no Columns, Settings, column menu (`pinnable` and `hideable` are off), sort, filters, pagination or eye; the register has them. It loads under skeleton rows, and a failure is one alert with Retry that keeps any rows already shown. Its empty state is the compact empty with an icon, a title and one line, with a create action only where the register it stands for would offer one to an empty workspace (Create program).

The activity feed is a `Section` holding a `Timeline size="small" wrap`, newest first and a handful of entries long. Each entry's title says who did what ("Priya Raghavan assigned …"), links to the record it names when that record has a page, carries the program as its meta and what was said as its description, and shows its time as relative words with the full moment in the reader's zone (`dateTime` alone). Consecutive edits of one record by one person are one entry that says what changed and in how many edits. A filterable audit log, such as a program's Activity tab, is a register, not this feed.

## Tabs

Every product page and preview uses a named `TabsList variant="line"`. Its underline spans the content width, up to a rail or panel boundary. The selected indicator slides to the next tab and the new panel enters with a short fade and movement on Ledger motion tokens; reduced motion switches immediately. Only the selected panel occupies the layout, and retained panel state survives selection. The kit owns the horizontal `ScrollArea` and `ScrollBar`: tabs stay in one row and the strip scrolls when it is narrower than its labels, in a desktop preview and on a phone alike. Do not add `flex-wrap`, a width class or an overflow class to `TabsList`. Arrow keys reveal the focused tab without scrolling the page.

## Forms and confirmations

The create and edit surface is a `Dialog` titled with the operation and the singular product noun. The trigger, the dialog title and the primary use the same words: Create task, Create organization, Create risk. `productRecordNoun` and `productCreateLabel` in [product-records](../../src/lib/product-records.ts) own the generic vocabulary, including the party subtype. Create makes a new record; Add or Link connects an existing one. Reference: [CreateTaskDialog](../../src/components/prototype/create-task-dialog.tsx). A record without a dedicated form opens `ProductRecordDialog` over the generic `RecordEditor` in [record-editor](../../src/components/app/record-editor.tsx): its fields follow the schema, its labels come from `productFieldLabel` (Owner, not Owner party), its status choices read as their badges, a value the context fixes shows as labelled text instead of a field, and once the context sets one member of a polymorphic target group (`productTargetGroups`) the others are hidden.

`DialogContent` takes a `width` step (`medium` for a few fields, `large` for a form in two columns), never a pixel width. `DialogBody` (in a Sheet, `SheetBody`) is the one scrolling region; the form sits inside it and the footer stays outside, joined to the form through native form ownership (`form` on the submit button). In `DialogFooter`, Cancel is a `DialogClose` rendered as a subtle Button, before the operation's primary; a dialog whose choices apply as they are made (the tailoring decisions) has no draft to cancel, and its secondary is Close. A button says the operation, never OK, Submit or Save alone. Navigation styled as a button is a `LinkButton` or `LinkIconButton`, never a Button that navigates. Button and action-menu labels stay on one line. Menus size to their contents within the available viewport; a narrow trigger does not constrain its action labels.

Every control sits in a kit `Field`, which binds its label, hint and `FieldError` to the control and carries `required`, `invalid` and `disabled` to it; a form writes no ids or ARIA. The wrappers in [fields](../../src/components/app/fields.tsx) take the field's `error` and a `controlRef`: `TextField` for text, `ChoiceField` (a Select) for a fixed list of values, `ComboboxField` for a set of records, `PartyField` for a person or organization; a moment is a `DateTimeField` and a day a `DatePicker`, never a native date input. A half-typed moment blocks the submission with the field's own message, also when Enter submits from inside the field (`unsettledMoment` in form-feedback). The Field marks a required field; a placeholder never says optional.

The first field takes focus through `initialFocus` on the dialog or sheet content, never `autoFocus`. Focus returns to the opener on close, so the opener stays enabled and mounted while its surface is open; where it cannot, `finalFocus` names a stable element. Validate on submit with the primary enabled, then on change. Every issue marks its field with a FieldError that says what fixes it. One issue moves focus to its control; several show an `ErrorSummary` above the fields, which takes focus and leads to each control. `useFormFeedback` in [form-feedback](../../src/components/app/form-feedback.ts) holds the attempt, the summary and that focus. A result that is not about one field (a failed save, choices that did not load, an unavailable context) is an `Alert` with an explicit role at the top of the body: `role="alert"` for a failure, `role="status"` or `role="note"` for a notice. The form never writes its own `role="alert"` paragraph. A primary that truly cannot run, such as for a viewer, keeps its place and explains itself with `disabledReason`.

A dirty dismissal, a route change away from a draft and a destructive decision go through `useConfirmation` in [confirmation](../../src/components/app/confirmation.tsx) (`discardChanges` for a draft), which renders the kit `AlertDialog`; never `window.confirm`. `useDraftGuard` in [use-draft-guard](../../src/components/app/use-draft-guard.tsx) owns a form's dirty and pending state: it asks before a dirty close or route change, and `start`, `finish` and `complete` bracket the save. The prompt's safe action is Keep editing, which keeps the values and the location; an explicit discard may close or navigate. A destructive or irreversible decision (Remove allocation, Unlink evidence, Publish version) passes its command to `confirm` as `action`: the prompt stays open and pending while it runs, shows a failure inside itself with its action as the retry, and closes on success, which a toast reports. A link a reader can remove has a danger row action and the same item in its preview's overflow menu, through a command in `src/lib` ([requirement-links](../../src/lib/requirement-links.ts)); `useRemovalFocus` in record-preview then moves focus to the collection's primary. Reference: the requirement Allocation, Control mappings and Evidence tabs. A pending save sets `pending` on the Dialog or Sheet, which cancels Escape, outside dismissal and every close control; the fields sit in `FieldSet disabled`, focus moves to the primary, which shows `isLoading` and is never also `disabled`, and the guard blocks navigation. A failed save ends the pending state, keeps the draft and focus, and only then says that retrying will not duplicate the record. The surface closes through its `open` state, so its exit and focus return run before the caller unmounts it. Reload and tab-close protection is the browser's `beforeunload`, never a custom dialog.

Profile control decisions and parameter overrides use Dialogs, including when they edit the program wizard’s draft. They do not extend the element Sheet exception.

The closed list of other surfaces:

- Program setup is a page wizard; its element Sheet edits the wizard's own draft. It validates each step on Continue with FieldErrors and an ErrorSummary, each step change moves focus to the step's heading, and the element Sheet checks its row on Done, with Keep as draft.
- The diagnostic schema inspector keeps addressable `/records/:collection/new` create pages. Product workflows use the Dialog default; the inspector shares its validation, labels and draft protection.
- One supported property is an `Editable`; a filter or a reason at its button is a `Popover`.
- Choosing records is a `PickerSheet`; it may collect one shared rationale when applying a selection, with dirty and pending protection. A second step that authors specifications moves to a Dialog. Linking related records is a `RecordBrowser`. Their internal preview belongs to the selection task. A linking form may supply an explicit operation label so its trigger, title and submit button all say the same Link operation.
- The evidence version review is the modal preview above.

Any other create or edit form is a Dialog, never a Sheet. An `AlertDialog` may open over the Dialog or Sheet that owns the decision; an independent record workflow navigates or replaces the current frame instead of stacking. Dirty and pending protection survive a change of surface.

## States and identity

Loading, errors and retry go through `QueryState` in [work-common](../../src/components/prototype/work-common.tsx), which keeps stale content usable after a failed refresh; libraries recover the same way. `Empty` describes an empty region (`size="compact"` in a small one); `Absent` describes a missing scalar. A status, state, severity or impact renders through the components in [status](../../src/components/app/status.tsx) over the one map in [src/lib/status](../../src/lib/status.ts), and `c.status` takes the same vocabulary; a screen keeps no tone mapper of its own. Every date goes through `DateTime` or the `LedgerProvider` formatters in the reader's zone, never `toLocaleString` or a raw ISO string. A failure is never a blank table, and a load in progress is never an empty state.

Focused program views retain the program name in their h1, include the focused view in the breadcrumb with the program's crumb linking back, show no tab strip, keep the Details rail, and take the program record's browser title (`<program name> — Program — Program Assurance`). The legacy risk and program dashboard URLs redirect to their canonical record.

Every route sets its browser title as `<Screen or record type> — Program Assurance` in its `head()`; a child route never inherits its parent's title. Once its record loads, a record route names it first, in the words of its h1: `<record name> — <record type> — Program Assurance`, through `useRecordTitle` in [browser-title](../../src/components/app/browser-title.ts). While the record loads, and when it is missing, the type alone stands. A screen that stands in for the route titles itself through `useBrowserTitle`: the sign-in form is `Sign in — Program Assurance`, and a workspace that cannot open is `Workspace unavailable — Program Assurance`. The root renders the one `<title>`; a screen never renders its own. Labels use the same words across program tabs, global registers, create actions and forms.

## Product vocabulary

The generic record noun is owned by `productRecordNoun`; a create or edit trigger, Dialog title and primary repeat that operation. Use these terms in columns, collection headings and labels:

| Concept           | Product terms                                                                                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Operational issue | Operational issue / Operational issues. Findings is a workspace grouping when it includes issues and observations.                                                                       |
| Assessment result | Assessment finding / Assessment findings. It is distinct from an operational issue.                                                                                                      |
| System            | System / Systems. A scope names a recorded assessment scope, not a system; old parameter names do not set UI vocabulary.                                                                 |
| Task              | Task / Tasks. My work is the personal register; Schedule is the program workspace containing tasks, lifecycle gates and responsibilities.                                                |
| Supplier          | Suppliers is the register and navigation label; its records are organizations, so the operation is Create organization.                                                                  |
| Risk              | Risk / Risks; Risk register is the standalone collection, POA&M & risk register is the combined workspace.                                                                               |
| Campaign          | Assessment campaign / Assessment campaigns, including the program tab and global navigation.                                                                                             |
| Remediation       | Remediation item is the ongoing record; remediation commitment is its version. A POA&M plan groups the items.                                                                            |
| Record lifecycle  | Status for operational progress; State for draft/published version state.                                                                                                                |
| Responsibility    | Owner for accountability; Sponsor, Assessor and Observer remain distinct recorded roles. Avoid Lead as a synonym for Owner.                                                              |
| Operations        | Create makes a new identity. Edit changes it. Add or Link selects and connects existing records. Map control creates a mapping relationship; Allocate requirement records an allocation. |

The diagnostic inspector displays database collection labels where they identify the schema. They do not replace product nouns in its forms.

## What checks it

`npm run lint` runs the Ledger rules on every application file: tokens only, no margins, no copied kit parts, `TextLink` for links (`ledger/text-link-navigation` rejects an action element rendered by one), `ledger/no-native-confirm` and `ledger/dialog-footer-order`, and the overlay and form rules `ledger/no-overlay-autofocus`, `ledger/no-disabled-while-loading`, `ledger/overlay-width-preset`, `ledger/no-plain-alert-role`, `ledger/link-button-navigation` and `ledger/no-style-design-value`. `ledger/no-inline-config` reports a comment that turns a Ledger rule off, and the application keeps no disable of one; a disable that silences nothing fails the run. A custom link adapter passes when it renders an anchor and forwards props and ref; the browser checks verify the destination. The app-only rules `ledger/product-responsive-table` and `ledger/product-line-tabs` enforce the table and tab contracts, including imported aliases and overriding prop spreads; generic kit examples keep their supported variants. Lint does not read cross-file workflow semantics.

`npm run test:app` guards the application boundary and the lint scope; the package tests cover public-export discovery and composition rules. [The screen inventory](screen-inventory.json) declares every route’s family, browser title, model and closed exceptions. The application boundary test rejects an unlisted route. `test-screen-families.mjs` reads this inventory to check every product route at desktop and touch widths, including every global register’s search, name link, visible eye and panel navigation, with real named fixtures where that family can be independently seeded and missing-record checks for dependent records. Domain workflow suites supply the deeper linked-record fixtures. `npm run test:app-a11y` runs axe and the console over every inventory route at 1440px and at a 390px touch phone, plus sign-in, an open create Dialog and an open preview; its known problems per screen are in `scripts/app-a11y-allow.json`, which may only shrink.

`npm run test:patterns` drives product flows against a disposable local workspace at desktop, 390px and 340px widths (app on port 8080, or `APP_TEST_URL`); the `product-patterns` CI job provisions the committed Supabase schema and pinned reference data with `supabase/setup-cli` and runs it.

Before calling a changed screen done, check it in the running app: real names and links, preview order and endpoints, a failed save, a dirty cancel, a pending dismissal, empty and filtered recovery, and actual table bounds with the panel both open and closed. Check that the outer preview header contains global navigation only and that one inner record header contains the visible name and record actions. Verify a one-row scrollable preview tab strip, a full-width underline, hidden-field access and unchanged reader state after resizing; check the toolbar at 390px and 340px and a register with touch emulated. A scrollable table frame alone does not count as responsive. The Storybook tests cover the kit, not these compositions.
