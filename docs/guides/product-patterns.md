# Product pattern contract

The application's composition guide. Read it before creating or changing a screen. Ledger's Storybook documents what each part does; this guide decides which part this application uses for each shape, names the exceptions, and points at the file to copy. Do not infer a shape from a neighbouring screen, and do not keep a second copy of these rules anywhere else. A screen that needs a shape this guide does not cover gets a written recommendation (kit part or bespoke) before it is built. When a rule changes, change this guide and its reference file together.

## Registers

Every register, record page and dashboard starts with `Page` from [the app shell](../../src/components/app/shell.tsx): its `PageHeader`, then its body, `space.200` apart, kept inside Main (`min-w-0`) and rising in once as the page opens; a loading or missing-record state inside it takes the same `Page` without rising again. A screen never builds its own root `Stack`.

A standalone register is one `PageHeader` with the name in `PageHeader.Heading` / `PageHeader.Title`, followed by a frameless `DataTable` with `fill`. Nothing else: no sentence under the title, no `Section` around the only table, no create button in the page header (the toolbar carries it). Reference: [WorkTable](../../src/components/prototype/work-table.tsx). All product collections compose [ProductCollection](../../src/components/prototype/product-collection.tsx); domain adapters retain their typed columns and relationships, and delegate the toolbar, query recovery, responsive table and empty region to it. Pass the collection's queries as `queries` rather than wrapping it in `QueryState`: a first load keeps the toolbar over skeleton rows, a failed refresh keeps the rows under one alert with Retry, and a page, search or filter on its way over the last one's rows (a query that keeps its previous data) keeps them under the table's busy state. ProductCollection draws `DataTable.Sort` and keeps the reader's question (search, sort, filters, page) in the address, its parameters named after the table's `view` (`risk-register.q`, `risk-register.filters`), so Back, a reload and a shared link ask it again and two collections on one page keep their own. The tab's session remembers it too, so a register reached with no question in the address asks the last one it asked and writes it back. A link that opens a register on a question builds its search with `questionSearch` from [collection-question](../../src/components/prototype/collection-question.ts), naming a view from [register-views](../../src/lib/register-views.ts), and a route's own navigation (a tab change) merges over the current search rather than replacing it. A collection inside a dialog, sheet or picker passes `keepQuestion={false}`, since its question ends with the task and stays out of the address, and one whose order is its meaning passes `sort={false}`. A read-only review table inside a Dialog (Take version's changes, Add from library's claims) is a `compact` ProductCollection with `sort={false}` and `keepQuestion={false}`, over a table whose `pinnable` and `hideable` are off and whose columns are not `sortable`: search only, in the order the review lists, with no Sort, Columns, Settings, column menu or sorting heading. Reference: the changes table in [library-update-review](../../src/components/prototype/library-update-review.tsx).

The toolbar is the kit `Toolbar`: search first, saved views in `views`, filters in `filters` with the count of applied filters in `activeFilters` (`table.state.columnFilters.length`, which ProductCollection passes), Columns and Settings as its children, and one small primary in `actions`. A register, and a tab whose only content is a collection, keeps that small primary. In a record body or a preview that holds collections under Section headings, each collection's create action is a small secondary, and the page header or the preview's record header keeps the surface's one primary: ProductCollection draws a `compact` collection's create action, in its toolbar and its empty state, as a secondary unsaid (`actionVariant`), and a headed EntitySection, a `section` ProgramCollection and a compact AssessmentTable are compact. A create drawn where ProductCollection cannot reach it, such as a menu trigger's `render`, is written `variant="secondary"`. Reference: the program's Schedule tab in [program-workspace](../../src/components/prototype/program-workspace.tsx). The search says Find and the collection, as its placeholder and its name (Find risks, Find assessment findings); ProductCollection writes it from the collection's noun when the caller names none. A compact collection in a preview whose task asks nothing of a search (an evidence artifact's Versions) passes `search={false}` and keeps its create action. Optional collection commands such as Export belong in the labelled Collection actions overflow beside Columns and Settings. This is the recommended home for secondary collection operations: the primary still creates the record, and export remains available without a second visible toolbar action. Because Columns, Settings and the Collection actions overflow are children, they fold into More after the filters when the row runs out of room, and a folded More says how many filters apply; the search, the saved views and the one primary never fold, and on a phone the kit keeps the toolbar to two rows, a third only when More and a long primary cannot share a line (Patterns/Toolbar, Phone). Row actions, the eye and a header's column menu are always shown on a touch screen, and pinned columns give way while they would take most of a narrow frame. When a collection has a second way to create its record, the primary is a `ButtonGroup`: the one create action, then a labelled icon menu for the other paths ("More ways to create a system" in [ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx)); a single path stays a plain small primary. Omit a capability the collection or the reader's role has no use for. Never rebuild the row with an `Inline` or a second wrapper.

Columns come from `defineColumns` by kind. A date is `c.date` with the raw value at its kind's width; formatting never becomes the sort value. A person (an owner, a sponsor, a reviewer) is `c.person`, or `kind: "person"` on a ModelTable, EntitySection or ProgramCollection column, which reads the people's names once and sorts, filters and searches by them; several values in one cell (assignees, types) are a `c.list`, whose filter lists each value once, never an array joined into a text column. The record's name is a `TextLink` rendering a router `Link` to its record page, through `RecordLink` in [record-preview](../../src/components/prototype/record-preview.tsx); a model without a dedicated page links to its schema record, and a record with no stored name links as "Unnamed <noun>", never as a missing value. A row whose record has no page yet (a selected control with no implementation) names it with a link-styled `Button` that opens its preview, its row click does the same, and its preview passes `openLink={false}` to `RecordPreviewActions`; reference: the Controls tab in [ssp-assembly](../../src/components/prototype/ssp-assembly.tsx), where a control is named by its code and title together in its one identity cell, since control titles repeat across families. A name that needs the record's kind, a mark or a second line takes `icon`, `badge` and `description` on its column (Ledger's `Table.Name`), never an `Inline` or a `Stack` in `cell`. In a cell that cuts it, a name ends in an ellipsis and shows whole on hover, on keyboard focus and on a long press. The primary name (`priority: 0`) names its row: DataTable draws its cell as the row header and names every row control after its text (Select, Row actions for, Preview, Show N more fields for); pass `rowLabel` only when a reader knows the row by other words, such as its code in a picker. A row click follows the name's destination and is never the only opener. When a join row's visible name is another record with a page (an allocation names its system), the name links to that record and the eye previews the join row. A collection with a preview passes `preview: { onPreview, activeId }` to `useDataTable`, memoized on the shown record's id, which draws the eye at the end of the row's first value, a column of any kind (the name, when it leads the row); the columns stay at module level, or memoized on what they read, so stepping through the preview never rebuilds them. The eye remains visible on devices without hover and stays keyboard accessible. Buttons act; links navigate.

A tab whose only content is a collection starts with its toolbar and table. The tab already names the collection: do not repeat its heading or put explanatory prose above it. Multiple distinct collections in a record body use `Section` headings, h2, or h3 under a dialog title; never a second page h1. A title no kit part draws is a `Heading` at the size it matches (`page` for a page or record title, `section` for a section's, `overlay` inside an overlay), never a raw `h1`–`h6` with type classes. Authored descriptions belong in labelled record properties. A Section's description is an instruction or an authored definition, never a computed sentence: a count is the Section's `count` (`countMax={9999}` for rows), and progress is a labelled `Progress` whose value says the count (Gates completed, 14 of 19), as on the Lifecycle timeline in [program-timeline](../../src/components/prototype/program-timeline.tsx). Baseline provenance, counts and derivation belong in a collapsed Details section; genuine warnings, missing prerequisites and instructions inside a picker or form remain visible where they affect the task. A shared adapter carries table and data rules only, never a copy of a kit part; headings are an explicit decision of the caller (`Section`, `showHeading`, or `section` for a domain collection), and default to absent; a new adapter needs a domain responsibility beyond renaming the table's props.

Record collections use `DataTable` even when embedded: component Structure and Program uses, product Variants, and requirement Adopted by follow this shape. Two named uses keep the kit `Table`: component/product version history selects the current version with an explicit button, and a profile's Source imports describes its ordered lineage and selection rules. These are version-selection and definition lists, not collection previews. Preserve their meaningful order; do not add search, sorting or an eye merely to resemble a register. This exception depends on the task, not an assumed small row count. A system preview's Contains card, the elements inside a system, is a `Related` list (`layout="list"`, compact): each row is its code and name with its kind as the subtle meta, and opens that element's preview. It summarizes what is inside rather than being a collection to work through, so it has no search, sort, eye or trailing count. Reference: [system-assurance-details](../../src/components/prototype/system-assurance-details.tsx).

Every product DataTable is responsive, which is the DataTable's default: product code never writes `responsive={false}`, and a DataTable that takes a prop spread writes `responsive` after it. The shared renderer measures its actual container, including space lost to an Aside or Panel, and retains the primary identity and row actions while moving lower-priority fields into each row's More fields disclosure, a labelled count ("+3", named Show 3 more fields for REQ-001). Give the primary name `priority: 0` and a readable width/minimum (usually 180–220px); lower numbers stay in the row longer. No field disappears: resize must not change stored column visibility, filters, sorting, selection, preview state or export. Do not solve narrow tables with a page overflow rule or a smaller font. Reference: [ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx).

A collection that pages takes 25 rows a page through `useCollectionTable` in [collection-question](../../src/components/prototype/collection-question.ts) (ModelTable, EntitySection and ProgramCollection do it unsaid), and another `pageSize` only where its task needs one. One that can hold more than about 200 rows pages or sets `virtualize` on its table, in a dialog, a sheet or a picker as on a page; one the server holds in thousands is `manual` with `rowCount`. Never draw every row at once.

Every empty collection supplies an illustration, a title, a one-line explanation and the same create action as its toolbar, under the same role check. A filtered result with nothing in it uses the table's built-in Clear filters unless the collection needs different copy. Empty data and an empty filter result are different states.

## Collection previews

The eye opens a `Shell.Panel` with two distinct headers. The outer preview header contains only global preview navigation: Back when a nested frame is open, previous/next, the full-record link and Close. Back is `Shell.Panel.Back`, the header's first child: an arrow that leads the bar, set apart from previous/next and Close at its end. The panel's name is the record type and "preview" in sentence case (Operational issue preview), which Close and the splitter repeat (Close Operational issue preview). The outer header never shows the record name and holds no record actions. The collection stays mounted, so filters, sort, selection and drafts survive preview navigation. A preview belongs to the tab its collection sits in: choosing another tab ends it, and coming back shows the collection as it was without reopening the preview or moving focus (a collection in a retained tab panel calls `useEndOnHide` from [record-preview](../../src/components/prototype/record-preview.tsx) with the setter that closes its preview). `RecordPreviewProvider` owns one panel across registers; `RecordPreviewPanel` replaces a nested record frame while keeping its parent mounted for Back. Shell owns the panel's placement at every width.

Close and Escape end the whole preview from any frame, and focus returns to the shown record's eye in the collection, else to the control the reader last used there. Back is the only way to leave one frame: it shows the parent frame as it was and returns focus to the control in it that opened the nested one. Opening a preview or a nested frame moves focus to the panel at every width, so the next Tab reaches its navigation. A tooltip open on a header control takes the first Escape and the preview the second. A modifier or middle click on a row opens the name's destination in a new tab and leaves the preview and the collection as they are.

Every collection preview passes `RecordPreviewActions` from [record-preview](../../src/components/prototype/record-preview.tsx) to `RecordPreviewPanel.navigation`: it renders the kit `PreviewNavigation` with previous, next, the announced record and position and a real open-in-new-tab link to the full record. Feed it the table's displayed rows from `useDisplayedRecords`: every row the current search, filters, sort and tree state leave, across all pages, so the position counts the whole result ("REQ-001 Access control, 21 of 62 records") and a row that has left the displayed order is shown as outside the results. When a step crosses a page, the table turns to the page that holds the shown record, and every step brings the marked row into view; turning the page by hand leaves the preview where it is. The table keeps its page only while its rows and columns keep their identity, so memoize what the collection passes. Previous and next change the frame's content, never the frame: key the content by its record, not the component that renders `RecordPreviewPanel`, so focus stays on the control the reader pressed. At an endpoint the control the reader used stays focused and says it is unavailable, and Escape still closes the preview. The status names the record from the frame's title; pass `recordLabel` when the title draws no plain words. The kit control takes callbacks, availability, position and a caller-supplied link; the application composition owns row order and destinations; Shell owns placement. Neither the kit nor Shell imports application routing. Reference: the requirement preview in [requirements-table](../../src/components/prototype/requirements-table.tsx).

The body starts with one inner record `PageHeader`: the record's name is its h2 title, and its domain actions belong in `PageHeader.Actions`. `RecordPreviewPanel` supplies this header from `title` and `recordActions`; consumers do not render a second copy. Use one small primary (Edit system) and, when there is more than one action, an overflow `DropdownMenu` behind a subtle icon button for the rest. Keep the title readable as the inner header reflows at narrow widths. Status, owner, dates, identifiers and editors are labelled properties below it. Do not add a separate body action row or repeat the full-record link at the bottom; a property repeats the name only to edit it. A collection with no domain-specific preview uses `RecordSummaryPreview` in [record-summary-preview](../../src/components/prototype/record-summary-preview.tsx), which requires the `fields` the reader asks for, never every column. Long authored text (a description, a provenance, a rationale) is a labelled `Prose`, not a truncated value. Reference: [the system preview in ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx).

The one modal preview is the evidence artifact's version review, where the task must hold focus: a `PreviewSheet` with global navigation in its outer header, identity and record actions in its inner record header, labelled properties below, and a real full-record destination. A preview inside `PickerSheet` or `RecordBrowser` belongs to the selection task and never becomes a second record workflow. `RecordPreviewPanel.navigation` is required. A panel for a task that is not a collection explicitly passes no collection navigation and names the task in its label; its record identity still belongs in the inner header.

## App navigation

The app uses `Shell collapsedSideNav="icons"`: minimizing the desktop navigation keeps a compact rail of destination icons and the account avatar. Keep the active destination visible, give every top-level destination an icon, and expose its label on hover and keyboard focus. The app mark stays in place; in the minimized header, the expand control appears over that mark on hover or keyboard focus, and shows there at rest on a screen without hover (a tablet in landscape). Expanding restores the labels and the reader's chosen width; the preference survives a reload. The desktop sidebar smoothly changes width in both directions; the phone overlay slides in and out with its scrim. Closing content stops accepting input immediately, and reversing an animation continues from its current position. Use Ledger's motion tokens and honor reduced motion; restoring the saved layout does not animate. Reference: [the app shell](../../src/components/app/shell.tsx). The Shell icon-rail story and the responsive app workflow check this behavior.

The top nav holds the app mark, the record search and the end actions. The search is `Shell.TopNav.Search` opening a `SearchDialog` over programs, risks and assessment findings, each result its code, name and status; ⌘K opens it too, and nothing loads until the reader reaches for it. End actions are `Shell.TopNav.Item`s, so the top nav folds them on a narrow screen. The account is a menu in the side nav's footer, with Sign out last. `Shell locationKey` takes the resolved pathname, so a page change moves focus to Main and announces the page, and choosing a search result hands focus to the new page.

Sign-in, the workspace and the session end follow [workspace](../../src/components/app/workspace.tsx). The sign-in form stays up while it is pending and says what fixes a failure beside its field. While the workspace opens there is a loading screen; when it cannot open, the screen is Workspace unavailable with Retry and Sign out. Sign out first asks every open draft, as a route change does. A session that ends on its own keeps the page, its drafts and its place behind a Sign in again prompt; signing in again as the same person carries on.

## Record pages

One page-level h1 names the record. The breadcrumb goes in `PageHeader.Lead` as a `RecordTrail` of `TrailLink`s from [record-trail](../../src/components/prototype/record-trail.tsx), which matches exactly and marks only its last level current. A record inside a program (a requirement, a control, a component, a system) is trailed Programs › the program › the program tab that lists it › any element that contains it: [program-record](../../src/components/prototype/program-record.tsx) draws it for the system, component and control records, and [requirement-record](../../src/components/prototype/requirement-record.tsx) for a requirement. The name goes in `PageHeader.Title`, and one primary action or the Actions menu, `RecordActions` in [work-common](../../src/components/prototype/work-common.tsx), in `PageHeader.Actions`: the edit first, the record's other commands as its children, and Inspect record (the schema record) last. A viewer keeps the menu with Inspect record alone. A code goes in the trail or in Details, never in place of the name. The header has no back-chevron row, sentence description, status badge, property editor or second action row. Reference: [the task record](../../src/routes/tasks.$taskId.tsx).

State, owner, identifiers and dates sit in an `Inspector` group named Details, in a `Shell.Aside` named after the record type, `<Record type> details` (Task details, System details, Program details), whose `summary` is the record's `StatusBadge` where the record has a status or a state. Render the Aside where its Details belong on a phone: right after the PageHeader (and its error alert) on a record without tabs, and first in Overview's panel on a tabbed record, rendered only while Overview is selected. From the aside breakpoint it is the rail beside the work area; below it, wherever the rail would follow Main, Shell shows it in that place as a closed Details disclosure whose row carries the state, so state, priority and due are one tap from the top and the collections keep their place. A tab that is a register fills the work area without it. Reference: [the task record](../../src/routes/tasks.$taskId.tsx).

A `KeyValue.Group` in the rail or a preview takes a named `labelWidth` (`default`, or `wide` for labels of about twenty characters), and one in a record body takes `labelWidth="auto"`; never a pixel width. A property edited in place (an owner, a type) is an `Editable` row in Details beside the identifiers and state, and a due day is `Editable.Date`; the body holds the authored text (a title, a statement, criteria, a rationale). A form whose fields span both shares one save at a time: RequirementForm in [requirement-form](../../src/components/prototype/requirement-form.tsx) hands its caller a `body` and the `properties`. A larger change follows the form contract. A version chooser in the rail is one of its facts, a KeyValue whose value is the Select. A record whose tabs all read one revision names it in a version menu in `PageHeader.Actions` instead, shown on every tab: a trigger reading Revision and its version, and a radio row per revision with its state; its Overview carries the revision's substance, with the provenance in a collapsed Section. Reference: [the profile record](../../src/routes/profiles.$profileId.tsx).

Comments and activity are a `Timeline` in a `Section` of the record body, newest first, each time with its minutes through the reader's locale and zone; the program's activity is the last Section of its Overview, grouped by month. A reader who may comment writes in the Comments section's `Composer` (see the closed list under Forms).

A missing record is an `Empty` with the search illustration, a clear title, an explanation and a route back. It is never an error alert or an empty title. Loading and failure are different states from not found.

## Dashboards

A dashboard says what needs attention across registers and leaves the work to them. It is one `PageHeader` that holds only the name, a Stat band, then its widgets in the page's own columns: the chart and top-N widgets take two thirds and the activity feed one third while Main has room (an `@container` grid, never the viewport), and they stack in one column when a panel or a phone narrows it. Reference: [the Portfolio](../../src/routes/index.tsx).

The Stat band is one `Stat.Grid frame="band"`, a named group of up to four linked `Stat.Tile`s. Each tile counts one thing a reader acts on (open risks, open operational issues), its note names the part to look at first ("12 high or critical"), and its `link` opens the register it counts on the tile's question, through `questionSearch`: a tile that counts part of a register carries its filter, and one that counts the whole register clears the filters (`{ filters: [] }`), so it opens what it counts whatever the register last asked. The value is the number itself, which the tile writes in the reader's locale and mutes at zero. `isLoading` holds its place while it loads; a count that cannot load is `Absent` with a "Could not load" note, under one alert with Retry above the band. A linked tile holds no other control.

A chart widget is a `Chart` frame. Its title says what it counts and how it splits it (Open risks by likelihood and impact), a heading at the widgets' level (`titleLevel`), its description says what the plot leaves out (open risks not yet assessed), and its table twin is one toggle away. It loads as the plot's skeleton. A failure is one alert with Retry above it (`QueryState`), as on the other widgets: a failed refresh keeps the plot, and a failed first load says Could not load in the plot's place. Each mark that holds records links to the register filtered to them through the register's address question (`link` on `Chart.Heatmap`, built with `questionSearch`), and the table twin carries the same links; a mark of zero does not link, and a mark never opens a card. Reference: the risk matrix in [the Portfolio](../../src/routes/index.tsx).

A top-N widget is a `Section` whose title says which records and in what order (Highest open risks, Recently updated programs) and whose action is a View all `TextLink` to the register, which opens it unasked (`questionSearch(view, { filters: [] })`) rather than on the question it last asked in the tab. Its body is a `DataTable` with no toolbar: at most five rows in the order the title names, the record's name as its `RecordLink`, and a row click that follows it. It has no Columns, Settings, column menu (`pinnable` and `hideable` are off), sort, filters, pagination or eye; the register has them. It loads under skeleton rows, and a failure is one alert with Retry that keeps any rows already shown. Its empty state is the compact empty with an icon, a title and one line, with a create action only where the register it stands for would offer one to an empty workspace (Create program).

The activity feed is a `Section` holding a `Timeline size="small" wrap`, newest first and a handful of entries long. Each entry's title says who did what ("Priya Raghavan assigned …"), links to the record it names when that record has a page, carries the program as its meta and what was said as its description, and shows its time as relative words with the full moment in the reader's zone (`dateTime` alone). Consecutive edits of one record by one person are one entry that says what changed and in how many edits. A filterable audit log is a register, not this feed, and a record's own activity is the Timeline in its body (Record pages).

## Tabs

Every product page and preview uses a named `TabsList variant="line"`. Its underline spans the content width, up to a rail or panel boundary. The selected indicator slides to the next tab and the new panel enters with a short fade and movement on Ledger motion tokens; reduced motion switches immediately. Only the selected panel occupies the layout, and retained panel state survives selection. The kit owns the horizontal `ScrollArea` and `ScrollBar`: tabs stay in one row and the strip scrolls when it is narrower than its labels, in a desktop preview and on a phone alike. Do not add `flex-wrap`, a width class or an overflow class to `TabsList`. `TabsContent` starts the panel `space.150` under a horizontal strip, so a screen adds no space between the strip and its panel: no `pt-*` on `TabsContent` or on a panel's first block, no `gap-*` on `Tabs`, and no `contents` on either. Arrow keys reveal the focused tab without scrolling the page.

A record page's tabs live in the address: choosing one pushes a history entry, so Back returns to the tab before, and an address that names no tab shows the first. Where the address owns the tab, it is the only owner; the component keeps no copy of its own. A strip inside a tab keeps its own search key (the program's Assessment campaigns tab keeps `assessmentTab`, and coming back to that tab shows the inner tab last shown). A preview's tabs are its own state. A filter over one collection is a `ToggleGroup` or a Toolbar filter, never a tab. A record's tabs are the views a reader comes back to, at most about seven where the record allows (Components/Tabs): views that hold the same kind of work share one tab under Section headings (the program's POA&M & risk), and a view read rarely folds into the Overview (the program's activity).

A tab that counts its collection shows a `Count` with `max={9999}`: 0 once its rows load, and no count while they load or after the load failed. A `Section`, a `Related` card or an `Item.Group` that counts rows passes the same cap as `countMax={9999}`.

## Forms and confirmations

The create and edit surface is a `Dialog` titled with the operation and the singular product noun. The trigger, the dialog title and the primary use the same words: Create task, Create organization, Create risk. `productRecordNoun` and `productCreateLabel` in [product-records](../../src/lib/product-records.ts) own the generic vocabulary, including the party subtype. Create makes a new record; Add or Link connects an existing one. A surface has one primary: the page header's, a dialog footer's or the preview's record header's, and a collection beside others creates through a secondary (Registers). Reference: [CreateTaskDialog](../../src/components/prototype/create-task-dialog.tsx). A record without a dedicated form opens `ProductRecordDialog` over the generic `RecordEditor` in [record-editor](../../src/components/app/record-editor.tsx): its fields follow the schema, its labels come from `productFieldLabel` (Owner, not Owner party), its status choices read as their badges, a value the context fixes shows as labelled text instead of a field, and once the context sets one member of a polymorphic target group (`productTargetGroups`) the others are hidden.

`DialogContent` takes a `width` step (`medium` for a few fields, `large` for a form in two columns), never a pixel width. `DialogBody` (in a Sheet, `SheetBody`) is the one scrolling region; the form sits inside it and the footer stays outside, joined to the form through native form ownership (`form` on the submit button). In `DialogFooter`, Cancel is a `DialogClose` rendered as a subtle Button, before the operation's primary; a dialog whose choices apply as they are made (the tailoring decisions) has no draft to cancel, and its secondary is Close. A button says the operation, never OK, Submit or Save alone. Navigation styled as a button is a `LinkButton` or `LinkIconButton`, never a Button that navigates. Button and action-menu labels stay on one line. Menus size to their contents within the available viewport; a narrow trigger does not constrain its action labels.

Every control sits in a kit `Field`, which binds its label, hint and `FieldError` to the control and carries `required`, `invalid` and `disabled` to it; a form writes no ids or ARIA. The wrappers in [fields](../../src/components/app/fields.tsx) take the field's `error` and a `controlRef`: `TextField` for text, `ChoiceField` (a Select) for a fixed list of values, `ComboboxField` for a set of records, `PartyField` for a person or organization; a moment is a `DateTimeField` and a day a `DatePicker`, never a native date input. A half-typed moment blocks the submission with the field's own message, also when Enter submits from inside the field (`unsettledMoment` in form-feedback). The Field marks a required field; a placeholder never says optional. A length limit is the field's `characterLimit`: a count under the field (always under several lines, from near the limit under one) and a FieldError on submit that says how many characters fit; a form never sets `maxLength`, which cuts a paste off without a word. A choice that waits on another answer is `readOnly` with a description that says why (Choose a control first.), never `disabled`, so it keeps its Tab stop. An upload shows each file in an `Attachment` row: a labelled Progress and the bytes sent of its size while it uploads, Cancel named for the file, and Retry and Remove after a failure. Reference: [EvidenceFile](../../src/components/app/evidence-file.tsx).

The first field takes focus through `initialFocus` on the dialog or sheet content, never `autoFocus`. Focus returns to the opener on close, so the opener stays enabled and mounted while its surface is open; where it cannot, `finalFocus` names a stable element. Validate on submit with the primary enabled, then on change. Every issue marks its field with a FieldError that says what fixes it. One issue moves focus to its control; several show an `ErrorSummary` above the fields, which takes focus and leads to each control. `useFormFeedback` in [form-feedback](../../src/components/app/form-feedback.ts) holds the attempt, the summary and that focus. A result that is not about one field (a failed save, choices that did not load, an unavailable context) is an `Alert` with an explicit role at the top of the body: `role="alert"` for a failure, `role="status"` or `role="note"` for a notice. The form never writes its own `role="alert"` paragraph. A primary that truly cannot run, such as for a viewer, keeps its place and explains itself with `disabledReason`.

A dirty dismissal, a route change away from a draft and a destructive decision go through `useConfirmation` in [confirmation](../../src/components/app/confirmation.tsx) (`discardChanges` for a draft), which renders the kit `AlertDialog`; never `window.confirm`. `useDraftGuard` in [use-draft-guard](../../src/components/app/use-draft-guard.tsx) owns a form's dirty and pending state: it asks before a dirty close or route change, and `start`, `finish` and `complete` bracket the save. The prompt's safe action is Keep editing, which keeps the values and the location; an explicit discard may close or navigate. A destructive or irreversible decision (Remove allocation, Unlink evidence, Publish version) passes its command to `confirm` as `action`: the prompt stays open and pending while it runs, shows a failure inside itself with its action as the retry, and closes on success, which a toast reports. A link a reader can remove has a danger row action and the same item in its preview's overflow menu, through a command in `src/lib` ([requirement-links](../../src/lib/requirement-links.ts)); `useRemovalFocus` in record-preview then moves focus to the collection's primary. Reference: the requirement Allocation, Control mappings and Evidence tabs. A pending save sets `pending` on the Dialog or Sheet, which cancels Escape, outside dismissal and every close control; the fields sit in `FieldSet disabled`, focus moves to the primary, which shows `isLoading` and is never also `disabled`, and the guard blocks navigation. A failed save ends the pending state, keeps the draft and focus, and only then says that retrying will not duplicate the record. A form whose save must be safe to retry chooses its record id once and saves through `useSaveOnce` in [save-once](../../src/lib/save-once.ts): it creates only when the id is absent, edits only at the revision the reader saw, writes nothing when the record already holds the values, and says which conflict stopped it (another session's change, a record that is gone, different values already saved). The surface closes through its `open` state, so its exit and focus return run before the caller unmounts it. Reload and tab-close protection is the browser's `beforeunload`, never a custom dialog.

Profile control decisions and parameter overrides use Dialogs, including when they edit the program wizard’s draft. They do not extend the element Sheet exception.

The closed list of other surfaces:

- Program setup is a page wizard; its path is a `Stepper orientation="responsive"` labelled Program setup, at every width: down the page in a `StickyRail from="lg"` beside the form, never a hand-written sticky class, and above the form where Main is narrow, across where its column fits four steps and down the page where it does not; its element Sheet edits the wizard's own draft. It validates each step on Continue with FieldErrors and an ErrorSummary, each step change moves focus to the step's heading, and the element Sheet checks its row on Done, with Keep as draft.
- The diagnostic schema inspector keeps addressable `/records/:collection/new` create pages. Product workflows use the Dialog default; the inspector shares its validation, labels and draft protection.
- One supported property is an `Editable`; a filter or a reason at its button is a `Popover`.
- Choosing records is a `PickerSheet`; it may collect one shared rationale when applying a selection, with dirty and pending protection. A PickerSheet whose candidates come from queries passes `state` as its DataTable does, so its footer never says there is nothing to choose from while they load or after they fail. When its rows run past one page, choosing the page with the header's checkbox offers Select all N in the footer, and the primary applies the whole choice in one request, with an id chosen once per choice, so it is all applied or none and a retry adds only the rest. Reference: Allocate requirements in [system-requirements](../../src/components/prototype/system-requirements.tsx). A second step that authors specifications moves to a Dialog. Linking related records is a `RecordBrowser`. Their internal preview belongs to the selection task. A linking form may supply an explicit operation label so its trigger, title and submit button all say the same Link operation.
- The evidence version review is the modal preview above.
- A record's Comments section writes a comment in an inline `Composer` at the top of the section, above its newest-first `Timeline`. It posts through a command in `src/lib` ([task-comments](../../src/lib/task-comments.ts)) as the reader, keeps the draft and says why after a failure (sending it again never posts it twice), and asks before a page with an unsent draft is left, as a form does. A reader who may not comment sees the feed alone. Reference: [the task record](../../src/routes/tasks.$taskId.tsx).

Any other create or edit form is a Dialog, never a Sheet. An `AlertDialog` may open over the Dialog or Sheet that owns the decision; an independent record workflow navigates or replaces the current frame instead of stacking. Dirty and pending protection survive a change of surface.

## States and identity

Loading, errors and retry go through `QueryState` in [work-common](../../src/components/prototype/work-common.tsx), which keeps stale content usable after a failed refresh; libraries recover the same way. A record page and each retained tab panel is a failure region (`QueryState region`; `RetainedTabPanels` makes every panel one, through [failure-region](../../src/components/prototype/failure-region.ts)): each QueryState and ProductCollection inside hands its failures to the region's one alert, whose Retry refetches all of them, and a block with nothing to show keeps its place with a quiet Could not load. A strip of plain `TabsContent` wraps each panel in `QueryState region`. Reads whose values say Could not load in place (`QueryValue`) hand their failures to the region through `ReportFailures` in work-common, and `QueryState` is never drawn inside a value or a cell. The page's region also says the reads its header and Details are drawn from, the record's own first (as its `queries`, or through `ReportFailures` beside them), and a program's focused view is such a page: its blocks hand their failures to the page's one alert. Reference: [the task record](../../src/routes/tasks.$taskId.tsx), and the program sub-records in [program-record](../../src/components/prototype/program-record.tsx). A block drawn through a portal (the Details rail, a dialog, a preview panel) says its own. A related record's name in a value or a cell is `RelationName` from [record-tools](../../src/components/prototype/record-tools.tsx), never a QueryState of its own. `Empty` describes an empty region (`size="compact"` in a small one); `Absent` describes a missing scalar, heard as "Not recorded" unless a `label` says more ("Not available" for a record the reader cannot see, "No due date"). A screen never writes a dash, "Not recorded" or "Unassigned" in place of a value; a row value that feeds search and sort stays null, and its cell draws Absent. Words stay only where the value is itself a statement (No versions, Tailored out). A status, state, severity or impact renders through the components in [status](../../src/components/app/status.tsx) over the one map in [src/lib/status](../../src/lib/status.ts), and `c.status` takes the same vocabulary; a screen keeps no tone mapper of its own. Every date goes through `DateTime` or the `LedgerProvider` formatters in the reader's zone, never `toLocaleString` or a raw ISO string. A due date, an expiry or a milestone's planned date is the kit's `DateLabel`, through `DueDate` in work-common for work that can be done or cancelled: overdue, due today and due soon say so beside the date while the work is open. A due is a calendar day, never a moment: a task's and a scheduled assessment task's due, a remediation commitment's planned completion and a milestone's planned date. A form asks for it with a `DatePicker` labelled Due date, and a record's Details edits it in place with `Editable.Date` and `due`, which says the same at rest, through a command in [due-dates](../../src/lib/due-dates.ts) at revision + 1. While the work is open, a day before the reader's today reads Overdue, today Due today and the next two days Due soon; done work's day reads plainly, and only a remediation item's latest commitment is still due. An expiry (an evidence version's, an authorization's) passes `kind="expiry"`, which says Expired and Expires soon instead. A failure is never a blank table, and a load in progress is never an empty state.

A screen reads its rows scoped on the server, by program, system or the ids another read names, with the columns it shows: `useRows(table, filters, { columns })` (a list reads as PostgREST `in`; a dotted key such as `engineering_requirements.program_id` or `assessment_plan_revisions.campaign_id` joins through a reference), `programRequirementScope` in [requirement-reads](../../src/lib/requirement-reads.ts), `useSelectedControls` in [control-reads](../../src/lib/control-reads.ts), `useLibraryComponentUses` and `useComponentTraceability` in [library-reads](../../src/lib/library-reads.ts). A whole tenant-wide table is for small reference collections only; in development the console names any read that pages past 5,000 rows. A collection's schema (a column's choices, a generic form's columns, what the role may do) comes from `useCollection`, `useColumnChoices` or `useSchemaCatalog` in [collections](../../src/lib/collections.ts), for the schema inspector, the generic record forms and the previews that name their facts from it; it loads on demand, and a surface waits on it like any query: a create or edit action keeps its place while it loads, never a read-only note. A register, a record page, a tab and a Details rail never read the record schema, so every route in the screen inventory but /schema and /records/* opens with no `app_schema` read: a column's kind and label are declared on it (`kind`, `statuses`, `label`), else its key decides; a record section that links existing records names the record it links (EntitySection `links`), and its action says Link and that record. A surface that needs the schema (a create or edit Dialog, a preview, a picker) reads it as it opens and says its own failure with Retry; a preview's Edit asks the role, and the form it opens waits on the schema. Reference: EntitySection and ModelFacts in [record-tools](../../src/components/prototype/record-tools.tsx). A screen that only asks whether the reader may create, edit or remove records of a collection every member writes (systems, requirements and their revisions, allocations, control mappings, evidence links, and the records of a program collection) asks the workspace role, every member but a viewer, and row-level security decides each write. An inline choice offers the values its command accepts (`requirementTypes` in [requirement-edit](../../src/lib/requirement-edit.ts)), not the schema's. A cell or field that names another record reads the name through `useRecordName` in [record-names](../../src/lib/record-names.ts), which reads a page's names together, one request per collection. Reference data (catalog editions, profiles, CCI releases) is loaded by a workspace administrator; an empty reference collection says so and never asks the reader to import.

Focused program views retain the program name in their h1, include the focused view in the breadcrumb with the program's crumb linking back, show no tab strip, keep the Details rail, and take the program record's browser title (`<program name> — Program — Program Assurance`). The legacy risk and program dashboard URLs redirect to their canonical record.

Every route sets its browser title as `<Screen or record type> — Program Assurance` in its `head()`; a child route never inherits its parent's title. Once its record loads, a record route names it first, in the words of its h1: `<record name> — <record type> — Program Assurance`, through `useRecordTitle` in [browser-title](../../src/components/app/browser-title.ts). While the record loads, and when it is missing, the type alone stands. A screen that stands in for the route titles itself through `useBrowserTitle`: the sign-in form is `Sign in — Program Assurance`, and a workspace that cannot open is `Workspace unavailable — Program Assurance`. The root renders the one `<title>`; a screen never renders its own. Labels use the same words across program tabs, global registers, create actions and forms.

## Product vocabulary

The generic record noun is owned by `productRecordNoun`; a create or edit trigger, Dialog title and primary repeat that operation. Use these terms in columns, collection headings and labels:

| Concept           | Product terms                                                                                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Operational issue | Operational issue / Operational issues. Findings is a workspace grouping when it includes issues and observations.                                                                                |
| Assessment result | Assessment finding / Assessment findings. It is distinct from an operational issue.                                                                                                               |
| System            | System / Systems. A scope names a recorded assessment scope, not a system; old parameter names do not set UI vocabulary. Create system from product makes a new system, a product variant.        |
| Task              | Task / Tasks. My work is the personal register; Schedule is the program workspace containing tasks, lifecycle gates and responsibilities.                                                         |
| Supplier          | Suppliers is the register and navigation label; its records are organizations, so the operation is Create organization.                                                                           |
| Risk              | Risk / Risks; Risk register is the standalone collection, POA&M & risk register is the combined workspace, and POA&M & risk the program tab holding its POA&M plans, remediation items and risks. |
| Campaign          | Assessment campaign / Assessment campaigns, including the program tab and global navigation.                                                                                                      |
| Remediation       | Remediation item is the ongoing record; remediation commitment is its version. A POA&M plan groups the items.                                                                                     |
| Record lifecycle  | Status for operational progress; State for draft/published version state.                                                                                                                         |
| Due               | Due date in a form, Due in a column and in Details: a calendar day (`due_on`), never a moment. A risk response's due stays a moment.                                                              |
| Responsibility    | Owner for accountability; Sponsor, Assessor and Observer remain distinct recorded roles. Avoid Lead as a synonym for Owner.                                                                       |
| Operations        | Create makes a new identity. Edit changes it. Add or Link selects and connects existing records. Map control creates a mapping relationship; Allocate requirement records an allocation.          |

The diagnostic inspector displays database collection labels where they identify the schema. They do not replace product nouns in its forms.

## What checks it

`npm run lint` runs the Ledger rules on every application file: tokens only, no margins, logical sides (`ledger/no-non-token-class` reports `text-left`, `pl-200`, `right-0` and the other physical sides with the logical class that mirrors right to left), a page layer by name (`z-overlay`, never `z-50`), no copied kit parts, no class that changes what a kit part sets itself or reaches into the parts inside an element (`ledger/no-restyle`: write the prop it names, or the part changes), `TextLink` for links (`ledger/text-link-navigation` rejects an action element rendered by one), `ledger/no-native-confirm` and `ledger/dialog-footer-order`, the overlay and form rules `ledger/no-overlay-autofocus`, `ledger/no-disabled-while-loading`, `ledger/overlay-width-preset`, `ledger/no-plain-alert-role`, `ledger/link-button-navigation` and `ledger/no-style-design-value`, a raw `h1`–`h6` with type classes, which is a `Heading` at the size it matches or the part that draws the title (`ledger/use-heading`), and a layout rule a kit part keeps inside itself (`sticky-rail`, `shell-*`, `sticky-bar`, `min-h-work`, `grid-cols-list-detail`), which `ledger/no-non-token-class` reports with the part that owns it. `ledger/no-inline-config` reports a comment that turns a Ledger rule off, and the application keeps no disable of one; a disable that silences nothing fails the run. A custom link adapter passes when it renders an anchor and forwards props and ref; the browser checks verify the destination. The app-only rules `ledger/product-responsive-table` (a DataTable that turns `responsive` off, or leaves it to a prop spread) and `ledger/product-line-tabs` enforce the table and tab contracts, including imported aliases and overriding prop spreads; generic kit examples keep their supported variants. Lint does not read cross-file workflow semantics.

`npm run test:app` guards the application boundary and the lint scope; the package tests cover public-export discovery and composition rules. [The screen inventory](screen-inventory.json) declares every route’s family, browser title, model and closed exceptions. The application boundary test rejects an unlisted route. `test-screen-families.mjs` reads this inventory to check every product route at desktop and touch widths, including every global register’s search, name link, visible eye and panel navigation, with real named fixtures where that family can be independently seeded and missing-record checks for dependent records. Domain workflow suites supply the deeper linked-record fixtures. `npm run test:app-a11y` runs axe and the console over every inventory route at 1440px and at a 390px touch phone, plus sign-in, an open create Dialog and an open preview; its known problems per screen are in `scripts/app-a11y-allow.json`, which may only shrink.

`npm run test:patterns` drives product flows against a disposable local workspace at desktop, 390px and 340px widths (app on port 8080, or `APP_TEST_URL`). It checks that Cancel, Escape and Discard on a create or edit Dialog hand focus back to the control that opened it; tabs through the Suppliers register, its preview and the Create organization and Create task Dialogs and fails a focus ring that an ancestor cuts by half or more (the kit's focus gate, in `scripts/tests/focus-ring.mjs`); and its failed-load checks include a refresh that fails under a nested preview frame and slow choices in a Dialog's picker and in a PickerSheet (`scripts/tests/failed-loads.mjs`); the `product-patterns` CI job provisions the committed Supabase schema and pinned reference data with `supabase/setup-cli` and runs it.

Before calling a changed screen done, check it in the running app: real names and links, preview order and endpoints, a failed save, a dirty cancel, a pending dismissal, empty and filtered recovery, and actual table bounds with the panel both open and closed. On a record, check the Details disclosure at 390px: closed, under the header or the tab strip, with the state in its row. Check that the outer preview header contains global navigation only and that one inner record header contains the visible name and record actions. Verify a one-row scrollable preview tab strip, a full-width underline, hidden-field access and unchanged reader state after resizing; check the toolbar at 390px and 340px and a register with touch emulated. A scrollable table frame alone does not count as responsive. The Storybook tests cover the kit, not these compositions.
