# Product pattern contract

The application's composition guide. Read it before creating or changing a screen. Ledger's Storybook documents what each part does; this guide decides which part this application uses for each shape, names the exceptions, and points at the file to copy. Do not infer a shape from a neighbouring screen, and do not keep a second copy of these rules anywhere else. A screen that needs a shape this guide does not cover gets a written recommendation (kit part or bespoke) before it is built. When a rule changes, change this guide and its reference file together.

## Registers

Every register, record page and dashboard starts with `Page` from [the app shell](../../src/components/app/shell.tsx): its `PageHeader`, then its body, `space.200` apart, kept inside Main (`min-w-0`) and rising in once as the page opens; a loading or missing-record state inside it takes the same `Page` without rising again. A screen never builds its own root `Stack`.

A standalone register is one `PageHeader` with the name in `PageHeader.Heading` / `PageHeader.Title`, followed by a frameless `DataTable` with `fill`. Nothing else: no sentence under the title, no `Section` around the only table, no create button in the page header (the toolbar carries it). Reference: [WorkTable](../../src/components/prototype/work-table.tsx). All product collections compose [ProductCollection](../../src/components/prototype/product-collection.tsx); domain adapters retain their typed columns and relationships, and delegate the toolbar, query recovery, responsive table and empty region to it. Pass the collection's queries as `queries` rather than wrapping it in `QueryState`: a first load keeps the toolbar over skeleton rows, a failed refresh keeps the rows under one alert with Retry, and a page, search or filter on its way over the last one's rows (a query that keeps its previous data) keeps them under the table's busy state. ProductCollection draws `DataTable.Sort` and keeps the reader's question (search, sort, filters, page) in the address, its parameters named after the table's `view` (`risk-register.q`, `risk-register.filters`), so Back, a reload and a shared link ask it again and two collections on one page keep their own. The tab's session remembers it too, so a register reached with no question in the address asks the last one it asked and writes it back. A link that opens a register on a question builds its search with `questionSearch` from [collection-question](../../src/components/prototype/collection-question.ts), naming a view from [register-views](../../src/lib/register-views.ts), and a route's own navigation (a tab change) merges over the current search rather than replacing it. A collection inside a dialog, sheet or picker passes `keepQuestion={false}`, since its question ends with the task and stays out of the address, and one whose order is its meaning passes `sort={false}`. A read-only review table inside a Dialog (Take version's changes, Add from library's claims) is a `compact` ProductCollection with `sort={false}` and `keepQuestion={false}`, over a table whose `pinnable` and `hideable` are off and whose columns are not `sortable`: search only, in the order the review lists, with no Sort, Columns, Settings, column menu or sorting heading. Reference: the changes table in [library-update-review](../../src/components/prototype/library-update-review.tsx).

The toolbar is the kit `Toolbar`: search first, saved views in `views`, filters in `filters` with the count of applied filters in `activeFilters` (`table.state.columnFilters.length`, which ProductCollection passes), Columns and Settings as its children, and one small primary in `actions`. A register, and a tab whose only content is a collection, keeps that small primary. In a record body or a preview that holds collections under Section headings, each collection's create action is a small secondary, and the page header or the preview's record header keeps the surface's one primary: ProductCollection draws a `compact` collection's create action, in its toolbar and its empty state, as a secondary unsaid (`actionVariant`), and a headed EntitySection, a `section` ProgramCollection and a compact AssessmentTable are compact. A create drawn where ProductCollection cannot reach it, such as a menu trigger's `render`, is written `variant="secondary"`. Reference: the program's Schedule tab in [program-workspace](../../src/components/prototype/program-workspace.tsx). The search says Find and the collection, as its placeholder and its name (Find risks, Find assessment findings); ProductCollection writes it from the collection's noun when the caller names none. A compact collection in a preview whose task asks nothing of a search (an evidence artifact's Versions) passes `search={false}` and keeps its create action. Optional collection commands such as Export belong in the labelled Collection actions overflow beside Columns and Settings. This is the recommended home for secondary collection operations: the primary still creates the record, and export remains available without a second visible toolbar action. Because Columns, Settings and the Collection actions overflow are children, they fold into More after the filters when the row runs out of room, and a folded More says how many filters apply; the search, the saved views and the one primary never fold, and on a phone the kit keeps the toolbar to two rows, a third only when More and a long primary cannot share a line (Patterns/Toolbar, Phone). Row actions, the eye and a header's column menu are always shown on a touch screen, and pinned columns give way while they would take most of a narrow frame. When a collection has a second way to create its record, the primary is a `ButtonGroup`: the one create action, then a labelled icon menu for the other paths ("More ways to create a system" in [ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx)); a single path stays a plain small primary. Among other collections under Section headings the same group is drawn in secondaries, written so on both halves, since ProductCollection cannot reach into a group: ProgramCollection takes the other paths as `createMenu` and draws the group in its toolbar and in its empty state. Reference: a gate's Gate criteria in [program-shared](../../src/components/prototype/program-shared.tsx), whose Create gate criterion is followed by "More ways to create a gate criterion" holding Add security outcomes. Omit a capability the collection or the reader's role has no use for. Never rebuild the row with an `Inline` or a second wrapper.

A register whose records a reader acts on several at once is `selectable`, for a reader who may edit, and hands its verbs to ProductCollection as `selection`: while rows are chosen the table's `DataTable.SelectionBar` takes the toolbar's place with the count, the verbs as small Buttons and Clear, so the rows stay where they were. The checkbox alone chooses a row; its name and its row click still open it. The verbs act on every chosen row, the ones on other pages too. On a server-paged register, once the page is chosen and the question finds more, the bar offers the whole result as a second, explicit step (Select all 62 risks), read through `useServerResult`. A viewer sees no checkbox and no verb. The one verb so far is Assign owner, `useOwnerAssignment` in [assign-owner](../../src/components/prototype/assign-owner.tsx): a Dialog titled Assign owner with one required Owner field, a person or an organization, which says how many records are chosen and that the owner replaces any they have now. It applies in one request, `assign_record_owner` through [owner-assign](../../src/lib/owner-assign.ts): every chosen record takes the owner or none does, and a record that already holds it is left as it is, so sending it again changes nothing. A toast says how many took it, the selection clears and focus goes to the table's select-all. A register that assigns owners draws an Owner column (`c.person`) and an Owner filter, the last of its filters, whose values are every person and organization by name and then No owner with how many records of the whole register nobody owns (`useOwnerOptions`), so they are one choice away; it adds no saved view for them, which would take the filters' place in the row. Its read reaches the column by the owner's name (`ownerField`). Reference: the risk register in [assurance-views](../../src/components/prototype/assurance-views.tsx); operational issues, evidence and a program's Requirements do the same. A requirement's owner is on its details, which take it at their next revision, and each change is an entry of the requirement's edit history, as an edit of its owner is; a requirement whose details are not recorded takes no owner, so its row cannot be chosen and Select all leaves it out. A program tab's own collection of owned records takes the verb, the column and the filter through ProgramCollection's `assignOwner`, with an Owner column among its columns (`owner_party_id`, `kind: "person"`, whose names it reads once): the operational issues on Findings, and the remediation items and the risks on POA&M & risk; its Evidence is the evidence register's own. Such a collection holds its records whole, so No owner counts them all and Select all is the table's own. Reference: the POA&M & risk tab in [program-workspace](../../src/components/prototype/program-workspace.tsx).

Columns come from `defineColumns` by kind. A date is `c.date` with the raw value at its kind's width; formatting never becomes the sort value. A person (an owner, a sponsor, a reviewer) is `c.person`, or `kind: "person"` on a ModelTable, EntitySection or ProgramCollection column, which reads the people's names once and sorts, filters and searches by them; several values in one cell (assignees, types) are a `c.list`, or `items` on a ProgramCollection column, whose filter lists each value once, never an array joined into a text column. The record's name is a `TextLink` rendering a router `Link` to its record page, through `RecordLink` in [record-preview](../../src/components/prototype/record-preview.tsx); in a table the kit draws a row's name in the text colour at medium weight, underlined under the pointer, whether it is a link or a button that opens a preview, so a register's colour stays with its statuses and a screen adds no colour or weight to a name; a record with no stored name links as "Unnamed <noun>", never as a missing value. A name never leads into the schema inspector: `recordDestination` gives a record's page, or nothing. A record with no page of its own (an observation, an organization, a CCI, a procedure, an ATT&CK technique, a link row) is named by a link-styled `Button` that opens its preview, and its row click does the same. `RecordLink` draws that button itself: it opens the collection's own preview where the caller passes `onPreview` (ModelTable, AssessmentTable and ProgramCollection do it unsaid), and otherwise the record's preview alone, `LinkedRecordPreview` in [linked-record-preview](../../src/components/prototype/linked-record-preview.tsx), in the panel beside the page or as a frame over the preview the name sits in. Such a preview offers no fuller record, and ends with the page or the tab its name sat in. A framework item's preview is named for what the item is (Security outcome preview, Life cycle process preview) and shows the items that hold it by name, each under what it is to the item (a security outcome's Process and Group, an approach's Technique), an approach's Architectural layers (the layers Table D-5 says it can be used at, in the table's order, `ApproachLayers` in [control-resiliency](../../src/components/prototype/control-resiliency.tsx)), then Printed in and its Framework by title; what the publication prints of it is a labelled `Prose`, Definition where it defines the item and Description elsewhere, then what it prints beside that: a goal's, an objective's, a technique's or an approach's Discussion and an approach's Examples, a list in the printed order, read through `itemGuidance` in [frameworks](../../src/lib/frameworks.ts), and an item with neither shows neither. An item ATT&CK identifies is titled by its identifier and name together. The words for each kind are `frameworkItemWords` in [product-records](../../src/lib/product-records.ts). Inside a Dialog or a Sheet, where no preview can open beside the task, the name is plain text. A row click goes where the name goes, through `useOpenRecord`. A revision opens the record it is a version of: an evidence version its artifact at that version, a risk assessment its risk's Assessments. Reference: the Observations tab in [observations-register](../../src/components/prototype/observations-register.tsx), and the Controls tab in [ssp-assembly](../../src/components/prototype/ssp-assembly.tsx), where a selected control with no implementation opens its preview and a control is named by its code and title together in its one identity cell, since control titles repeat across families. A name that needs the record's kind, a mark or a second line takes `icon`, `badge` and `description` on its column (Ledger's `Table.Name`), never an `Inline` or a `Stack` in `cell`. In a cell that cuts it, a name ends in an ellipsis and shows whole on hover, on keyboard focus and on a long press. The primary name (`priority: 0`) names its row: DataTable draws its cell as the row header and names every row control after its text (Select, Row actions for, Preview, Show N more fields for); pass `rowLabel` only when a reader knows the row by other words, such as its code in a picker. A row click follows the name's destination and is never the only opener. When a join row's visible name is another record (an allocation names its system, an issue's observation the observation), the name is that record's own link, the row click opens it and the eye previews the join row; an EntitySection that names the record it links (`links`) does it unsaid, and reads the linked records' names once for the table, so the rows sort, search and export by the name and every row control says it (Preview Signature test report), never the link's id. A collection with a preview passes `preview: { onPreview, activeId }` to `useDataTable`, memoized on the shown record's id, which draws the eye at the end of the row's first value, a column of any kind (the name, when it leads the row); the columns stay at module level, or memoized on what they read, so stepping through the preview never rebuilds them. The eye remains visible on devices without hover and stays keyboard accessible. A gate's criteria say where each came from in a Source column: the life cycle process the criterion was drawn from, read once from the register's view (`gate_criterion_rows`, through `useGateCriterionSources` in [gate-criteria](../../src/lib/gate-criteria.ts)) and handed to ProgramCollection as `queries`, so the collection waits on it and the rows sort, search and export by the process's name. A criterion somebody wrote draws Absent. Buttons act; links navigate.

A tab whose only content is a collection starts with its toolbar and table. The tab already names the collection: do not repeat its heading or put explanatory prose above it. Multiple distinct collections in a record body use `Section` headings, h2, or h3 under a dialog title; never a second page h1. A title no kit part draws is a `Heading` at the size it matches (`page` for a page or record title, `section` for a section's, `overlay` inside an overlay), never a raw `h1`–`h6` with type classes. Authored descriptions belong in labelled record properties. A Section's description is an instruction or an authored definition, never a computed sentence: a count is the Section's `count` (`countMax={9999}` for rows), and progress is a labelled `Progress` whose value says the count (Gates completed, 14 of 19), as on the Lifecycle timeline in [program-timeline](../../src/components/prototype/program-timeline.tsx). A program's control baseline is the exception that is shown: how it is formed is a `BaselineStackTable` from [baseline-stack](../../src/components/prototype/baseline-stack.tsx), the kit `Table` as an ordered definition list, one line a row and numbers only (the reference baseline, a second one combined with it where the program starts from two, each overlay and the tailoring in the order they apply, how many controls each added and removed, how many parameters it sets values for and the running count; no description or second line in a cell), on the program's Overview, in its focused Control baseline view and under each chosen baseline in program setup; its order is its meaning, so it has no search or sort. Other provenance, counts and derivation belong in a collapsed Details section; genuine warnings, missing prerequisites and instructions inside a picker or form remain visible where they affect the task. A shared adapter carries table and data rules only, never a copy of a kit part; headings are an explicit decision of the caller (`Section`, `showHeading`, or `section` for a domain collection), and default to absent; a new adapter needs a domain responsibility beyond renaming the table's props.

Record collections use `DataTable` even when embedded: component Structure and Program uses, product Variants, and requirement Adopted by follow this shape. Three named uses keep the kit `Table`: component/product version history selects the current version with an explicit button, a profile's Source imports describes its ordered lineage and selection rules, and a control's Cyber resiliency lists the techniques it supports in the order Table E-1 prints them, strongest first, one line a technique with its approaches, each row opening in place onto NIST's guidance for them. A fourth is the Layers take of the program's Cyber resiliency view, techniques by baseline layer with a number and a `Tally` a cell, in the framework's order and the stack's. These are version-selection, definition and derivation lists, not collection previews. Preserve their meaningful order; do not add search, sorting or an eye merely to resemble a register. This exception depends on the task, not an assumed small row count. A system preview's Contains card, the elements inside a system, is a `Related` list (`layout="list"`, compact): each row is its code and name with its kind as the subtle meta, and opens that element's preview. It summarizes what is inside rather than being a collection to work through, so it has no search, sort, eye or trailing count. Reference: [system-assurance-details](../../src/components/prototype/system-assurance-details.tsx).

Every product DataTable is responsive, which is the DataTable's default: product code never writes `responsive={false}`, and a DataTable that takes a prop spread writes `responsive` after it. The shared renderer measures its actual container, including space lost to an Aside or Panel, and retains the primary identity and row actions while moving lower-priority fields into each row's More fields disclosure, a labelled count ("+3", named Show 3 more fields for REQ-001). Give the primary name `priority: 0` and a readable width/minimum (usually 180–220px); lower numbers stay in the row longer. No field disappears: resize must not change stored column visibility, filters, sorting, selection, preview state or export. Do not solve narrow tables with a page overflow rule or a smaller font. Reference: [ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx).

A collection that pages takes 25 rows a page through `useCollectionTable` in [collection-question](../../src/components/prototype/collection-question.ts) (ModelTable, EntitySection and ProgramCollection do it unsaid), and another `pageSize` only where its task needs one. One that can hold more than about 200 rows pages or sets `virtualize` on its table, in a dialog, a sheet or a picker as on a page. Never draw every row at once.

A register whose collection can hold thousands of rows reads one page from the server: the catalog's Controls and CCIs, a program's Requirements, the risk register, operational issues, observations, assessment findings, system assets, Unrolled findings, evidence and the task registers (My work, a program's and a workstream's tasks). It is `useServerCollection` in [collection-question](../../src/components/prototype/collection-question.ts) over a `serverRead` from [server-table](../../src/lib/server-table.ts), spread into ProductCollection (`<ProductCollection {...collection} />`). The server pages, sorts, filters and searches the question ProductCollection keeps in the address, and counts the whole result in the same request; the first read asks the address's question, else the one the tab's session remembers. A new search, sort or filter asks from the first page, a search being typed is asked once the typing pauses, and another scope (an edition, a program) opens on its first page. Its states are ProductCollection's: the page the reader had stays under the busy state while the next one loads, and under the one alert with Retry when it fails. Its saved views count the whole register (`useServerPresetCounts`), its filters pass their values as `options` (`vocabularyOptions` for a status), since one page's rows are not every value there is, and its Export reads the whole result (`useServerResult`), never the page. A collection that stays small, a record's own collection under a few hundred rows, keeps client paging. Reference: the catalog's CCIs in [catalog](../../src/routes/catalog.tsx).

The read names the columns its screen draws, and a read whose preview edits the record also names every column the record's form edits: the form starts from the row it is given, and saves a column it was not given as empty. A column the register derives (a family, a latest severity, an allocation state) comes from the register's view, `<register>_rows` with `security_invoker = true`, never from joins on screen, and the read names in `models` each table the view derives from (a risk's latest severity reads `risk_revisions`), so a write to one reads the page again. A column that sorts in another order than its value's names the view's sort column: `code_order` orders AC-2 before AC-10, and a status sorts by its `_rank` column, in the product vocabulary's order. The server places a sorted column's empty values as a table does: last ascending, first descending. A tree register pages top-down: its view orders each part right after the row that holds it, a page nests the parts it holds under the rows above them, and a part whose parent is on an earlier page leads its page; an order the reader chooses lists every row on its own. Reference: the program's Requirements in [requirements-table](../../src/components/prototype/requirements-table.tsx).

Every empty collection supplies an illustration, a title, a one-line explanation and the same create action as its toolbar, under the same role check. A filtered result with nothing in it uses the table's built-in Clear filters unless the collection needs different copy. Empty data and an empty filter result are different states.

## Collection previews

The eye opens a `Shell.Panel` with two distinct headers. The outer preview header contains only global preview navigation: Back when a nested frame is open, previous/next, the full-record link and Close. Back is `Shell.Panel.Back`, the header's first child: an arrow that leads the bar, set apart from previous/next and Close at its end. The panel's name is the record type and "preview" in sentence case (Operational issue preview), which Close and the splitter repeat (Close Operational issue preview). The outer header never shows the record name and holds no record actions. The collection stays mounted, so filters, sort, selection and drafts survive preview navigation. A preview belongs to the tab its collection sits in: choosing another tab ends it, and coming back shows the collection as it was without reopening the preview or moving focus (a collection in a retained tab panel calls `useEndOnHide` from [record-preview](../../src/components/prototype/record-preview.tsx) with the setter that closes its preview). `RecordPreviewProvider` owns one panel across registers; `RecordPreviewPanel` replaces a nested record frame while keeping its parent mounted for Back. Shell owns the panel's placement at every width.

Close and Escape end the whole preview from any frame, and focus returns to the shown record's eye in the collection, else to the control the reader last used there. Back is the only way to leave one frame: it shows the parent frame as it was and returns focus to the control in it that opened the nested one. Opening a preview or a nested frame moves focus to the panel at every width, so the next Tab reaches its navigation. A tooltip open on a header control takes the first Escape and the preview the second. A modifier or middle click on a row opens the name's destination in a new tab and leaves the preview and the collection as they are.

Every collection preview passes `RecordPreviewActions` from [record-preview](../../src/components/prototype/record-preview.tsx) to `RecordPreviewPanel.navigation`: it renders the kit `PreviewNavigation` with previous, next, the announced record and position and, where the record has a page, a real open-in-new-tab link to it; a record with no page of its own has no such link, and never one to its schema record. Feed it the table's displayed rows from `useDisplayedRecords`: every row the current search, filters, sort and tree state leave, across all pages, so the position counts the whole result ("REQ-001 Access control, 21 of 62 records") and a row that has left the displayed order is shown as outside the results. When a step crosses a page, the table turns to the page that holds the shown record, and every step brings the marked row into view; turning the page by hand leaves the preview where it is. The table keeps its page only while its rows and columns keep their identity, so memoize what the collection passes. A server-paged register's displayed rows are its page, and carry the page's place in the server's count: the position is the page's offset plus the row's place on it, out of the whole result, and the endpoint is the server's count. A step past the page's edge turns the table's page, waits for it and shows its first or last row, and a step onto a page read before waits for that page as it is now. A page turned by hand leaves the preview at its place, and its next step turns back. A record missing from the page that should hold it, such as one an edit in the preview moved, is counted where the server places it now (`useServerPosition` in [server-table](../../src/lib/server-table.ts)), and its steps go on from there; once the question no longer finds it, it is outside the results. Pass the array `useDisplayedRecords` returns as it is, never a copy. A fact the register derives from another record's name (a risk's owner) reads that record by its id in the preview (`RelationName`), so the preview's own Edit shows the change at once. Previous and next change the frame's content, never the frame: key the content by its record, not the component that renders `RecordPreviewPanel`, so focus stays on the control the reader pressed. At an endpoint the control the reader used stays focused and says it is unavailable, and Escape still closes the preview. The status names the record from the frame's title; pass `recordLabel` when the title draws no plain words. The kit control takes callbacks, availability, position and a caller-supplied link; the application composition owns row order and destinations; Shell owns placement. Neither the kit nor Shell imports application routing. Reference: the requirement preview in [requirements-table](../../src/components/prototype/requirements-table.tsx).

The body starts with one inner record `PageHeader`: the record's name is its h2 title, and its domain actions belong in `PageHeader.Actions`. `RecordPreviewPanel` supplies this header from `title` and `recordActions`; consumers do not render a second copy. Use one small primary (Edit system) and, when there is more than one action, an overflow `DropdownMenu` behind a subtle icon button for the rest. Keep the title readable as the inner header reflows at narrow widths. Status, owner, dates, identifiers and editors are labelled properties below it. Do not add a separate body action row or repeat the full-record link at the bottom; a property repeats the name only to edit it. A collection with no domain-specific preview uses `RecordSummaryPreview` in [record-summary-preview](../../src/components/prototype/record-summary-preview.tsx), which requires the `fields` the reader asks for, never every column. It labels a fact in the product's words where the column has them (`productColumnLabel` in [product-records](../../src/lib/product-records.ts)) and names a related record through the foreign key its field belongs to, alone or in a composite key; a record of another schema (an account, a stored file) reads Not available, never its id. Long authored text (a description, a provenance, a rationale) is a labelled `Prose`, not a truncated value. Reference: [the system preview in ProgramSystemsTree](../../src/components/prototype/program-systems-tree.tsx).

The one modal preview is the evidence artifact's version review, where the task must hold focus: a `PreviewSheet` with global navigation in its outer header, identity and record actions in its inner record header, labelled properties below, and a real full-record destination. A preview inside `PickerSheet` or `RecordBrowser` belongs to the selection task and never becomes a second record workflow. `RecordPreviewPanel.navigation` is required. A panel for a task that is not a collection explicitly passes no collection navigation and names the task in its label; its record identity still belongs in the inner header.

## App navigation

The app uses `Shell collapsedSideNav="icons"`: minimizing the desktop navigation keeps a compact rail of destination icons and the account avatar. Keep the active destination visible, give every top-level destination an icon, and expose its label on hover and keyboard focus. The schema inspector is not a destination: Settings opens it, under Diagnostics, and a record's Actions menu opens its own schema record. The app mark stays in place; in the minimized header, the expand control appears over that mark on hover or keyboard focus, and shows there at rest on a screen without hover (a tablet in landscape). Expanding restores the labels and the reader's chosen width; the preference survives a reload. The desktop sidebar smoothly changes width in both directions; the phone overlay slides in and out with its scrim. Closing content stops accepting input immediately, and reversing an animation continues from its current position. Use Ledger's motion tokens and honor reduced motion; restoring the saved layout does not animate. Reference: [the app shell](../../src/components/app/shell.tsx). The Shell icon-rail story and the responsive app workflow check this behavior.

The top nav holds the app mark, Search and actions, and the end actions. `Shell.TopNav.Search` opens the shared `CommandPalette` over matching records, saved views, personal destinations and registered page commands; ⌘K opens the same launcher. Record results include source context and excerpts; commands keep their existing handlers and disabled explanations. End actions are `Shell.TopNav.Item`s, so the top nav folds them on a narrow screen. The account is a menu in the side nav's footer, with Sign out last. `Shell locationKey` takes the resolved pathname, so a page change moves focus to Main and announces the page, and choosing a search result hands focus to the new page.

Sign-in, the workspace and the session end follow [workspace](../../src/components/app/workspace.tsx). The sign-in form stays up while it is pending and says what fixes a failure beside its field. While the workspace opens there is a loading screen; when it cannot open, the screen is Workspace unavailable with Retry and Sign out. Sign out first asks every open draft, as a route change does. A session that ends on its own keeps the page, its drafts and its place behind a Sign in again prompt; signing in again as the same person carries on.

## Record pages

One page-level h1 names the record. The breadcrumb goes in `PageHeader.Lead` as a `RecordTrail` of `TrailLink`s from [record-trail](../../src/components/prototype/record-trail.tsx), which matches exactly and marks only its last level current. A record inside a program (a requirement, a control, a component, a system) is trailed Programs › the program › the program tab that lists it › any element that contains it: [program-record](../../src/components/prototype/program-record.tsx) draws it for the system, component and control records, and [requirement-record](../../src/components/prototype/requirement-record.tsx) for a requirement. The name goes in `PageHeader.Title`, and one primary action or the Actions menu, `RecordActions` in [work-common](../../src/components/prototype/work-common.tsx), in `PageHeader.Actions`: the edit first, the record's other commands as its children, and Inspect record (the schema record) last. A viewer keeps the menu with Inspect record alone. A code goes in the trail or in Details, never in place of the name. The header has no back-chevron row, sentence description, status badge, property editor or second action row. Reference: [the task record](../../src/routes/tasks.$taskId.tsx).

State, owner, identifiers and dates sit in an `Inspector` group named Details, in a `Shell.Aside` named after the record type, `<Record type> details` (Task details, System details, Program details), whose `summary` is the record's `StatusBadge` where the record has a status or a state. The Aside is the `aside` of an `AsideLayout` around the body it belongs to: everything after the PageHeader (and its error alert) on a record without tabs, and the content of Overview's panel on a tabbed record, so the header and the tab strip span the page on every tab and the Details leave with Overview. Where the layout leaves the body room, the Details are the rail at the body's end, under the tab strip, staying in view as the page scrolls; narrower (a phone, a narrow window, beside an open panel or a widened side nav) they are a closed Details disclosure above the body whose row carries the state, so state, priority and due are one tap from the top and the collections keep their place. A `Shell.Aside` is never rendered outside an `AsideLayout`. ## Chain records

A control, a requirement, an evidence artifact, an assessment finding, an operational issue, a risk and a remediation item sit on one chain: a control is met by requirements, a requirement is supported by evidence, an assessor's finding judges a control and cites the evidence it examined, an issue cites evidence, names the requirement it is about or is what a finding became, a risk rests on an issue or was raised by a finding, and a remediation item answers an issue or a risk its commitment cites. Each of the seven records opens with the same band, `TraceBand` in [assurance-trace](../../src/components/prototype/assurance-trace.tsx): a `Stat.Grid frame="band"` of up to four numbers that say where the record stands (its severity, what it rests on or reaches, how its remediation's milestones stand), then a Section named Trace holding Ledger's `Trace`. The numbers are the record's own, and the page names its kind (`kind`) so their labels hold their place while the trace loads: a requirement's are the controls it meets, its evidence and how much of it a reviewer accepted, and the open issues that name it or cite that evidence and the risks they lead to; a remediation item's are its milestones reached and its planned day, the open issues it answers, the open risks and the controls it reaches; an assessment finding's are its determination (with the day it was made, or Draft results), the controls it judges by code, the open risks it led to and how the remediation answering them stands; a control's are the requirements that map it and how many of them cite evidence, the findings of published results short of satisfied on its parts, out of all its findings and in the worst one's tone, and its open issues and risks. The trace draws the seven stages in order (Controls, Requirements, Evidence, Assessment findings, Operational issues, Risks, Remediation) with the record itself current, every record a link to its page, and a stage the record does not reach saying so (No evidence cited, No assessment finding, No risk recorded): the gap is part of what the page shows, and a link that passes it is drawn through it. A finding says its determination in its tone and words; a walk reaches findings of published results only, since an assessor's draft decides nothing, and a finding of draft results stands in its own trace alone. A gap the reader can close from the record carries its fix under those words, the stage's `action`: a small link that says the step and leads to where it is made, for a reader who may make it, or, for a fix made on the control itself, a link-styled button in the same words that opens it over the page (`NextStep` in [next-step](../../src/components/prototype/next-step.tsx)). A control read in a program offers Map a requirement where none maps it, which opens the picker of the program's requirements on the control's page (one whose requirements map some of its objectives holds them in the stage, which offers nothing, and its Details' Next step maps the rest); where its requirements cite no evidence, Link evidence to the first of them by code (that requirement's Evidence tab); and, where no assessor has determined that evidence, Add to assessment campaign in its Assessment findings stage, the picker of the program's open campaigns with a draft plan, or Plan an assessment where none has one, the form that plans a campaign around the control. A control whose evidence an open campaign's plan holds already is under way: the stage names it instead, Open assessment campaign (its Execution tab), shown to every reader. A requirement offers Map control and Link evidence on its own tabs; an operational issue that names no requirement offers Link requirement, which opens the issue's own Link requirement (its address asks for it, `link=requirement`), since the link is the issue's. A control the program's product variants inherit with a determination (the control status's `determinedBy` is the product) is not missing a requirement: its empty Requirements stage offers none and names the product assessment that decided it instead, a link to it in the stage's words (Decided by X800 Missile version 2 product assessment), shown to every reader. A stage with nothing wrong in it (No operational issue, No risk recorded) offers nothing, and otherwise a record further down the chain closes nothing upstream from its own page: evidence, a finding, a risk and a remediation item offer nothing. The fixes are derived in [next-steps](../../src/lib/next-steps.ts) (`traceGapFixes`, given the control's standing from `program_control_status` and what the program's open campaigns hold of it, `useControlAssessment` in [control-assessment](../../src/lib/control-assessment.ts)) and drawn by `NextStep` in [next-step](../../src/components/prototype/next-step.tsx). The band spans the page: it comes after the PageHeader, inside Overview's panel on a tabbed record, and before the `AsideLayout` that holds the body and the Details. It has no prose of its own. Its numbers hold their place while the trace loads, wait while another record's trace replaces the one drawn, and say Could not load when the read fails, under the page's one alert with Retry, as a dashboard's tiles do; a number never reads as zero because it could not be read. ## Dashboards

A dashboard says what needs attention across registers and leaves the work to them. It is one `PageHeader` that holds only the name, a Stat band, then its widgets in the page's own columns: the chart and top-N widgets take two thirds and the activity feed one third while Main has room (an `@container` grid, never the viewport), and they stack in one column when a panel or a phone narrows it. Reference: [the Portfolio](../../src/routes/index.tsx).

The Stat band is one `Stat.Grid frame="band"`, a named group of up to four linked `Stat.Tile`s. Each tile counts one thing a reader acts on (open risks, open operational issues), its note names the part to look at first ("12 high or critical"; on Open risks, "41 without an owner", or "All have an owner", since the matrix and Highest open risks under the band say their severity), and its `link` opens the register it counts on the tile's question, through `questionSearch`: a tile that counts part of a register carries its filter, and one that counts the whole register clears the filters (`{ filters: [] }`), so it opens what it counts whatever the register last asked. The value is the number itself, which the tile writes in the reader's locale and mutes at zero. `isLoading` holds its place while it loads; a count that cannot load is `Absent` with a "Could not load" note, under one alert with Retry above the band. A linked tile holds no other control.

A chart widget is a `Chart` frame. Its title says what it counts and how it splits it (Open risks by likelihood and impact), a heading at the widgets' level (`titleLevel`), its description says what the plot leaves out (open risks not yet assessed), and its table twin is one toggle away. It loads as the plot's skeleton. A failure is one alert with Retry above it (`QueryState`), as on the other widgets: a failed refresh keeps the plot, and a failed first load says Could not load in the plot's place. ## Tabs

Every product page and preview uses a named `TabsList variant="line"`. Its underline spans the content width, up to a panel boundary. The selected indicator slides to the next tab and the new panel enters with a short fade and movement on Ledger motion tokens; reduced motion switches immediately. Only the selected panel occupies the layout, and retained panel state survives selection. `RetainedTabPanels` in [program-shared](../../src/components/prototype/program-shared.tsx) draws a panel once it is first shown, so its reads start then, and leaves a hidden panel as it was drawn: the record re-rendering re-renders only the panel the reader sees. The kit owns the horizontal `ScrollArea` and `ScrollBar`: tabs stay in one row and the strip scrolls when it is narrower than its labels, in a desktop preview and on a phone alike. Do not add `flex-wrap`, a width class or an overflow class to `TabsList`. `TabsContent` starts the panel `space.150` under a horizontal strip, so a screen adds no space between the strip and its panel: no `pt-*` on `TabsContent` or on a panel's first block, no `gap-*` on `Tabs`, and no `contents` on either. Arrow keys reveal the focused tab without scrolling the page.

A record page's tabs live in the address: choosing one pushes a history entry, so Back returns to the tab before, and an address that names no tab shows the first. Where the address owns the tab, it is the only owner; the component keeps no copy of its own. A record's tab holds no second strip: the collections it holds sit under Section headings, each compact with a small secondary create action, as on the program's Assessment campaigns (Campaigns, Events, Scopes, then Objectives, the longest, last), Schedule and POA&M & risk. A campaign's event count there filters the Events section to that campaign, brings it into view and moves focus to it. A preview's tabs are its own state. A filter over one collection is a `ToggleGroup` or a Toolbar filter, never a tab. A register page that holds more than one collection draws them as line tabs under its one h1, each a register that keeps its question while another is shown, and the address keeps the tab: Findings & assets, and Assessment campaigns (`assessmentTab`), the same collections across every program. Reference: `AssessmentBrowser` in [assessment-browser](../../src/components/prototype/assessment-browser.tsx), whose `layout` is `tabs` on the page and `sections` in a program. A record's tabs are the views a reader comes back to, at most about seven where the record allows (Components/Tabs): views that hold the same kind of work share one tab under Section headings (the program's POA&M & risk), and a view read rarely folds into the Overview (the program's activity).

A tab that counts its collection shows a `Count` with `max={9999}`: 0 once its rows load, and no count while they load or after the load failed. A `Section`, a `Related` card or an `Item.Group` that counts rows passes the same cap as `countMax={9999}`.

## Workbooks

A program workbook is a dedicated working surface for requirements, traceability mappings and analytical sheets. Its grid uses Ledger's Spreadsheet pattern, with a formula/name bar, worksheet navigation, selection, typed editing and a bounded scrolling viewport. It is a separate interaction family from the responsive DataTable registers. The existing registers retain their navigation and preview contracts; their collection actions link to the workbook. The workbook keeps record drill-through and the shared record preview, including at 390px. Its compact toolbar groups editing, column sizing, filtering, sorting, view selection, formatting and workbook commands directly above the formula bar. Review and Save stay in the workbook header. The toolbar scrolls horizontally with visible overflow arrows on narrow screens, independently of the two-dimensional cell viewport; keyboard focus reveals each control. Column-header menus expose sizing, sorting, filtering and, on analysis sheets, insertion and deletion. Cell, row and column context menus use the clicked target and preserve an existing range when invoked inside it. A single worksheet strip exposes the sheet picker, per-sheet actions, dimensions and add controls. Letter-only headings avoid repeating field names from row one. Hidden axes retain canonical addresses, and analysis comments, dropdown rules, formatting and sheet order persist with the analysis document. Row boundaries support dragging, fit-to-content and automatic sizing; wrapped text and larger fonts grow automatic rows, while fixed rows clip their content. Vertical alignment controls placement in tall rows. Visual styles on source cells persist by stable row/column identity, separately from canonical values and field types. Source structures remain managed by their record workflows; duplicating a source creates an independent analysis copy. Filtering and sorting use displayed values without changing canonical cell addresses. Every cell remains keyboard reachable.

Record-backed sheets bind cells to immutable record and field identities. Sorting and filtering change presentation only. Authored requirement fields and permitted mapping fields enter a local changeset; derived fields and relationship identities stay read-only. Completing a cell edit, including clicking away, only stages that edit. Narrative fields preserve line breaks, and owner pickers, cell display, filtering and sorting use consistent human-readable labels. A review Dialog names every affected record and field, shows before/after values and validation errors, and applies the changes through one revision-checked, idempotent server transaction. A failed or uncertain save retains its request identity and draft. Undo before applying affects the local changeset; a persisted reversal is a new audited edit. Formula results never silently become authoritative assurance facts.

The application owns typed field definitions, source queries, permission checks, relationship pickers and persistence. Ledger owns neutral cell interactions, command scopes and change presentation. The spreadsheet core owns workbook operations, calculation and interchange, with no dependency on application records or UI. Analytical sheets may reference the complete bounded source snapshot; the workbook identifies that snapshot and refuses partial results rather than presenting a current page as a complete program. Refreshing source data must preserve or explicitly resolve outstanding edits. Workbook layout and analytical content persist separately from canonical requirement and mapping records.

Commands are registered once per active scope and reused by buttons, menus and the workbook command palette. Text composition and an active cell editor retain their keyboard ownership. The workbook palette uses a separate shortcut from the application's record search. Optional presence describes collaborators' selections, and is not an authorization mechanism or a saved business change.

## States and identity

Loading, errors and retry go through `QueryState` in [work-common](../../src/components/prototype/work-common.tsx), which keeps stale content usable after a failed refresh; libraries recover the same way. A record page and each retained tab panel is a failure region (`QueryState region`; `RetainedTabPanels` makes every panel one, through [failure-region](../../src/components/prototype/failure-region.ts)): each QueryState and ProductCollection inside hands its failures to the region's one alert, whose Retry refetches all of them, and a block with nothing to show keeps its place with a quiet Could not load. A strip of plain `TabsContent` wraps each panel in `QueryState region`. Reads whose values say Could not load in place (`QueryValue`) hand their failures to the region through `ReportFailures` in work-common, and `QueryState` is never drawn inside a value or a cell. The page's region also says the reads its header and Details are drawn from, the record's own first (as its `queries`, or through `ReportFailures` beside them), and a program's focused view is such a page: its blocks hand their failures to the page's one alert. Reference: [the task record](../../src/routes/tasks.$taskId.tsx), and the program sub-records in [program-record](../../src/components/prototype/program-record.tsx). The Details render in the page's or the tab's region, so they hand their failures to its alert too; a block drawn through a portal (a dialog, a preview panel) says its own. A related record's name in a value or a cell is `RelationName` from [record-tools](../../src/components/prototype/record-tools.tsx), never a QueryState of its own. `Empty` describes an empty region (`size="compact"` in a small one); `Absent` describes a missing scalar, heard as "Not recorded" unless a `label` says more ("Not available" for a record the reader cannot see, "No due date"). A screen never writes a dash, "Not recorded" or "Unassigned" in place of a value; a row value that feeds search and sort stays null, and its cell draws Absent. Words stay only where the value is itself a statement (No versions, Tailored out). A status, state, severity or impact renders through the components in [status](../../src/components/app/status.tsx) over the one map in [src/lib/status](../../src/lib/status.ts), and `c.status` takes the same vocabulary; a screen keeps no tone mapper of its own. Every date goes through `DateTime` or the `LedgerProvider` formatters in the reader's zone, never `toLocaleString` or a raw ISO string. A due date, an expiry or a milestone's planned date is the kit's `DateLabel`, through `DueDate` in work-common for work that can be done or cancelled: overdue, due today and due soon say so beside the date while the work is open. A due is a calendar day, never a moment: a task's and a scheduled assessment task's due, a remediation commitment's planned completion and a milestone's planned date. A form asks for it with a `DatePicker` labelled Due date, and a record's Details edits it in place with `Editable.Date` and `due`, which says the same at rest, through a command in [due-dates](../../src/lib/due-dates.ts) at revision + 1. While the work is open, a day before the reader's today reads Overdue, today Due today and the next two days Due soon; done work's day reads plainly, and only a remediation item's latest commitment is still due. An expiry (an evidence version's, an authorization's) passes `kind="expiry"`, which says Expired and Expires soon instead. A failure is never a blank table, and a load in progress is never an empty state.

A screen reads its rows scoped on the server, by program, system or the ids another read names, with the columns it shows: `useRows(table, filters, { columns })` (a list reads as PostgREST `in`; a dotted key such as `engineering_requirements.program_id` or `assessment_plan_revisions.campaign_id` joins through a reference), `programRequirementScope` in [requirement-reads](../../src/lib/requirement-reads.ts), `useSelectedControls` in [control-reads](../../src/lib/control-reads.ts), `useLibraryComponentUses` and `useComponentTraceability` in [library-reads](../../src/lib/library-reads.ts); a register that can hold thousands of rows reads a page at a time (Registers). A whole tenant-wide table is for small reference collections only; in development the console names any read that pages past 5,000 rows. A collection's schema (a column's choices, a generic form's columns, what the role may do) comes from `useCollection`, `useColumnChoices` or `useSchemaCatalog` in [collections](../../src/lib/collections.ts), for the schema inspector, the generic record forms and the previews that name their facts from it; it loads on demand, and a surface waits on it like any query: a create or edit action keeps its place while it loads, never a read-only note. ## What checks it

`npm run lint` runs the Ledger rules on every application file: tokens only, no margins, logical sides (`ledger/no-non-token-class` reports `text-left`, `pl-200`, `right-0` and the other physical sides with the logical class that mirrors right to left), a page layer by name (`z-overlay`, never `z-50`), no copied kit parts, no class that changes what a kit part sets itself or reaches into the parts inside an element (`ledger/no-restyle`: write the prop it names, or the part changes), `TextLink` for links (`ledger/text-link-navigation` rejects an action element rendered by one), `ledger/no-native-confirm` and `ledger/dialog-footer-order`, the overlay and form rules `ledger/no-overlay-autofocus`, `ledger/no-disabled-while-loading`, `ledger/overlay-width-preset`, `ledger/no-plain-alert-role`, `ledger/link-button-navigation` and `ledger/no-style-design-value`, a raw `h1`–`h6` with type classes, which is a `Heading` at the size it matches or the part that draws the title (`ledger/use-heading`), and a layout rule a kit part keeps inside itself (`sticky-rail`, `shell-*`, `grid-cols-main-rail`, `sticky-bar`, `min-h-work`, `grid-cols-list-detail`), which `ledger/no-non-token-class` reports with the part that owns it. `ledger/no-inline-config` reports a comment that turns a Ledger rule off, and the application keeps no disable of one; a disable that silences nothing fails the run. A custom link adapter passes when it renders an anchor and forwards props and ref; the browser checks verify the destination. The app-only rules `ledger/product-responsive-table` (a DataTable that turns `responsive` off, or leaves it to a prop spread) and `ledger/product-line-tabs` enforce the table and tab contracts, including imported aliases and overriding prop spreads; generic kit examples keep their supported variants. Lint does not read cross-file workflow semantics.
