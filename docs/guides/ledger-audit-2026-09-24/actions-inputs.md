# Family deep dive: actions and inputs

Part of the [Ledger audit, 24 September 2026](README.md).

Five units: actions, text inputs and fields, choice controls, Select and Combobox, and dates. Four problems cross the units and are cheapest fixed once:

- Field only does layout, so no product form binds errors to fields: INP-1, INP-2, SEL-3.
- `forced-colors.css` covers switch, radio, tabs and progress, but not buttons, menus or the calendar: BTN-8, SEL-2, DAT-6.
- The shadcn-derived parts use `sm`/`default` sizes against the kit's small/medium: BTN-13, CTL-16, SEL-10.
- Raw `aria-pressed` and `disabled` are used where the kit already has a state: BTN-1, BTN-3.

## Button, IconButton, ButtonGroup, Toggle, ToggleGroup

The family sits on sound Base UI foundations. Buttons default to `type="button"`, IconButton requires a name, and loading blocks activation while keeping focus when used as documented. Two kit defects stand out: the Toggle and ToggleGroup pressed fill is the same 6% grey as hover (1.4.11), and the saved-views button replaces its visible label with "Saved questions" on every register (2.5.3, Level A). In the app, every `isLoading` button also passes the pending flag to `disabled`, so focus falls to the page body mid-save. Fix those three first.

Keep: IconButton requires `label`, uses it as the name and pairs a tooltip; the loading guard blocks click, Enter and Space, including handlers on render children, and keeps label and focus; `type="button"` by default, with native form attributes, refs and state callbacks for className and style; icons in `iconBefore`/`iconAfter` are aria-hidden and sized, backed by the button-icon-slot lint rule; thorough play functions; ToggleGroup arrows follow the locale's reading direction, with Home/End, loopFocus and typed values; ButtonGroup joins on logical edges; the touch-target hit area on the link variant and IconButton.

**BTN-1 · Every loading button in the app also passes `disabled`, so focus drops to the page body** (high)
[button.tsx:164-169](../../../packages/design-system/src/components/button.tsx#L164-L169); call sites [create-task-dialog.tsx:457-458](../../../src/components/prototype/create-task-dialog.tsx#L457-L458), [create-evidence-dialog.tsx:467-470](../../../src/components/prototype/create-evidence-dialog.tsx#L467-L470), [add-from-library.tsx:756-757](../../../src/components/prototype/add-from-library.tsx#L756-L757), [add-product-system.tsx:292-293](../../../src/components/prototype/add-product-system.tsx#L292-L293), [product-structure.tsx:664-665](../../../src/components/prototype/product-structure.tsx#L664-L665), [requirement-evidence.tsx:553-554](../../../src/components/prototype/requirement-evidence.tsx#L553-L554), [library-products.tsx:1025](../../../src/components/prototype/library-products.tsx#L1025), [requirement-allocations.tsx:436](../../../src/components/prototype/requirement-allocations.tsx#L436), [record-browser.tsx:803](../../../src/components/app/record-browser.tsx#L803), [program-wizard.tsx:462-463](../../../src/components/app/program-wizard.tsx#L462-L463), [\_\_root.tsx:88-89](../../../src/routes/__root.tsx#L88-L89)
Button computes `focusableWhenDisabled ?? Boolean(isLoading && !disabled)`, so `disabled` wins, and all 11 `isLoading` call sites also pass the same pending flag to `disabled`. Reproduced on /work with the Create task save held: while pending, `document.activeElement` was BODY and the button wore the grey disabled palette. After a forced 500, Tab walked the aria-hidden top nav behind the open modal. The AlertDialog story, which passes `isLoading` alone, kept focus on Delete throughout.
Fix:

- Drop the pending flag from `disabled` at the 11 sites; `isLoading` already blocks activation.
- Add a lint rule that flags a `disabled` expression reusing the `isLoading` identifier.
- Changing precedence in the kit is optional. It contradicts [Button.mdx:40](../../../packages/design-system/src/stories/components/Button.mdx#L40) ("An explicitly disabled button remains disabled"), so it needs a documented contract change.

**BTN-2 · The Toggle and ToggleGroup pressed state looks the same as hover** (high)
[toggle.tsx:7](../../../packages/design-system/src/components/toggle.tsx#L7); consumers [mode.tsx:149-166](../../../packages/design-system/src/mode/mode.tsx#L149-L166), [filter.tsx:432-449](../../../packages/design-system/src/patterns/data-table/filter.tsx#L432-L449), [frame.tsx:366-375](../../../packages/design-system/src/patterns/chart/frame.tsx#L366-L375), [shell.tsx:164](../../../src/components/app/shell.tsx#L164)
Hover (`bg-neutral-subtle-hovered`) and pressed (`bg-neutral`) both resolve to neutral-200a at 6% alpha, so a hovered unpressed item and the pressed item are identical. At rest the pressed fill is about 1.1:1 against white and the text change about 2.2:1. Readers cannot tell which colour mode, saved view or chart state is active, and the colour-mode switch is on every page (1.4.11).
Fix: put pressed on the selected palette with a 3:1 indicator (for example `bg-selected text-selected` with a `border-selected` inset ring), matching Button `isSelected`. Keep hover visibly different, and add a pressed-against-rest contrast test.

**BTN-5 · The saved-views button's name replaces its visible label on every register** (high)
[filter.tsx:393-405](../../../packages/design-system/src/patterns/data-table/filter.tsx#L393-L405), [requirements-table.tsx:484-489](../../../src/components/prototype/requirements-table.tsx#L484-L489)
The button sets `aria-label={ariaLabel ?? t("savedQuestions")}` over visible text such as "All programs 7"; /programs, /work and /evidence all expose "Saved questions". A voice-control user saying "click All programs" gets nothing, and a screen-reader user never hears which view is active (2.5.3, Level A).

## Input, Textarea, InputGroup, Field, Forms

The parts share one control recipe and are well tested in stories. Field only does layout, though, and the app helper meant to bind it (`useRecordForm`) does not exist. So no product form marks an invalid field, errors arrive one at a time under the form, and focus stays on the submit button: a regression from the removed `useRequired`. Decide how Field binds first (a Field backed by Base UI Field.Root is the natural fit), then rebuild CreateTaskDialog and the wizard on it. After that come one clearable search part, Textarea autosize, no silent `maxLength` truncation, the phone grid and 16px text on touch.

Keep: one shared `controlBase` gives Input, Textarea, InputGroup and Select the same hover, focus, invalid, disabled and read-only looks; parts forward native props and refs, and Input keeps Base UI `render`, state className and cancellable `onValueChange`; play functions check names, descriptions, first-invalid focus, retained values, FormData and server-rejection recovery; clicking empty InputGroupAddon space focuses the control, a squeezed group clips at its edge, and the Kbd hint uses a container query; FieldError takes children or an errors array, removes duplicates and renders nothing when empty; the Don't pairs give concrete content guidance; the InField stories validate on submit, revalidate on change and keep the draft.

## Select and Combobox

Thin wrappers over Base UI 1.7 whose keyboard, typeahead and form behaviour is sound; the defects are in what Ledger adds. The worst is ComboboxInput's built-in chevron: Button's props override Base UI's `tabIndex -1`, so every app Combobox has an extra tab stop named "Choose…", which stays focusable inside aria-hidden while the list is open. The defaults come next: Select opens over its trigger at fit-content width, Combobox does not highlight the first match, so type-then-Enter selects nothing, and ComboboxSeparator is invisible because the token lint does not read `classes()`.

Keep: Base UI's APG keyboard (typeahead, Home/End, Escape one layer at a time in dialogs, focus return); one menu item look in menu.ts for Select, Combobox, DropdownMenu and Command; play functions for FormData, required, cancelled changes, object identity, multiple values, read-only and RTL; locale and direction from LedgerProvider, including popup positioning; Scroller arrows only for hover-capable pointers, with focused items revealed clear of them; Select reuses Base UI's scroll arrows in the Scroller look; popups stayed within the viewport at every width in the responsive sweeps.

**SEL-1 · ComboboxInput's chevron is an extra tab stop named "Choose…"** (high)
[combobox.tsx:93-100](../../../packages/design-system/src/components/combobox.tsx#L93-L100)
ComboboxInput renders its trigger through InputGroupButton, and Button's props override Base UI's `tabIndex -1`. In Create task the tab order runs Input, "Choose…", Input, "Choose…": three identical buttons that do not name their field. With the popup open, axe reports a serious `aria-hidden-focus`, because the aria-hidden addon still holds the tabbable button. The trigger also loses `data-slot="combobox-trigger"`, so selectors and tests that target the slot miss it.
Fix: render the Base UI trigger directly with the InputGroupButton classes, or pass `tabIndex={-1}` after the merge. Name it from the field label, as the APG examples do. Add a play assertion that Tab leaves the field, and run axe with the popup open.

## Calendar and DatePicker

Sound underneath: DayPicker's keyboard grid, the ISO-day form contract and focus return all hold. Accessibility and locale are weak. Keep: the APG grid keyboard from DayPicker (arrows, PageUp/PageDown, Shift for the year, Home/End by week, one tab stop, a visible focus ring); the ISO-day hidden input, with external form, native reset, disabled omission and controlled/uncontrolled all covered by play functions; focus returns to the trigger after select, Clear and Escape, including inside a Dialog; `formatCalendarDate` keeps date-only values from shifting across zones; RTL and `navLayout="around"` asserted in both directions; the two-month layout keyed to its container, with a 320px story; Do/Don't examples that steer remembered dates to Input; the dark-mode selected and today treatment, and 32px cells at 340px.
