# Explicit prototype demo import

This dataset is the preserved fictional prototype, imported only when explicitly requested. It is separate from the authoritative NIST/DISA reference seed. Application code reads Supabase records; it does not import the archived prototype or use a fallback fixture.

The importer defaults to a read-only plan and requires an explicit tenant and account. `--check` validates in a transaction and rolls back; `--apply` commits the reviewed import. Existing records are not overwritten. See [the importer](../scripts/seed-demo.mjs) for the exact command interface and [the provenance migration](../supabase/migrations/20260912090000_demo_seed_provenance.sql) for source-record storage. A mapping report records omissions and conversions; a successful import does not mean every original field has a normalized equivalent.

## Source and reproduction

Run `node scripts/extract-demo.mjs` to reproduce [the compressed fixture](../supabase/demo/original-poc.json.gz) and [its manifest](../supabase/demo/manifest.json). The extractor bundles archived source modules in an isolated Node VM, invokes their original registration functions, and reads their shipped records. It has no browser storage, Supabase client, or database write path.

The extraction clock, `2026-08-30T12:00:00Z`, is the literal clock in the archived `dataset-clock.ts`; it is not today's date. Original timestamp strings remain unchanged, including incomplete dates and inconsistent historical demo dates. Source fields are never advanced to the current date.

The manifest records the extractor hash, 99 archived input hashes, compressed/uncompressed fixture hashes, and asset hashes. The shipped WS-X90 JSON still has SHA-256 `4221c55b7c7892eefc2d175f35883064c06cfe699874d4c8efec2850911803b3`. All collections captured by the previously paused extraction were compared and remain JSON-equivalent; this extraction adds previously omitted records rather than replacing them.

Route-only literal records are extracted through TypeScript's AST and a literal-only evaluator; the route code is not executed. This includes six vendor records and the risk-detail page's four timeline entries and three evidence filenames. That risk page reused these literals for every risk without recording a risk ID, so they remain unassigned source records. A scan of the other route-level literal collections found navigation/tone dictionaries and dashboard summary counters; those display counters are deliberately excluded.

The fixture contains both the original WS-X90 source arrays under `platform` and the original native-store projections. These are two representations of the same records, not additive populations. `platformIds` contains the original source-to-native ID mappings for components, nodes, assets, and scopes. Source pointers use JSON Pointer syntax, for example `/platform/control_implementations/0/by_component/0`.

## Workflow and evidence mapping

The [workflow mapper](../scripts/demo/map-workflow.mjs) consumes the same fixture and assurance UUID maps. It maps resolvable evidence metadata and explicit requirement-evidence links, campaigns, procedure revisions/steps, recorded observations, operational issues, risks, POA&M items/milestones, workstreams, tasks, gates, and activity. Formal assessment documents and test-run models require exact plan, configuration, SSP or procedure-version pins that many original records lack; their original observations can be retained without inventing those pins. The import's generated mapping report is the exact per-record result. The import therefore publishes no assessment result: WS-X90's 420 recorded results reach the database only as the 52 findings their failures raised. The showcase step writes the plan and results documents the import could not and publishes those results as determinations ([WS-X90's assessment results](#ws-x90s-assessment-results)).

POA&M links require an explicit source ID or finding reference in the same program. Two missing IDs never establish a relationship. Where the legacy register projection coarsened the original state, the original value wins: `PRG-1041/V-0001` remains Open and `PRG-1041/V-0003` remains Deferred, rather than their projected Ongoing labels. These differences are recorded as import issues.

All 368 WS-X90 evidence records supply a `urn:demo:evidence:...` reference and a source-claimed hash. None supplies file bytes. The remaining 22 catalog records have no artifact URI. No evidence catalog record has a URL. An immutable imported metadata version with an existing URI is not a claim that bytes were uploaded, that its checksum was verified, or that a reviewer accepted it.

## Explicit gaps and source inconsistencies

- All three packages name system IDs absent from the actual system records: `SYS-2210`, `SYS-2214`, and `SYS-2301`. `PKG-0014` also names absent program `PRG-1052`. No package is assigned to a similar-looking system.
- The 147 ODP starting-value records identify a control and prose parameter references, often several values in one string. They do not identify exact OSCAL parameter IDs. Their text is retained without guessed parameter assignments.
- Requirement derivations identify whole controls or non-control sources such as threats and policies. The current normalized relationship requires a particular `control_part_id`; no assessment objective or statement link is invented to fill it.
- Provider allocations `ALC-0003` (`signing-enclave`) and `ALC-0006` (`provisioning-line`) lack an identified providing system or provider organization record. The provider labels and source allocation data remain in provenance.
- Many owner strings identify roles, teams, abbreviated names, or people absent from the 14-person directory. Exact-name matches are used; similar names and role titles do not create identities.
- Three POA&M records (`V-0001`, `V-0002`, `V-0003`) point to portfolio risk IDs `RSK-2388`, `RSK-2311`, and `RSK-2402`, rather than the separate register-risk collection. They are retained as source references when that risk cannot be mapped without inventing a program.
- Source labels such as `Aug 27, 09:41`, `Aug 12`, and `—` do not identify a complete timestamp. The importer leaves unavailable normalized dates null and preserves the exact string in provenance; it does not infer a year or timezone from the import clock.
- Original source aggregate counts, historical claims, synthetic checksums, and incomplete approvals are source content. They are not substitutes for normalized observations, uploaded bytes, authorization decisions, or review records.

## WS-X90 control baseline

The import above reproduces WS-X90's saved 546-control selection as a draft profile for its SSP. It does not give the program a baseline: `PRG-1090` has no `program_reference_choices` row, so its Control baseline view has nothing to show. [A separate explicit step](../scripts/seed-demo-baseline.mjs) records the baseline as the layered stack the source describes.

The source is `profiles[0]` of the archived [WS-X90 platform seed](../tests/fixtures/legacy-poc/src/data/wsx90-platform-seed.json): its `starting_selection`, its four `overlays` in order, and its `effective_control_ids`. The script reads the fixture from disk; application code never imports it. Controls are matched by code against the pinned catalog, and the starting selection must equal the published reference resolution of the NIST SP 800-53 Rev 5 High baseline.

|     0 | NIST SP 800-53 Rev 5 High   |                          |       |            |         |      370 |

Each overlay becomes a published `control_overlays` record in the target workspace: its code is the source `overlay_id`, its title the source `name`, its description the source `reason`. Each `adds` entry is an `include` decision and each `removes` entry an `exclude` decision, with the overlay's `reason` as the rationale. The source's per-control `tailoring_events` rationales are not copied. `apply_control_overlay` then authors one published layered profile per overlay, coded `PRG-1090/profiles/1/overlays/<n>`, on the layer beneath it. An add the layer beneath already selects is recorded as a reaffirmation in `profile_overlay_applications`, not as a rule. The CNSSI 1253 overlay is the source's nonauthoritative demo allocation; the records do not claim to implement CNSSI allocation rules.

Before the program's `program_reference_choices` row is written, the final layer's selected controls are compared by code with the source `effective_control_ids`. Any difference, an unknown control code, a newly added control that is not active, or an overlay that changes nothing aborts the transaction.

```sh
npm run seed:demo-baseline -- --tenant UUID --account EMAIL            # read-only plan
npm run seed:demo-baseline -- --tenant UUID --account EMAIL --check    # whole transaction, rolled back
npm run seed:demo-baseline -- --tenant UUID --account EMAIL --apply    # commit
```

The step follows the importer's conventions: an explicit tenant and account, a read-only plan by default, and one transaction. It is idempotent. A repeat finds the overlays by code, the layers by profile code and the program's choice, and changes nothing. An overlay with the same code but different decisions, a draft overlay with the same code, a layer profile that is not that overlay on the layer beneath, or a program that already has a different baseline stops the run without overwriting anything. The overlays and layers are written outside the `demo_import_records` provenance tables.

### WS-X90's assessment results

The import publishes no assessment result, since it could not pin WS-X90's results to a results revision, so a workspace with the import alone reads 0% satisfied and shows no determination; the showcase's first version spread determinations over the baseline by a hash of each control's code. Josef decided on 2026-11-13 that the demo seed should carry a believable published assessment result. The showcase now publishes the one the archive already holds: the [platform seed](../tests/fixtures/legacy-poc/src/data/wsx90-platform-seed.json)'s `assessments` and its 420 `assessment_results`, each a requirement judged on its components by one method, with the evidence examined, an outcome and a day. [The seed script](../scripts/seed-demo-showcase.mjs) reads them from disk (`archivedAssessments`); application code never imports the fixture.

Each archived result becomes a determination on the statement of each control its requirement maps. A pass is satisfied. A failure raised one of the archive's 52 findings, which the import keeps as operational issues: where that finding is high or critical the control is other than satisfied, otherwise partially satisfied. An inconclusive result, and one the assessor did not carry out, is recorded as not assessed with the assessor's words, which decides nothing. Within a results revision a control takes the worst of the results that judged it, the latest on a tie. Only a control whose requirements cite evidence takes a determination, so a control with no requirement or no evidence still reads No requirement or No evidence; six of the initial assessment's results fall on such controls and are left out. The initial assessment's results carry no narrative of their own, so their words are written from the result (`assessments.narrative`); the expanded assessment's are the assessor's own. Every determination cites the evidence its result examined, and a short one the observation the import recorded for the finding it raised, so Open assessment findings leads to what was found and the operational issue it became. The issues' risks are draft revisions, which a published finding cannot cite, so no finding names a risk.

A pending review is a row of the Review queue (Evidence to accept), waiting on the assessor. Each artifact that waits on one and has no owner is given one through `assign_record_owner` as the account: the person of the program's team who holds the role the archive gives the requirement it was collected for ([`evidenceOwnerRoles`](../scripts/demo/showcase-scenario.mjs)): Priya Raghavan for the System Security Engineer, Victor Amsel for the Product Security Engineer, Ingrid Solberg for the Firmware Lead and Joel Barrantes for the Platform Lead. Who asked for a review and when are the review row's `created_by` and `created_at`, which the record lifecycle trigger stamps when the row is written (the session's account, the moment it runs) and keeps on every update, so the queue's Requested by stays empty and its Waiting since is the day the showcase was seeded.

### The flow-down

Afterwards 61 of the 62 elements hold their own requirements (one to seven) and evidence. One answer moves: CUSA-SSRD 3.4.2 now also rests on the R210 firmware Customer A changed, so of Customer A's 14 requirements 5 are met by the product as delivered and 6 rest on a changed element (6 and 5 before).
