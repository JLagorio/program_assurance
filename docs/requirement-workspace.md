# Requirement workspace

The program's Requirements tab uses the shared design system DataTable. The requirement code opens its full page; the eye opens a Shell.Panel beside the table. Search, filters, sorting and columns remain available while reviewing records. Previous and next follow the visible requirement order.

The table shows actual requirement statements, allocation targets and linked controls. Expand allocations to inspect their recorded details. Parent and child rows come from recorded decomposition links. Ambiguous or cyclic relationships remain visible as flat rows with a notice. Requirements without authored details remain visible as “Details not recorded”; viewing one does not invent content. Optional columns and saved views use the existing table controls.

## Inline editing and edit history

The preview and full page share Statement, Control mappings, Allocation, Verification, Evidence and Edit history. Opening the full page retains the selected tab. The requirement has no revision action, version selector, revision table or publication workflow. Old revision search parameters no longer select another snapshot in the product interface.

Title, requirement type, owner, statement, acceptance criteria and rationale use the design system's `Editable` controls. Click a value to edit it. Enter or leaving a text field saves; multiline fields use Control/Command+Enter or leaving the field. Escape cancels. Owner choices come from actual workspace parties; requirement types use the schema's controlled values. An existing identity without authored content uses the focused **Add requirement details** dialog.

Each changed field updates the same requirement record and appends its actual before/after values, actor and time to edit history in one transaction. Existing relationships keep their IDs and targets. Edits do not create snapshots or copies. Blank required values fail validation; unchanged values produce no edit event.

Stale requests fail instead of overwriting another session's changes. Failed saves retain the proposed value for retry or discard. Repeating an identical request returns its recorded result without duplicating the edit or history entry. See [requirement edit persistence](requirement-edit-history.md) for database behavior and compatibility with existing records.

## Evidence flow

**Add evidence** opens the design system RecordBrowser as a large dialog with search, filters, multiple selection and an internal preview. It lists published evidence versions belonging to the program or the workspace without a program assignment. Evidence links retain the exact selected evidence version; already linked versions are excluded.

**New evidence / Upload** moves to the evidence creation dialog and then version preparation. Creation records an artifact and its first draft metadata version. Preparation supports private file upload and recovery or a recorded external URI. **Publish version** freezes the evidence version; it does not link it to a requirement or record an approval. Returning to the browser retains prior selections, and the new published evidence version can then be selected.

**Link evidence** saves the complete selection through `link_requirement_evidence` in one transaction. The database checks workspace access, program scope, the current requirement and every selected published evidence version. Requirements do not need to enter a revision workflow to link evidence. Failed requests leave selections available for retry. Existing links and authored claims survive repeated requests. Selecting evidence does not invent applicability decisions or review results.

The evidence picker, linked evidence preview and version preparation share `EvidenceVersionDetails`. Sequential dialogs use the RecordBrowser's optional controlled selection API; uncontrolled consumers clear their selections when closed.

## Verification

With the local stack and frontend running, `npm run test:requirements` exercises authorization and atomic edits, edit history, preserved record and relationship IDs, exact evidence links, the preview and full-page flows, retained selections, failed-save recovery and stale edits. It creates and removes disposable test workspaces. Read-only developer workspace checks are available through `node scripts/test-requirements-workspace.mjs`.

## Workbook authoring and review

The workbook uses Ledger's `Spreadsheet`, `SpreadsheetFormatting`, `SpreadsheetToolbar` and `SpreadsheetSheetBar`. The app supplies record identities and authorization; the UI package owns editing, focus, range selection, menus, formula assistance, clipboard gestures and dimensions. The independent `@ledger/spreadsheet-core` package owns operations, stable cell IDs, formulas, conditional rules, history, file interchange and calculation workers. `assurance-workbench.tsx` connects these layers; `workbook-view.ts` translates canonical formula coordinates into stable cell identities. Presentation controls do not import the calculation engine.

Source sheets retain field-defined types and protected columns. Editing requirement or mapping fields stages an atomic proposal; **Review changes** applies it against the loaded revisions. Analysis sheets accept formulas and authored formatting. **Save analysis** persists analysis cells, source-sheet presentation and conditional rules without applying source edits. Pending cell drafts guard navigation and structural changes. Existing local recovery and uncertain-response receipts remain in force.

The formatting toolbar supports font family and size, bold/italic/underline/strike, text and fill colors, borders, number formats, alignment and wrapping. Source fields accept visual formatting but keep their defined number representation. Row height supports automatic content measurement, manual resizing and fit-to-data. Formula entry offers function completion, signatures, argument hints and highlighted references. Pointer reference insertion currently selects ranges on the active sheet; typed references can address other sheets. The host evaluates formulas in a retained worker model, sends deltas after input edits, and avoids reevaluation for presentation-only changes. This does not claim that the underlying formula engine recalculates only affected nodes after every input edit.

**Find and replace** searches authored input or calculated display, across one or all sheets. Only authored, editable cells can be replaced; one replacement batch is one undo step, and source replacements still require review. Hidden rows and columns are omitted from search. Selection totals use evaluated values and exclude hidden cells. Conditional number, text and blank rules target stable cell IDs and are persisted with the sheet. Later matching rules take precedence. The editor can add, edit and remove rules; copied formatting captures authored styles rather than transient conditional output.

Local rich copy and paste preserves formulas, literal-text intent and authored cell styles. **Paste values** retains destination formatting. **Paste formatting** retains destination inputs and their interpretation. A paste crosses the component boundary as one `onPaste` intent, and the app applies one `paste-cells` operation; rejection leaves a retryable operation. External clipboard text cannot carry trusted style metadata. Supported conditional rules round-trip through XLSX; unsupported imports report warnings and unsupported exports fail explicitly. Native workbook JSON preserves the complete model.

**Saved views** persists a named private or workspace-shared definition. Collection views contain filters, sorting, columns, pinning, widths, wrapping, density and page size. Workbook views contain active sheet, filter/sort, grid/matrix/chart view, analytical grouping/measure, and active-sheet dimensions, visibility and frozen headings. Applying a view changes presentation rather than canonical records; workbook layout changes remain undoable and use **Save analysis** to persist with the workbook. Only the view's author may edit or delete it; stale edits are rejected and identical retries do not create duplicates.

**Discuss cell** opens contextual review and evidence citations without adding a permanent details rail. Source requirement and mapping rows resolve to their domain record; evidence rows resolve to a version. Analysis cells require a saved workbook and use stable workbook, sheet, row and column IDs. Review threads record authors, timestamps, replies and resolved/reopened events. Reopening or replying changes the thread revision. Stale status changes fail; uncertain submission retries retain the original request identity.

Citations capture an exact evidence version, content hash, quoted passage and optional page, anchor and rectangle. The version picker searches and pages the complete eligible set. Source links and **Referenced by** connect the passage back to its requirement, mapping or saved cell. External URIs are stored as provenance; private uploaded evidence captures its exact storage object and verifies SHA-256 on download. Workspace clients cannot replace or delete a cited object. Quoted passages and locations are reviewer assertions; the system records them and verifies stored-file hashes, not whether a quote occurs in the file. Private uploaded PDFs can now open in the in-app reader. PDF.js supplies the rendered page and selectable text; Ledger supplies page/zoom controls, selection tools and anchor overlays. Selecting text captures its quote, page and normalized rectangle; region selection supports scanned pages with an explicit transcription. Cite, Discuss and Copy passage link retain the exact version. Opening a citation resolves its exact ID beyond the first result page, verifies the captured bytes and focuses the original page/region. Password-protected PDFs request their password locally; denied extraction disables text capture. Unsupported/external content remains explicitly unavailable in the private reader. This is page text extraction for reading and selection, not a workspace-wide binary file index.

Workspace search covers program/requirement/control text, evidence metadata and cited passages, findings and risks with tenant-scoped queries and excerpts. It does not index the binary contents of uploaded files. **My work → Attention** combines open review threads, assigned blocked/overdue work, mappings needing review and changed cited evidence. Seen/done acknowledgments belong to the reader and exact source revision; later changes return as unread. **Undo** restores the prior acknowledgment without changing the underlying record. Acknowledgment commands retain exact request receipts and compare a monotonic acknowledgment version; retries and stale tabs cannot overwrite newer decisions. Allocation repair and later removal advance a separate generation so a recurring mapping issue reappears.

## Review and navigation

Requirement edit-history prose uses Ledger `Diff` with view switching, previous/next change and source-line discussion actions. Title, type and owner changes retain their readable value summaries with the same anchored discussions. A discussion targets its immutable activity event, field, side and line range. Server validation captures the original context; a later in-place requirement edit cannot change that discussion's source. Deep links return to the original edit and scroll the selected line range into view, including long statements. Invalid ranges clear a prior selection. Existing general requirement discussions capture current context when created; older threads keep their original unanchored context. No new revision or publication workflow is introduced.

The evidence reader's exact passage and citation threads use the same review commands, authors, replies and resolve/reopen history. Citations can target requirements, mappings, saved cells or assessment findings; the finding's record page exposes its citations and review discussions.

**Pin reference** in a record preview creates an explicit comparison workspace. The reference is read-only and remains visible when the active record or route changes. Both panes preserve their DOM and independent reading positions; on a narrow screen a labelled switch changes the visible pane. Linked identifiers provide lazy hover/focus summaries and a separate Preview action for touch and keyboard. Their normal link and modified-click navigation remain available.

The global **Search and actions** launcher combines matching record excerpts, saved views, personal destinations and registered page commands. Page commands reuse their existing handlers and permissions. A saved-view destination captures its actual collection route and tab; following it reapplies its stored definition, including repeated visits. Older ambiguous collection views must be resaved from their original collection before they can launch directly.

**Favorites** and **Recently opened** belong to the signed-in reader within the current workspace. The server resolves source names and links; clients cannot inject arbitrary destinations. Supported destinations include programs, requirements, evidence, saved views and saved workbook sheets. Reordering favorites requires the current exact set. Clearing recent history retains favorites. Unsaved analysis sheets are not durable destinations.

The shared package owns presentation and interaction: `DocumentReader`, `DocumentPage`, `DocumentSelectionToolbar`, `Comparison`, `Peek`, and the existing `Diff` and `CommandPalette` extensions. Their Storybook pages document native props/refs, controlled state, keyboard/touch behavior and narrow layouts. PDF parsing, file identity, source permissions, historical target validation, route registration and persistence stay in application modules.

## Shared interaction components

The prototype consumes Ledger's ContextMenu for workbook cells, headers and sheets, FindBar for workbook search and current-page PDF search, and MatchText for query excerpts. PDF find matches literal text on the current rendered page, up to 500 matches; copy-restricted PDFs disable it. PDF search highlights are local navigation markers, separate from citation or discussion anchors; they reset with the page and completed text-layer render. DocumentSelectionToolbar uses SelectionActions for an optional floating action row with an inline touch and Escape fallback.

Saved view menus, management and editing use controlled SavedViewPicker, SavedViewManager and SavedViewEditor. The application retains private/shared permissions, persistence, revision conflict recovery, URL restoration, deletion confirmation and dirty drafts. ReviewThread and Citation standardize discussion and source presentation while immutable targets, writes and file identity checks remain application logic.

Analysis sheet tabs and personal favorites use Reorder's pointer, keyboard and explicit move controls. Source tabs remain protected; workbook moves run through the existing guarded draft operation. Favorites use stable visible selection identities, including range and select-all, for batch removal. These controls change ordering or personal navigation, not underlying source records.

`npm run test:shared-interactions` exercises saved-view and collection workflows against local Supabase; `test:review-workspace` covers evidence reading and anchored reviews, and `test:workbook` covers grid operations. Ledger's family pages and Guidance/Interaction states document the reusable contracts.
