# Control baseline: catalog, baseline, overlays, tailoring

How a program's control baseline is formed, and where each step shows in the product.

## The stack

A program's control baseline is a stack, read bottom up:

1. **Catalog.** One published catalog edition (NIST SP 800-53 Rev 5).
2. **Reference baseline.** A published profile on that catalog (Low, Moderate, High, Privacy), or two of them combined: their union (Two baselines in one stack, below).
3. **Overlays, in order.** Each overlay is a library record: a named set of control decisions, each with a rationale. A decision adds a control or removes one. An overlay is not tied to a baseline, so the same overlay can be stacked by any program on the same catalog edition.
4. **Program tailoring.** The program's own last layer: controls out, controls in and parameter overrides.

A system adopts one program profile and may tailor once more on top of it.

Applying a layer never guesses. An add of a control the baseline beneath already selects is recorded as **already selected** (a reaffirmation); a removal of a control it does not select is recorded as **not in the baseline**. An overlay that changes nothing where it sits is refused, in setup and by the database. A later layer can undo an earlier one (an overlay removes a control and a later one adds it back); the control's origin is then the last layer that added it.

## What is stored

Every layer is a real OSCAL profile layered on the one beneath it, authored by `author_tailored_profile`: the base imported with `include-all`, one exclusion per control removed, the catalog imported with one inclusion per control added. A stack is therefore an import chain of `profile_resolutions` joined by `base_profile_resolution_id`, at most eight layers on the reference profile.

- `control_overlays` and `control_overlay_decisions` hold the overlay and its decisions, and `control_overlay_parameters` the values it gives parameters (`parameter_values`, in order, with a rationale; written through `set_control_overlay_parameters`). They are written only through `save_control_overlay`, `set_control_overlay_decisions` and `publish_control_overlay`; a published overlay is immutable.
- `apply_control_overlay` authors the layer one overlay makes of a base, with the overlay's values for the controls the layer selects as the layer's own `profile_parameter_settings` and `profile_parameter_values`, and `profile_overlay_applications` names the overlay behind each layer with the decisions that were already true.
- `create_program_wizard` takes `overlayIds` on each program profile, in order, and records the top of the stack in `program_reference_choices`.
- `set_program_baseline_overlays` changes the overlays of an existing program profile's stack (Changing the stack after creation, below); `program_baseline_requests` holds its receipts.
- `delete_control_overlay` deletes a draft overlay, its decisions and its values; a draft version leaves the version it was created from as it is.
- `create_control_overlay_version` creates the next version of a published overlay (below). A published overlay, or one a program's stack applies, is refused.
- `control_overlay_rows` is the register's view. `program_control_requirement_counts` counts, per program and control, the requirements whose latest revision maps the control.

An overlay carries parameter values beside its decisions. A value is set for a parameter of a control of the overlay's catalog edition: a choice parameter takes a published choice, one that takes one value exactly one, and SA-24's five offer the cyber resiliency framework's items, as the tailoring checks and offers them. Applied, a value for a control the layer selects becomes a setting of the layer, so it is effective as `author_tailored_profile` resolves it: the nearest layer of the stack that sets the parameter, else the catalog's own, which is what `program_control_parameters` and `program_resiliency_choice` read. A value for a control the layer leaves out sets nothing and is recorded beside the layer (`not_applicable_parameter_ids`). An overlay that changes nothing where it is applied, no control added or removed and no value set, is refused; one with values alone is a layer of its own. Publishing needs a decision or a value, and a published overlay's values are immutable like its decisions. The program's tailoring still sets values of its own, last. A rationale taken from Table E-1 is the decision's `rationale` text like any other: `resiliencyRationale` in `src/lib/control-overlays.ts` writes it from the framework's control links, and nothing ties the decision to those rows afterwards.

## Where it shows

- **Libraries, Overlays, Parameter values.** The overlay record's Parameter values Section lists each parameter the overlay sets (its name, ID, control, values and rationale), with Set parameter values, a small secondary, and Edit values and Remove values on a draft's rows. Set parameter values is the tailoring's Dialog over the edition's parameters: unsearched, the list holds those the overlay sets and those of the controls it adds, and a search finds any parameter by its control, its id or its name (the first 100 matches listed); a parameter's values are entered as the tailoring enters them (`ParameterValueEntry` and `entryMode` in `src/components/app/profile-tailoring/`) and saved on their own with their rationale. The register counts Parameters, and so do the preview and the record's Details. The stack table has a Parameters column and the Control baseline view's rows say "+3 −8 · 2 parameters".
- **Libraries, Overlays** (`/overlays`): the register, Create overlay, and the overlay record where a draft's decisions are added and the overlay is published. A row's eye opens Overlay preview: its state, code, what it adds and removes, how many baselines apply it, when it changed and its description. The preview is read only; the edit, the decisions and Publish are the record's. A draft is deleted with Delete overlay, the danger item of the record's Actions and of a draft's preview overflow menu, after a confirmation that says how many decisions go with it; from the preview, focus goes to Create overlay. The words of a decision (Adds, Removes) are `overlayDecisionActions` in `src/lib/status.ts`, and an overlay's State is a revision's.
- **Add decisions, from Table E-1.** Where the catalog edition has NIST SP 800-160 Vol. 2 Rev. 1's Table E-1 loaded (`docs/reference-seeding.md`, Transcribed frameworks), the picker filters the edition's controls by Resiliency technique, one technique at a time, each with the count of controls the table names for it (Segmentation 41, Substantiated Integrity 58). A decision that adds controls takes one rationale written for all or each control's own from the table: `Supports Realignment [Purposing, Restriction] and Segmentation [Predefined Segmentation] (NIST SP 800-160 Vol. 2 Rev. 1, Table E-1).`, the techniques strongest first as the table orders them, each with its approaches. A chosen control the table does not name stops the save until it is cleared or the rationale is written. A removal's rationale is always written. Without the reference data the picker offers neither.
- **Create program, step 2.** Under each chosen baseline: Combine with (a reference baseline, a Select of the catalog's other reference baselines with No second baseline), the stack table (layer, type, added, removed, parameters, running count; one line a row, both baselines first where two are combined), then Resulting baseline: the Control baseline view's Grid of the draft's result, tailoring included, under its key, with a List of the same controls one toggle away (`DraftBaselineMap` in `src/components/prototype/draft-baseline-map.tsx`); a mark opens its family in the List. The stack table counts what each layer did and the map says where each control ends up, so the map keeps its own table, the List, rather than leaning on the stack table's numbers, Add overlay, move and remove for each overlay, and Tailor for this program on top of the stacked baseline.
- **Program Overview, Control baseline.** The saved stack, with a link to the focused view.
- **Program, Control baseline** (Actions, Views; `/programs/:id/control-baseline`): one list-and-detail pane. The list is the stack: the reference baseline, then each layer with what it added and removed and the running count. Choosing a row shows the baseline after that layer, and Replay walks the rows. Beside it, the catalog at that step as a Grid or a Skyline (Ledger's `TileMap`: a mark a control, filled for one in the baseline, the brand colour for one a layer added, hollow for one a layer removed, faint for one not selected, with a key that counts each), or as a List with each control's family, status, the layer that changed it and its requirement count. A mark opens its family in the List. The address keeps the step (`layer`, how many layers are applied: `layer=0` is the reference baseline alone) and the take (`show=skyline` or `show=list`) beside the technique: a choice is a step Back returns from, an address that names neither shows the last layer as a Grid, and Replay writes only the step it ends on. Where the pane shows one side at a time (a phone), an address that names a step, a take or a technique opens on the detail, and Back to one that names none returns to the layers. The layer is its place in the stack, so a shared link holds while the stack keeps its order.
- **Program, Control baseline, what-if.** Each layer's row has a switch, Apply and the layer's name. Switched off, the layer keeps its place, reads Not applied and changes nothing, and every layer after it is applied again to what is beneath it, so an add the missing layer made moot adds again; the count, the map, its key and the List read that stack at every step, and a step switched off is headed "549 controls without Deployed Platform Overlay". A status line says how the result differs from the saved one ("What-if: 5 more and 0 fewer controls than the saved baseline"), names the layers not applied and offers Back to saved. Nothing is saved, and the database is not asked: `stackWithout` in `src/lib/baseline-stack.ts` re-derives the stack from the decisions the saved layers recorded, their reaffirmations and removals of controls not selected included. The address keeps the layers switched off (`off`, the first eight characters of each layer's resolution id, comma-separated): a switch is a step Back returns from, a reload or a shared link keeps the what-if while those layers stand, and a control opened from the List comes back to it. On WS-X90, Mission Assurance off reads 565 controls, 5 more than the saved 560; with the program tailoring off too, 5 more and 14 fewer.
- **Program, Control baseline, Edit overlays.** A reader who may edit changes the stack's overlays from the list's toolbar (the view's one primary; a secondary for each baseline where a program adopted several): a Dialog with the stack table, each overlay's Move earlier, Move later and Remove, Add overlay (the published overlays of the program's catalog edition), and What changes against the baseline the program has now (controls now and after, the controls added and removed, the program tailoring carried, the systems that move and the SSP revisions that keep their baseline). An overlay that changes nothing where it sits is a FieldError. Applying asks first, since it changes what the program owes; a refusal (another session's change) stays in the Dialog, and the change itself is `set_program_baseline_overlays`.
- **Program, Control baseline, by resiliency technique.** A Select beside Show as reads the same view by one cyber resiliency technique of NIST SP 800-160 Vol. 2 Rev. 1 (`?technique=segmentation`, the technique's code after `technique.`). Each option and the heading count the baseline's controls at the layer shown that support the technique, of the catalog's active controls that support it in Table E-1 ("16 of 41"). The map colours only those controls (one the baseline leaves out is hollow, every other control keeps its place as a faint mark), the key counts them, and the List holds them with an Approaches column; Replay shows the count rise layer by layer. Over all controls the List has a Techniques column. The techniques a program chose for SA-24 lead the Select.
- **Program, Cyber resiliency** (Actions, Views; `/programs/:id/resiliency`): the same stack read by NIST SP 800-160 Vol. 2's ladder. Two numbers lead: the controls the baseline holds of the 265 Table E-1 names, and the approaches with nothing behind them, which narrows the view to those approaches. The layers are a stepper with Replay, and the address keeps the layer. Show as chooses Ladder (goals, objectives, techniques and approaches joined by every relation the publication prints, each with what the baseline holds of the controls behind it) or Layers (a technique a row and a layer a column, with the approaches under each technique one switch away). The ladder keeps its wires while its levels have room, down to a 1280px window with the preview open beside it, and stacks its levels in order in less, as on a phone. An approach opens its preview: what Table D-4 says of it (its definition, NIST's examples and its discussion), then the controls that support it, those in the baseline first with their requirement counts.
- **Control records.** The catalog's and the program's control record list the techniques a control supports under Cyber resiliency, strongest first, each with its approaches and how many examples NIST gives for them. A row opens in place onto the technique's definition and discussion and each approach's definition, examples and discussion (Table D-4). In a program a technique opens the Control baseline read by it. Under it, ATT&CK techniques lists the techniques Appendix F prints the control against, with the tactics, mitigations, approaches and effects, and, in a program, how many of its risks name each. The control preview carries Cyber resiliency, closed.
- **Program Controls tab.** An Origin column and filter, for a program with a recorded baseline.

`src/lib/baseline-stack.ts` is the one walker: `deriveStack` applies layers to a selection, `deriveSavedBaseline` reads a saved chain as layers, `stackAt` reads a derivation after its first few layers, and `controlStanding` says where a control stands at that step. Program setup builds its draft stack with `stackDraftOverlays` in the shape the database will author, so the tailoring editor and every count read a draft stack the same way as a saved one.

`src/lib/control-resiliency.ts` regroups the reads of `src/lib/frameworks.ts` for these screens: `techniqueControls` gives each technique the controls behind it among those a screen counts, `selectedOf` how many of them a step selects, `supportedOnce` one row a technique for a control, and `techniqueSlug` and `techniqueParam` the name a technique takes in the address. The view reads Table E-1 for the program's catalog edition once and the techniques in the framework's order; a control record reads its own links alone.

`supportedGuidance` joins a control's techniques and approaches with what `itemGuidance` in `src/lib/frameworks.ts` reads of each: the definition, the one-line description, the discussion and the examples Table D-4 prints. `src/lib/control-threats.ts` regroups Appendix F's rows for a control into one line a technique (`controlThreats`) and counts a program's risks by technique identifier (`risksByTechnique`). A control record reads the techniques and approaches once for every control.

## Two baselines in one stack

A program profile's stack can start from two reference baselines combined: High and Privacy is 370 and 96 controls, 53 of Privacy's beyond High, so the stack starts from 423. The first stays the root of the profile chain; the second is the layer right above it, authored by `author_tailored_profile` like every other layer (`combine_reference_baselines`), adding each control the second selects and the first does not with "Selected by NIST SP 800-53 Rev 5 Privacy baseline." as its rationale, and `profile_baseline_combinations` names the second baseline behind that layer. So the stack stays an import chain the resolver already checks, the layer's selection is the union, and every read of a program's baseline (`program_control_status`, `program_resiliency_choice`, `program_control_parameters`, the `profile_resolution_catalogs` view) reads it without a change.

- **Setup.** `create_program_wizard` takes `combinedResolutionId` on a program profile beside `baseResolutionId`. Both are published reference baselines on the program's catalog edition, two different ones; a second the first holds whole adds nothing and is refused, and so is one that sets parameter values (none the workspace holds does). The same base with and without a second baseline are two program profiles.
- **Changing the overlays.** `set_program_baseline_overlays` keeps the combined root: the layer that combines the second baseline is part of the root the overlays are applied on again, so Edit overlays shows it as the stack table's second row, with no actions.
- **On screen.** Program setup offers Combine with under a chosen reference baseline. The stack table, in setup, on the Overview and in Edit overlays, shows both baselines as its first rows (Type Baseline), and the Control baseline view lists them first: the second's row reads "Baseline · +53 · 423", its step is headed "423 controls in NIST SP 800-53 Rev 5 High baseline and NIST SP 800-53 Rev 5 Privacy baseline", and its switch reads the stack without it. The walker names such a layer `baseline` (`layerKinds` in `src/lib/baseline-stack.ts`), from `profile_baseline_combinations` on a saved stack and from the second's selection in setup's draft stack.

## Versions of an overlay

A published overlay cannot change, so deciding differently is a new version. Each version is an overlay row of its own, chained to the version it was created from (`previous_overlay_id`) and numbered (`version`), sharing the overlay's code: (tenant, code) names the overlay and (tenant, code, version) one version. A chain rather than revisions under one record, because everything that applies an overlay names the exact row it applied (`profile_overlay_applications`, the layer's authored profile, the program's stack): kept as rows, each of those keeps meaning that version, and a draft version can be deleted without touching the published one.

- `create_control_overlay_version(p_tenant_id, p_overlay_id, p_version_id)` makes the next version of a published overlay as a draft: the same code and catalog edition, its name, description, decisions and parameter values, numbered one more, under the id the caller chose once, so the same request sent again answers the same draft. A version has at most one next version (a unique index on `previous_overlay_id`), so the chain is a line and a next version is made from the newest; a draft has none.
- A version keeps its overlay's code; its name and description may change. Another overlay may not take the code.
- Deleting a draft version deletes it alone; the version before it stays, and may take a next version again.
- A program's stack keeps the version it applied until someone changes it. Taking a newer version is `set_program_baseline_overlays` with the newer version in the older one's place: the layers beneath stay, and the newer version and everything above it are applied again.
- `control_overlay_rows` gives each version its `version`, `previous_overlay_id`, `next_overlay_id` and `overlay_application_count`, the baselines that apply any version of the overlay.

On screen: the register lists each overlay once, at its newest version, with a Version column, and Applied counts every version's baselines. The record has a version menu in `PageHeader.Actions`, "Version 2" and a radio row a version with its state, newest first; choosing one opens it in place. Create version 3 is a command of the Actions menu on a published newest version, a confirmation that says the published version stays, and opens the draft; on an older version it waits and names the newest. A draft after the first is deleted with Delete draft version, which opens the version before it. Edit overlays says when a newer version of an overlay in the stack is published, in a status Alert with Take version 2 for each, which puts the newer version in its place for the reader to apply; Add overlay, there and in program setup, offers each overlay at its newest published version and none the stack holds in any version. A layer of a version after the first is named with its version ("Version check · version 2").

## Changing the stack after creation

`set_program_baseline_overlays(p_tenant_id, p_choice_id, p_expected_revision, p_request_id, p_overlay_ids)` changes the overlays of one program profile (its `program_reference_choices` row, at the revision the reader saw) to `p_overlay_ids`, a JSON array of overlay ids in the order they apply, bottom up, at most six. It runs as its owner, as the other overlay commands do, and asks for workspace write access: a viewer is refused.

- **The stack it reads.** The chain from the choice's resolution down to its root, the reference baseline. Above the root are the overlay layers (each with its `profile_overlay_applications` row) and at most one layer no overlay accounts for, the program's tailoring, which must be last; any other shape is refused.
- **What it writes.** The layers the new order shares with the old one from the bottom stay as they are; each overlay after them is applied to what is beneath it through `apply_control_overlay`, which refuses one that changes nothing where it sits. The overlays must be published, in the workspace and on the program profile's catalog edition.
- **The tailoring stays last.** It is authored again on the new top with its decisions and parameter values, each with its rationale. A decision the new stack already makes true (an add of a control it selects, a removal of one it leaves out) and a parameter value of a control it no longer selects are left out of the layer, and the answer names them; a tailoring left with nothing to change is not authored, and the program adopts the top overlay layer. What is left out is not brought back by a later change.
- **Systems.** Each system of the program whose explicit adoption is the old top adopts the new one, at its next revision. A system that adopts anything else (its own tailored baseline layered on the old top, another program profile, a reference baseline) keeps it, and an element that inherits follows the system that contains it.
- **SSP revisions never change.** The schema pins each one to the resolution it implements (`stable_context` on `ssp_revisions.profile_resolution_id` and `implemented_requirements.selected_control_id`), so a published SSP keeps its exact baseline and so does a draft. The answer names the SSP revisions left on the old top; the SSP assembly says when a system's baseline differs from its SSP's, and the system's next SSP revision takes the new baseline.
- **The old layers stay.** They are published profiles, so an SSP pinned to one still reads it.
- **Sent again.** The same request id with the same request answers what it answered; the same id with another change is refused (`PT409`). The overlays the stack already holds, in its order, write nothing. A request at a revision another session moved on is refused (`PT409`), and the Dialog then reads the stack again behind itself.

The answer: `choiceId`, `programId`, `changed`, `profileResolutionId` (the new top), `previousProfileResolutionId`, `revision` (the choice's), `overlayIds`, `controls` (`before`, `after`, `added`, `removed`), `tailoring` (`authored`, `decisions`, `parameters`, `alreadySelected` and `notInBaseline` by control code, `parametersDropped` by parameter id; null for a stack without one), `systems` (each moved system's `id` and `code`) and `ssps` (each SSP revision left on the old top: `id`, `systemId`, `systemCode`, `version`, `state`).

`src/lib/program-overlays.ts` holds the command (`useSetProgramBaselineOverlays`) and `restackPreview`, which reads a changed stack the way the command will author it, for the Dialog's What changes.

## SA-24: the program's resiliency choice

No reference baseline selects SA-24, Design for Cyber Resiliency: a program tailors it in and sets its five parameters (`sa-24_odp.01` to `.05`: goals, objectives, techniques, implementation approaches, design principles) in the same tailoring. Setup offers their values from the cyber resiliency framework (`nist-sp800-160v2r1-cref`): 4 goals, 8 objectives, 14 techniques, 50 approaches under their techniques, and 5 strategic and 14 structural design principles. A value is stored as the item's title, since an OSCAL parameter value is text, so the authored profile reads `"values": ["Anticipate", "Withstand"]`.

`program_resiliency_choice(p_program_id)` reads the choice back: `selected` when a control baseline of the program selects SA-24, and for each of the five lists the codes of the items its effective values name, in the publication's order, with `unmatched` for the values that name none. A value is effective as `author_tailored_profile` resolves it: the nearest layer of the stack that sets the parameter, else the catalog's own. A value names an item when it is the item's title, whatever its case and the space around it, and the item is of the parameter's kind. A program with several program profiles answers as one: every item any of them names. The function runs as the caller and refuses a program the caller cannot read. `src/lib/resiliency-choice.ts` holds the read (`useProgramResiliencyChoice`) and what each parameter may name (`resiliencyVocabulary`).

The chosen values show on the profile record's Tailoring tab, under Parameters and Inspect parameters. The program's control record prints the control with its assignment placeholders and the catalog's values, not the program's.

## Demo

The CNSSI allocation is a third-party extraction the fixture marks as not authoritative. WS-X90's systems keep the archived selections their SSPs were imported with; the stack is recorded as the program's reference choice. `npm run seed:demo-showcase` then adds the program's own tailoring on top, SA-24 and 13 cyber resiliency controls (560), and moves the reference choice to it (`docs/demo-seed-mapping.md`, Showcase scenario).

Read by technique, every count on WS-X90 rises at the CNSSI 1253 allocation and holds after it: Segmentation 7 of 41 in High and 16 of 41 from there on, Substantiated Integrity 20 then 35 of 58, Unpredictability 1 then 2 of 7, Dynamic Positioning 0 then 1 of 8. WS-X90 does not select SA-24, so its Select is one list.

The Cyber resiliency view says the same of the whole ladder: High alone holds 64 of the 265 controls Table E-1 names, the CNSSI 1253 allocation adds 70 and removes 3, and the count stays at 131 through the three layers after it. 11 of the 50 approaches have no control behind them in WS-X90's baseline (21 at High alone).

On a control: SC-7 supports Segmentation through Predefined Segmentation (13 examples) and counters 14 ATT&CK techniques. AC-2(8) supports Adaptive Response through three approaches (14 examples) and Privilege Restriction through one (6). Table E-1 names 265 controls and Appendix F 186; 181 are named by both. No risk of WS-X90 names an ATT&CK technique yet, so the Risks column reads 0.
