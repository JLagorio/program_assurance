# Reference releases and database seeding

The application starts with no programs, systems, requirements, implementation claims, evidence, test results, risks, or authorization decisions. Those records must be created from actual work. Reference publications are separate: the local database can be populated with the actual NIST catalog, NIST baseline profiles, DISA CCI list, and the NIST SP 800-160 frameworks that this project transcribes from their PDFs.

Run `node scripts/seed-reference.mjs` after the local schema migrations. The importer connects only to the `supabase_db_program-assurance` container through the dedicated `~/.colima/program-assurance/docker.sock` socket. It does not accept a remote URL or write a service-role key to the application. Run `node scripts/seed-reference.mjs --check` to verify source hashes and normalized records without connecting to a database.

Every source is tracked under `supabase/reference/`. A source is either a compressed copy of the exact fetched bytes or a transcription, which [Transcribed frameworks](#transcribed-frameworks) describes. [The manifest](../supabase/reference/manifest.json) records each source URL, publication release, retrieval date, authority, rights, byte count, and SHA-256 of its **decompressed** content. Seeding needs no network connection and does not depend on the old ignored `docs/examples` directory. A changed hash or missing file fails before any database mutation.

The NIST copies came from NIST's OSCAL content repository. The DISA list came from the public mirror named in the manifest; `ref_sources.authoritative` is **false** for that copy. The source's `draft` CCI status is retained as published by DISA; importing the release does not assert that each item is an approved CCI. Empty source contributors become SQL `NULL`. Missing values are never filled with a plausible name, date, score, or conclusion. The importer names each stable catalog and profile record with a short display title (`displayTitles` in `scripts/seed-reference.mjs`: NIST SP 800-53 Rev 5, NIST SP 800-53 Rev 5 Low baseline, and so on); the revision keeps the document's own OSCAL title, so nothing about the source is lost.

The importer preserves the original OSCAL JSON and CCI XML in document/release records. The compressed source files preserve the exact artifact bytes corresponding to each hash. Normalized records retain source identifiers separately from database UUIDs. Control parts preserve every nested statement, objective, method, and container; raw parameter insertion tokens remain unchanged. Parameters, choices, guidelines, and values are separate records. All historical CCI publication references survive import; older publications remain `unsupported-publication` because those catalog revisions have not been imported. A Rev. 5 source control index yields a control link only. It does not establish an assessment-objective link.

The bundled profile resolver supports the exact NIST source form: explicit selected IDs, `merge.as-is: true`, and no modifications. Every selection points to the source import and rule, and every resolution pins both document revisions plus input/output hashes. An unsupported profile construct fails instead of producing a partial or misleading resolution. Authoring an arbitrary OSCAL profile is supported by the relational schema; executing general import/merge/modify resolution requires a complete OSCAL resolver.

All imports run in one transaction under an advisory lock. IDs are deterministic for a source release and source location. Repeating the import skips existing records and preserves publication timestamps and audit history. Published document/catalog/profile/CCI revisions and their descendants reject update, delete, reparenting, and further child insertion. New releases receive new revision identities; no published history is overwritten. Shared references are readable by authenticated users and writable only by the database importer. Tenant-authored reference documents use tenant membership access policies.

For review or combined migration verification, `node scripts/seed-reference.mjs --sql /tmp/reference.sql` writes the exact transactional SQL without applying it. Never place a database password or service key in that file; none is required or emitted.

To update a reference publication, download the intended official release into a temporary directory, inspect its metadata and changes, compress the original bytes into `supabase/reference/`, and update the manifest's actual provenance and digest. If an authority republishes changed bytes with the same human version label, the content hash gives it a separate revision. A previously imported profile remains pinned to its original catalog revision; attempting to silently reuse that profile revision against changed catalog bytes fails. Such a dependency change requires a new profile revision with its new inputs explicitly recorded. The current importer intentionally contains no fictional development seed.

## Transcribed frameworks

NIST publishes SP 800-160 as a PDF only. Parts of it are reference data all the same, read beside the control catalog: the cyber resiliency constructs of Volume 2 with the controls that support them, Volume 2's analysis of ATT&CK for Enterprise techniques in its Appendix F and of ATT&CK for ICS techniques in its Appendix G, and the system life cycle processes of Volume 1 with their security outcomes.

A transcription is this project's reading of those printed tables into the `reference-framework/1` format, which `scripts/reference-transcribe/lib.mjs` defines and checks. A file holds one framework: its items (a technique, an approach, a process, an outcome), each with its kind, the item that holds it and where it is printed; the links the publication prints between items; the links it prints between a control and an item; and a list of corrections, one for every place the transcription departs from the printed text, with the reason. One script for each file reads the PDF's text through poppler's `pdftotext` and writes the file. The PDF is not stored in the repository. The file's `source` block and the manifest's `transcribed_from` name it by title, URL, SHA-256 and byte count, and a script refuses any other file. The manifest pins the transcription's own decompressed bytes like any other source, and its `authoritative` is **false**: the authority is the PDF.

`node scripts/seed-reference.mjs --check` verifies each transcription before anything is written:

- its bytes against the pinned hash and byte count;
- the format's own checks, and that the bytes are the format's serialization of their content;
- that the manifest's `transcribed_from` names the document the file says it was read from;
- that every item a link names exists, in the same file or in the pinned transcription of the framework the link names, and that the technique a control link is printed under (`props.technique`) is an item of the same file;
- that every control label, such as AC-2(6), is the label of an active control of the pinned catalog revision.

A label that names a withdrawn control, or no control, fails the check with its place in the publication. Nothing is imported on a guess. One label the publication prints does not resolve: Table F-8 names CM-4(4) for the technique T1574 under the mitigation M1038, and the pinned SP 800-53 Rev. 5 catalog has no CM-4(4). The transcription makes no control link for it and keeps it on its row as `props.controls_not_in_catalog`, beside the row's other control, CM-7(5), which does resolve.

The records go into `frameworks`, `framework_revisions`, `framework_items`, `framework_item_links` and `framework_control_links`. They follow the reference schema as the CCI tables do: a shared row has no tenant, only the importer writes it, and a published revision with its items and links rejects change. A revision keeps the document it was transcribed from, the method and the corrections; every other member of the file is a row, so the file's JSON is not stored a second time. Its identity (`input_sha256`) covers everything it was built from: the transcription, the catalog revision its control labels were resolved against, and the framework revisions its links name. A corrected transcription, a new catalog release, or a correction to a framework that another one names is therefore a new revision beside the old one, and no published row is written again. Frameworks are imported in the order their links need.

Table D-4 prints, beside each technique and approach, the guidance for applying it. An item's `prose` is its definition. A technique's `props.discussion` is the Discussion in the table's first column. An approach has its `props.informal_description`, its `props.discussion` and its `props.examples`: the bullets of the table's Examples column in printed order, one text a bullet, a bullet that wraps over lines joined into one and a word hyphenated at a line's end keeping its hyphen. A control reaches this guidance through Table E-1: the approaches it supports carry the examples. Tables 2 and 3 print a Discussion under each goal's and objective's definition, the paragraph that opens with "Discussion:" to the end of the row (on the next page too); it is the item's `props.discussion`, as a technique's is, and its `prose` stays the definition.

Table D-5 marks with an X the architectural layers at which each approach can be used. Its eleven columns are items of their own, kind `architectural-layer`, code `layer.<name>`, in the order of the columns (Hardware and Firmware to Environment of Operation), with no prose, since the table defines none; an X is a `used-at` link from the approach to the layer, named `D-5:<approach>:<layer>`, 240 in all. The layers are items rather than a list on each approach because the table relates two vocabularies, as Tables D-12 to D-15 do, and a layer is one thing the 50 approaches share: a layer is read once, an approach's layers are its links, and a question from the layer's side (the approaches usable at Operations) needs no scan of every approach. Each layer keeps the headings it is printed under, outermost first, as `props.within` (Socio-Technical System, Technical System, Software): the headings are turned up the page and centred in their cells, and the script tells which rows of grouping headings stand over a layer by where its heading's middle stands, then checks that each grouping heading stands over the middle of the run of layers it groups. Table D-5 lists every approach once, under the technique Table D-4 holds it under, though it puts Coordinated Protection before Contextual Awareness.

A control link of Table E-1 keeps the technique group it is printed in as `props.technique`. That is the approach's own technique in every row but one: the table lists Self-Challenge, a Coordinated Protection approach, under Deception for SR-7. `framework_control_link_rows` gives the group as `technique_code` and `technique_title`, and a reader takes a link's technique from there, never from the approach's parent.

An Appendix F link keeps the row it is printed in as `props`: the tactic and the mitigation by their item codes, the approaches as references to the cyber resiliency constructs (`approaches`, and `approach` when the row names exactly one), and the effects by the names of the effect items. A row that names several approaches is one item link for each. Three rows print "Standard practice" where an approach belongs; they have no approach link, and their controls keep the words as `approach_as_printed`.

Appendix G analyses ATT&CK for Industrial Control Systems as Appendix F analyses ATT&CK for Enterprise, in tables of the same columns: Tables G-1 to G-12, one a tactic, and Table G-13, its candidate mitigations. It is a framework of its own, `nist-sp800-160v2r1-attack-ics`, with items of the same kinds as Appendix F's (tactic, attack-technique, mitigation, candidate-mitigation). ATT&CK for ICS numbers its own tactics, techniques and mitigations, and the appendix presents its mappings "as separate tables" (Section G.1); nine of its twelve tactics share a name with an Enterprise tactic and would share its code in one framework (`tactic.initial-access`), and Table G-13 defines its candidate mitigations again under its own identifiers (Passive Decoys is CM1104 in Table F-17 and CM1204 in Table G-13). A framework of its own also leaves Appendix F's file as it was pinned. The appendix prints no table of effects: a row's effects are Table F-1's, named by title as Appendix F's rows name them, and its script checks them against the pinned Appendix F transcription. Section G.1.2 says a control is printed in bold where the analysis matched the mitigation better than the SP 800-53 controls ATT&CK for ICS identifies for it; a bold word's box is taller than a regular one's, every control label is one or the other, and a control printed in bold keeps `bold: true` on its link (547 of 999, all under ATT&CK mitigations). Table G-7 gives Default Credentials (T0812) no mitigation and prints dashes in its other cells; its tactic link keeps the words as `mitigation_as_printed`. The notes after each table, which relate the techniques to ATT&CK for Enterprise, are not transcribed. Both appendices are read by one module, `scripts/reference-transcribe/attack-appendix.mjs`, and each script names its tables, the counts its reading must reach and its corrections.

Each import names the revision built from the pinned files in `frameworks.current_revision_id`. The views `framework_rows`, `framework_item_rows` and `framework_item_link_rows` answer for that revision, so the product reads what the manifest pins, also after a transcription is corrected or an earlier one is pinned again. `framework_control_link_rows` answers for it too, and for a catalog revision the current revision was not read against it keeps the latest revision that was: a program on an earlier catalog edition keeps the links to its own controls. The application reads the views through `src/lib/frameworks.ts`.

A new revision gives every item a new id and leaves its code as it was, so an item is named by its code. The revision it replaces stays in the database, published and no longer current: a database that imported an earlier pin holds both, and a new database holds the pinned one alone. A new revision of the cyber resiliency constructs is also a new revision of Appendices F and G, whose links name its approaches. A record that names an item keeps the id of the revision it was made from, and is read by the item's code: a risk's ATT&CK techniques (`risk_attack_techniques`, a technique of either appendix) and the security outcome a gate criterion was drawn from (`gate_criteria.outcome_item_id`). Adding Tables 2, 3 and D-5 to the constructs made new revisions of them and of Appendix F; every risk's techniques, every gate's outcomes and every program's SA-24 choice read the same after the import as before.

To re-derive a transcription, download the PDF from the URL the manifest names and run the file's script with `--check`:

```sh
node scripts/reference-transcribe/sp800-160v2r1-cref.mjs --pdf <path> --check
```

The scripts are `sp800-160v2r1-cref.mjs`, `sp800-160v2r1-appendix-f.mjs` and `sp800-160v2r1-appendix-g.mjs` for Volume 2 and `sp800-160v1r1-processes.mjs` for Volume 1. A script refuses a PDF whose SHA-256 is not the pinned one, transcribes it, and compares the result with the pinned file; it writes nothing. Without `--check` it writes the file, and `--json <path>` adds a plain copy to review; the manifest's `sha256` and `uncompressed_bytes` then take the values the script prints. Re-deriving needs poppler's `pdftotext` 26.04.0, the version the pinned files were made with, and the PDF. Another version can lay the text out differently, and the comparison then fails. Seeding and CI need neither poppler nor the PDFs.

The manifest's `rights` records, for each transcription, what the publication says of itself, NIST's statement for its Technical Series publications as its site gives it, and the attribution NIST asks for: its recommended citation followed by "Republished courtesy of the National Institute of Standards and Technology." Both publications name authors at NIST and at The MITRE Corporation. Appendices F and G name MITRE ATT&CK tactics, techniques and mitigations by their ATT&CK identifiers and names, so their entries also record MITRE's terms of use for ATT&CK as its site gives them: a non-exclusive, royalty-free license for research, development and commercial purposes, on condition that a copy reproduces MITRE's copyright designation and the license. Appendix F cites ATT&CK for Enterprise, Appendix G names ATT&CK for ICS, and neither names an ATT&CK version. Volume 1 reprints passages of ISO/IEC/IEEE 15288 with IEEE's permission, each under the notice "Reprinted with permission from IEEE, Copyright IEEE 2015, All rights reserved." Its transcription leaves those passages out, and each process's Security Purpose with them, and keeps the process names and NIST's security outcomes.
